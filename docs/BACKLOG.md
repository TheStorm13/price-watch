Завершённые задачи удалены; их решения и проверки сохранены в ADR и отчётах.
Идентификаторы оставшихся задач сохранены для ссылок.

Приоритеты: **P2** — ближайшие технические работы, **P3** — улучшать при развитии

### Архитектура и качество кода — 3 задачи

- [ ] **ARCH-01 · P2. Разделение ответственности desktop runtime.**
  Локальные службы уже вынесены в `native_services.rs`, но `RuntimeState`
  в `lib.rs` по-прежнему объединяет управление worker и Chrome, миграцию
  профиля, окружение и публикацию состояния. Определить границы компонентов
  и явный порядок запуска и остановки. Сохранить IPC, фоновый режим,
  восстановление служб и жизненный цикл профиля. Эта задача объединяет
  прежний пункт «Упорядочение запуска desktop-служб».

- [ ] **ARCH-04 · P3. Общая фабрика коннекторов.**
  В `price_watch/cli.py` параметры `AsyncOzonClient` отдельно собираются
  для прямого сбора и worker. Вынести создание коннекторов в одну фабрику
  с явными параметрами браузера, режима и обработчиком проверки. Сохранить
  асинхронный контракт, queued-сбор, `main.py collect` и numeric JSON mode
  без `DATABASE_URL`. Задача перенесена из прежнего архитектурного backlog.

- [ ] **ARCH-05 · P2. Автоматизация и расширение desktop-проверок.**
  Изолированный smoke Tauri → API → worker → собственная БД уже существует:
  `scripts/smoke_reliability_desktop.py`. Он использует fake connector,
  проверяет повтор сбора через настоящий WebView и восстановление API.
  Автоматизировать подготовку среды и запуск, определить дополнительные
  сценарии и статические проверки: frontend-команда `lint` сейчас выполняет
  только TypeScript-проверку. Реальный Ozon и CAPTCHA остаются вне этого smoke.
  Не использовать пользовательские данные и не считать mock E2E проверкой
  живых служб. Источники: `scripts/smoke_reliability_desktop.py`,
  `frontend/package.json`, `docs/guide/TESTING_AND_TROUBLESHOOTING.md`.

### Потенциальная точка роста: полный перенос Python на Rust

**Состояние:** идея для будущей оценки, добавлено 2026-11-11; решение о переносе
не принято, реализация не начата. Не является обязательным условием выпуска
Windows-версии и не входит в три текущие задачи «Архитектура и качество кода».

Рассмотреть полный отказ от Python в поставляемом приложении: перенести backend,
worker, сборщики маркетплейсов и CLI на Rust. Сохранить React/Tauri-интерфейс
и PostgreSQL; переписывание интерфейса на Rust и смена БД в это предложение
не входят. Возможная польза — исключить Python-окружение из установки и объединить
сопровождение backend и desktop runtime на одном языке. Выигрыш в размере,
скорости запуска и надёжности требует измерений и заранее не гарантируется.

**Предполагаемый объём:**

- Перенести каталог, группы и варианты, историю, правила выгодных предложений,
  импорт/экспорт и настройки с сохранением текущих контрактов и данных.
- Перенести работу с PostgreSQL и исполнение миграций; определить переход
  с Alembic с учётом уже применённых ревизий, резервного копирования
  и восстановления после неудачной миграции.
- Перенести очередь, расписание и worker: владение заданиями, параллелизм,
  таймауты, повторы, отмену и восстановление после сбоев.
- Перенести все действующие коннекторы: Ozon, AliExpress, Wildberries и
  Яндекс Маркет. Сохранить семантику цен, вариантов и доступности, авторизацию,
  обработку проверок магазинов и отсутствие дубликатов истории.
- Заменить Python/Playwright-управление браузером Rust-реализацией через CDP;
  `chromiumoxide` рассмотреть как кандидата, а не утверждённую зависимость.
  Проверить постоянный профиль Chrome, cookies, ручной вход, передачу профиля
  между просмотром и сбором, восстановление сессии и корректное завершение.
  JavaScript, выполняемый в контексте страницы магазина, при необходимости
  сохраняется; отказ от Python не означает отказ от Chrome или PostgreSQL.
- Сохранить необходимые API- и CLI-сценарии, queued-сбор и отдельный numeric
  Ozon JSON mode без `DATABASE_URL`. Отдельно решить, где нужен HTTP API,
  а где достаточно команд Tauri; не удалять API без оценки его потребителей.
- Обновить упаковку Linux/Windows, автоматические проверки, документацию
  и диагностику. После завершения перехода удалить заменённые Python-модули,
  зависимости, конфигурацию и точки входа; не оставлять legacy/fallback-режим.

**Первый шаг для оценки:** отдельный прототип Rust → Chrome → авторизованный
профиль → получение товара → повторный сбор → штатное завершение на Linux
и Windows. Сравнить с текущей реализацией точность результата, устойчивость,
отмену и восстановление. Успех одного товара не считается подтверждением
готовности всех коннекторов и всех режимов работы.

**Условия перехода к реализации:** оценить стоимость и ожидаемую пользу,
проверить браузерный прототип, согласовать архитектуру и ADR, затем оформить
спецификацию через выбранный workflow. Планировать последовательный перенос
с проверкой эквивалентности на одинаковых входных данных и одноразовых БД,
с сохранением пользовательской истории и Linux/Windows-поведения.
Это самостоятельная потенциальная переработка backend, а не способ сократить
объём уже предложенной задачи Windows-установщика.

### Повторное появление товара и уведомления

**Состояние:** предложение, требует проверки и доработки.

Добавить статус «Появился в наличии». Правила отображения статусов:

- **«Появился в наличии»** — товар сейчас доступен, а за последние 7 дней хотя бы
  раз было зафиксировано его отсутствие. Сохранять статус, пока оба условия
  выполняются.
- **«В наличии»** — товар сейчас доступен, а в последние 7 дней больше нет
  зафиксированного отсутствия.
- **«Нет в наличии»** — товар сейчас отсутствует.

Уведомления также нужны, в том числе для повторного появления товара в наличии.
Их содержание, формат и правила отправки пока не определены; согласовать их
перед реализацией с учётом существующих уведомлений о выгодных предложениях.

Пока действует статус «Появился в наличии», показывать товар среди выгодных
предложений с этой отметкой, чтобы он не терялся среди остальных предложений.
Проверить переходы статусов на границе недельного периода, повторное отсутствие,
поведение в группе и при обоих видах отображения.

## Сбор и автоматизация

### Повтор неудачных обновлений в рамках одного запуска

**Состояние:** предложение, не реализовано.

Для каждого товара, обновление которого завершилось ошибкой, выполнить один
повтор через 2 секунды. Повтор входит в тот же запуск обновления.
До завершения повторной попытки не показывать пользователю окончательную
ошибку товара и не включать его в итоговое число неудачных обновлений.

Например, если два товара завершились с ошибкой, сначала повторить обновление
этих товаров и только затем показать итог запуска. Успешные товары повторно
не обновлять; после неудачного повтора показать окончательную ошибку.

### Обновление цен всех вариантов для статистики

**Состояние:** предложение, не реализовано.

Обычное обновление цены уже существует: оно собирает цены главного и отмеченных
для отслеживания вариантов. Добавить отдельное действие для обновления цен всех
вариантов товара, включая неотмеченные, чтобы накапливать историю и статистику
по каждому варианту. Такой запуск не должен менять отметки отслеживания.

### Таймауты AliExpress в эксперименте с N=8

**Состояние:** отложено пользователем 2026-11-08; причина не установлена.

В двух прогонах на одинаковых 40 SKU с concurrency=8 и без pacing первые
восемь browser fetch evaluations завершились таймаутами без наблюдаемого
HTTP-статуса; остальные 32 запроса не отправились после отказа транспорта.
Весь пул без ограничения в двух других прогонах дал 40/40 успешных результатов.
Перезапуск Chrome и пауза 10 секунд между попытками не устранили сбой N=8.
Это не доказательство блокировки AliExpress или преимущества большего N.

В отдельной будущей задаче установить, где возникал сбой: browser evaluation,
fetch/abort либо координация транспорта. Использовать сохранённые данные;
повторять live-прогон только с конкретной диагностической целью.
Диагностика прежнего N=8 не входит в текущий переход всех коннекторов на
max_in_flight_requests=100; обычные проверки очереди, таймаутов и освобождения
слотов новой реализации остаются обязательными. Запись не означает исправления
или приёмки открытого эксперимента.

Источники: [Ali experiment](../openspec/changes/experiment-aliexpress-unpaced-concurrency/spec.md),
[первый N=8](../openspec/changes/experiment-aliexpress-unpaced-concurrency/measurements-n8.json),
[повторный N=8](../openspec/changes/experiment-aliexpress-unpaced-concurrency/measurements-restart-8.json).

### Ограничение запросов AliExpress

**Состояние:** ограничение действует, отмечено 2026-11-03; пересмотр не реализован.

Сейчас AliExpress урезан по запросам: по умолчанию выполняется только один
одновременный запрос (`concurrency=1`), при ограничителе старта 5 запросов/сек.
Это текущая политика приложения. Она сохраняется и при отслеживании всех SKU,
поэтому товары с множеством вариантов собираются дольше.

Отдельной задачей измерить скорость успешного сбора, частоту 429/CAPTCHA и
повторов, затем оценить увеличение параллелизма или настройку лимитов.
Сохранить общий cooldown, ограниченное восстановление сессии и точную историю
каждого SKU. Источники: `marketplace_connector/connectors/aliexpress/client.py`
и `marketplace_connector/connectors/aliexpress/json_transport.py`.

### Ускорение асинхронного JSON-сбора Ozon

**Состояние:** реализовано и принято 2026-11-08, коммит `31f6a1d`.

Выбраны асинхронный сбор без планового лимита частоты и фиксированный N=8.
Транспорт и общий сборщик используют восемь слотов Ozon; остальные коннекторы
сохраняют прежнюю политику. Retry-After, конечные повторы, таймауты, recovery,
отмена и правила сохранения истории сохранены. Миграций данных нет.

Проведены A/B/C, C/D и фиксированные N=5/8/12 сравнения на одинаковых 40 SKU.
Короткие замеры не доказывают длительную устойчивость; в последней серии два
пакета завершились ошибкой подготовки сессии до отправки товарных запросов.
Проверки реализации: 104 теста без ошибок, 7 DB-зависимых пропусков.
Политика и ограничения: [ADR0014](adr/0014-ozon-unpaced-async-concurrency.md).
[Принятый результат и сырые метрики](../openspec/changes/archive/2026-11-08-experiment-ozon-serial-dispatch/spec.md).

## Сборка и развёртывание

### Windows: автономная установка и обновление

**Состояние:** предложение, добавлено 2026-11-11; реализация не начата.
Приоритет, сроки, поддерживаемые версии Windows и окончательные технические
решения требуют оценки. Запись фиксирует объём будущей работы и не заменяет
согласование архитектуры и спецификации перед реализацией.

**Цель:** пользователь скачивает один `PriceWatch-Setup.exe`, устанавливает
приложение и работает с собственной локальной БД без ручной настройки Python,
PostgreSQL, API и worker. Повторная установка новой версии сохраняет каталог,
историю цен, настройки и авторизованный профиль браузера. Сервер для хранения
пользовательских данных и Docker для обычного запуска не требуются.

**Текущее состояние и ограничения:**

- Linux-релиз содержит Tauri-бинарник и Python-код; PostgreSQL, Python-зависимости,
  Google Chrome, Xvfb и xauth предоставляет система через пакетные зависимости.
  Это пока не автономный комплект для Windows.
- В `frontend/src-tauri/tauri.conf.json` установочная упаковка отключена
  (`bundle.active: false`), а `desktop:build` использует `--no-bundle`.
  Скрипт `packaging/make-linux-release.sh` поддерживает только Linux x86_64.
- `native_services.rs` использует Unix-права, сигналы, `/dev/urandom`,
  Unix-сокеты PostgreSQL и обязательный Xvfb. В `lib.rs` остаются Unix-импорты,
  Linux-пути, XDG/HOME-каталоги и Linux-команды запуска Chrome.
- Браузерный сбор использует платформенные параметры Chrome и скрытый X-дисплей.
  Работоспособность авторизации, проверок магазинов и скрытого сбора на Windows
  не подтверждена. Переключение на headless само по себе не считается решением.
- npm-скрипты используют POSIX-запись переменных окружения
  (`VITE_DESKTOP_MODE=true ...`), которую необходимо адаптировать для Windows.

**Предлагаемое направление:** сохранить React/Tauri, PostgreSQL и Python API/worker;
поставлять Windows-окружение вместе с приложением. Не включать переход на SQLite
или другую БД в эту задачу. Начать с Windows x86_64 как кандидата для первого
релиза, затем согласовать точную матрицу поддержки. До существенной перестройки
runtime сравнить варианты, согласовать ADR и оформить изменение через выбранный
в проекте workflow. Связать работу с ARCH-01, не расширяя её до общего рефакторинга
всего приложения.

**Необходимые доработки:**

1. **Платформенные границы desktop runtime.** Отделить общую последовательность
   запуска/восстановления служб от операций Linux и Windows. Убрать безусловные
   Unix-импорты из общего кода. Определять ресурсы установленного приложения через
   runtime-пути, а не через исходный checkout, `/usr/lib` или путь машины сборки.
   Учесть `.exe`, пробелы и кириллицу в путях; сохранить рабочий Linux-сценарий.

2. **Каталоги, доступ и блокировка запуска.** Предлагаемый каталог данных —
   `%LOCALAPPDATA%\PriceWatch`, отдельно от файлов установки. Разместить там БД,
   профиль браузера, настройки, логи и резервные копии; точную структуру согласовать.
   Настроить пользовательские права доступа Windows вместо Unix mode bits,
   системный источник случайности вместо `/dev/urandom`, блокировку второго
   владельца БД/профиля и понятные ошибки доступа. Разделить данные разных
   пользователей Windows и не записывать изменяемые файлы в каталог программы.

3. **Поставляемый PostgreSQL.** Подготовить проверенные Windows-бинарники и все
   необходимые библиотеки/ресурсы, включая инструменты создания БД, проверки
   готовности, резервного копирования и восстановления. Приложение должно
   создавать собственный кластер и запускать его без регистрации общей системной
   службы. Вместо Unix-сокета настроить loopback TCP, аутентификацию и защищённое
   хранение необходимых секретов; не открывать БД во внешнюю сеть. Учесть занятые
   порты, отсутствие конфликта с установленным PostgreSQL и восстановление после
   аварийного завершения.

4. **Python и зависимости.** Выбрать и проверить способ поставки: отдельное
   окружение Python с зависимостями либо упакованный backend. Пользователь не
   должен устанавливать Python, запускать pip или скачивать зависимости при
   первом старте. Проверить Windows-совместимость зависимостей и lock-файлов,
   поставку Playwright driver, PostgreSQL-драйвера, миграций Alembic и ресурсов.
   Удалить предположения о `.venv/bin/python` и `python3`. API, worker и миграции
   должны запускаться из установленного комплекта без исходного репозитория.

5. **Жизненный цикл процессов.** Реализовать Windows-механизм владения API,
   worker, PostgreSQL и Chrome, включая контролируемое завершение дерева
   процессов и защиту от оставшихся процессов после падения приложения.
   Оценить Windows Job Objects и штатные способы остановки каждой службы.
   Не заменять все Unix-сигналы безусловным принудительным завершением:
   сохранить отмену сбора, корректное закрытие профиля и безопасную остановку БД.
   Учесть частичный запуск, повторную попытку, таймауты, восстановление служб,
   скрытие лишних консольных окон и диагностику ошибок.

6. **Chrome и сбор маркетплейсов — главный исследовательский риск.** Выбрать
   поставляемый браузер или поддерживаемый установленный Chrome; проверить поиск
   исполняемого файла и совместимость версий. Убрать обязательность Xvfb/xauth
   для Windows и Linux-флаги запуска. Отдельно проверить headless и обычное окно,
   вход пользователя, CAPTCHA/другие проверки, сохранение cookies, общий профиль,
   ручное открытие магазина и передачу профиля между ручным просмотром и сбором.
   Согласовать, когда допускается видимое окно и как приложение объясняет
   необходимость действия пользователя. Не обещать полностью незаметный сбор
   до проверки Ozon, AliExpress, Wildberries и Яндекс Маркета.

7. **Интеграция с Windows.** Проверить трей, открытие окна из трея, закрытие окна
   с продолжением фоновой работы, полный выход, single-instance-поведение,
   автозапуск и запуск с `--background`. Проверить используемые native-плагины,
   диалоги импорта/экспорта и внешний браузер. Сохранить понятное сообщение при
   ошибке служб и возможность повторного запуска без повреждения данных.

8. **EXE-установщик.** Включить Tauri NSIS для Windows и упаковать все runtime-
   ресурсы. Определить пользовательскую установку, ярлыки, идентификатор приложения
   и правила удаления. Обработать наличие/установку WebView2; явно определить,
   какие сетевые загрузки нужны установщику и поддерживается ли офлайн-установка.
   Удаление программы должно сохранять пользовательские данные по умолчанию;
   их удаление допускается только отдельным явным действием пользователя.

9. **Обновление через новый установщик — первый выпуск.** Обнаруживать работающее
   приложение, корректно останавливать сбор и службы до замены файлов, сохранять
   данные и профиль. Перед изменением схемы создавать проверяемую резервную
   копию; применять миграции с понятным состоянием ошибки, без запуска worker
   на неподготовленной схеме. Разделить обновление приложения/схемы и смену major
   PostgreSQL: последняя требует отдельной процедуры переноса кластера, а не
   замены бинарников поверх старых данных. Описать восстановление из копии после
   сбоя без сохранения старой реализации как совместимого режима работы.

10. **Автообновление — следующий этап.** После устойчивого обновления установщиком
    добавить проверку новой версии и установку из приложения через Tauri Updater.
    Определить публикацию релизов/манифеста, HTTPS, подписи пакетов, хранение
    закрытого ключа и действия при ошибке загрузки или проверки подписи.
    Отдельно оценить подпись Windows-установщика и исполняемых файлов: она
    отличается от подписи пакетов Tauri Updater. Не включать секреты в репозиторий.

11. **Сборка и выпуск.** Подготовить Windows-скрипт и CI job на Windows runner
    с закреплёнными версиями Node, Rust, Python и runtime-зависимостей. Адаптировать
    npm-команды и конфигурацию упаковки, сохранив Linux-процесс. Выпускать версионированный
    установщик, контрольные суммы и сведения о составе. Проверить происхождение,
    лицензии и условия распространения поставляемых PostgreSQL, Python, браузера
    и библиотек. Точный набор сборочных инструментов закрепить в инструкции.

12. **Проверки и документация.** Добавить релевантные автоматические проверки
    Windows-путей, конфигурации, запуска/остановки и восстановления служб.
    Интеграционные проверки выполнять только на одноразовой БД и временном профиле.
    Отдельно проверить queued-сбор desktop/API/worker, `main.py collect` и numeric
    Ozon JSON mode без `DATABASE_URL`, включая доступность обоих CLI-импортов.
    Проверить импорт/экспорт и отсутствие дубликатов истории. Обновить руководства
    по установке, данным, выпуску, обновлению и диагностике. Native-сборки и ручная
    проверка приложения остаются за пользователем, если он отдельно не поручил
    их агенту; demo E2E не подтверждает работу настоящих служб Windows.

**Предлагаемый порядок:**

- Сначала подтвердить жизнеспособность браузерного сбора на Windows на отдельном
  тестовом профиле, зафиксировать режим Chrome и ограничения.
- Затем перенести runtime, подготовить поставляемые Python/PostgreSQL и проверить
  полный локальный цикл на одноразовых данных.
- Собрать установщик и проверить установку/обновление с сохранением данных.
- После первого устойчивого выпуска добавить автообновление из приложения.

**Критерии готовности первого выпуска:**

- На чистой поддерживаемой Windows установка не требует заранее установленных
  Python/PostgreSQL и ручной настройки окружения; политика Chrome и WebView2 явна.
- Приложение создаёт свою БД, запускает API/worker, собирает товары и сохраняет
  историю; повторный запуск использует те же данные и авторизованный профиль.
- Проверены пути с пробелами/кириллицей, занятые порты, повторный запуск,
  падение/восстановление служб, фоновый режим и завершение без оставшихся процессов.
- Обновление с предыдущей тестовой версии сохраняет карточки, группы, историю,
  настройки и профиль; сбой миграции не приводит к потере данных.
- Удаление и повторная установка сохраняют данные по умолчанию. Linux-проверки
  затронутых путей проходят; ограничения живого сбора и непроведённые проверки
  перечислены явно. Автообновление не является условием готовности первого выпуска.

Источники текущих ограничений: `frontend/src-tauri/src/native_services.rs`,

`frontend/package.json`, `marketplace_connector/browser/session.py`,
`packaging/make-linux-release.sh`, `packaging/aur/PKGBUILD`.
