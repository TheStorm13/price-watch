# Визуальное оформление групп — исследование

- Исходный запрос: изучить неудобное оформление групп, съехавшие теги и лишнее время обновления; показать пару вариантов. Последующее одобрение реализации записано ниже.
- Текущая стадия: дизайн одобрен, реализация в каталоге проверена; ожидается приёмка приложения после коммита.
- Исследованы CatalogGroup, CatalogProduct, CatalogResults, TagList и соответствующие стили global.css. CodeGraph вернул актуальные исходники без предупреждений о свежести. Repowise get_why не нашёл решений для CatalogGroup; индекс старше текущего дерева (10 дней), исторические выводы не использованы. Для исследования без изменения кода обновление индекса не запускалось.
- Найдено: группа отличается преимущественно фоном, без явного обозначения типа; название/счётчик/теги не имеют устойчивого общего layout. Табличная группа выводит время, обычная товарная строка — нет. В плитке время есть и у обычных товаров.
- Сейчас TagList группы получает representativeCard.tags; собственные group.tags существуют отдельно. Предыдущая задача compute-group-card-metrics закрепила использование товарных полей представителя. Источник тегов в рамках визуального исправления не менять автоматически.
- Варианты: docs/design/group-card-variants.html. «Строка-папка» сохраняет выравнивание метрик по колонкам, добавляет подпись «Группа», иконку папки, фон и вложенность. «Секция» выносит название/теги/метрики в самостоятельный заголовок с вложенной таблицей. Данные иллюстративные; картинки обозначены нейтральными иконками. Макеты сосредоточены на списке; перенос выбранной идеи в плитку требует отдельной проверки.
- Рекомендация: «Строка-папка». Сохраняет сравнение цен, сортировку колонок и существующую плоскую виртуализацию. «Секция» заметнее, но занимает больше места и требует более существенного пересмотра табличной структуры/виртуализации.
- Предлагаемый план после выбора: выделить идентичность группы (иконка, подпись, имя, счётчик); отдельная строка тегов с ограничением ширины и раскрытием полного текста; удалить время группы; сохранить все метрики, фильтры, сортировку, редактирование и раскрытие. Проверить список и плитку, длинные названия/теги, пустую группу, нет цены, hasMemberDeals и dealsEnabled, раскрытое/свёрнутое состояние, клавиатуру, светлую/тёмную тему и измерения виртуальных строк. Данные/API/БД не меняются.
- Проверки реализации: применимые unit и mock E2E групп, TypeScript lint и desktop frontend build, визуальная проверка 1024/1536 px. Для секционного варианта до реализации оформить OpenSpec из-за изменения структуры отображения; для локального варианта оценить необходимость по итоговому согласованному объёму.
- Следующее действие: явный выбор и одобрение плана пользователем. До этого application code не менять согласно vibe-flow, этап 1.
- Проверка макетов: автономный preview от visualize/render.py, Playwright Chromium; раскрытие/сворачивание обоих вариантов и заглушка редактирования работают, pageerror отсутствуют. Осмотрены изображения 780 и 360 px. В узком окне таблица прокручивается внутри контейнера. Browser plugin отсутствует, использован установленный Playwright. Приложение и его тесты не запускались, production-код не менялся.

## Доработка выбранного направления

- Пользователю понравилась «Строка-папка», но раскрытый состав сливается с последующими самостоятельными карточками. Запрос — доработать макет; разрешения на реализацию приложения пока нет.
- У «Строки-папки» теперь непрерывный синий левый маркер от заголовка до последнего участника, слабая общая подложка участников, замыкающая нижняя линия и промежуток 12 px перед следующим товаром. При сворачивании линия замыкает сам заголовок; отступ сохраняется. Табличные колонки и исходный дизайн заголовка сохранены.
- Прежний вариант «Секция» оставлен для сравнения. Существующий standalone preview /tmp/group-card-variants-preview.html обновляется по прежнему пути.
- Проверено после доработки: Playwright Chromium без pageerror; раскрытие/сворачивание работают, на 360 px нет переполнения корневого контейнера. Осмотрены снимки раскрытой/свёрнутой группы и тёмной темы при 780 px. git diff --check пройден. Приложение не менялось.

## Скругление и спокойная граница

- По следующему уточнению пользователя убрана синяя нижняя линия: граница снизу теперь нейтральная, толщиной 1 px. Синий акцент остаётся только слева.
- Единый радиус 10 px у внешних углов группы и самостоятельной карточки. У раскрытой группы скругляются верх заголовка и низ последнего участника; у свёрнутой — все внешние углы заголовка. Внутренние строки остаются соединёнными. Подложка и поля вокруг таблицы позволяют видеть скругления; отступ 12 px между сущностями сохранён.
- Меняется только выбранный макет «Строка-папка», приложение не меняется. Preview обновляется по прежнему абсолютному пути.
- Проверки ревизии: Playwright Chromium подтвердил радиусы 10 px у раскрытого низа группы, свёрнутого заголовка и самостоятельной карточки; нижняя граница 1 px с нейтральным цветом. Раскрытие/сворачивание работают, pageerror отсутствуют, на 360 px нет переполнения корня. Осмотрены снимки светлой раскрытой/свёрнутой группы и тёмной раскрытой группы при 780 px. git diff --check пройден.

## Одобренная реализация

- Пользователь явно одобрил перенос дизайна в проект, уточнив: уменьшить отступ и сделать его одинаковым между всеми самостоятельными карточками и группами. Принят отступ 8 px, радиус 10 px. Внутренние товары группы соединены. Второй review gate — после реализации и коммита.
- Локальная правка представления каталога: CatalogGroup, CatalogProduct, CatalogResults, global.css. API, доменная семантика, формат тегов, БД и сбор не меняются. OpenSpec/ADR не нужны: существующая плоская таблица и виртуализация сохраняются, новая архитектура не вводится.
- Границы группы определяются по полному массиву визуальных строк, а не по DOM/видимой части. Межблочный интервал включён в высоту измеряемой строки таблицы. Список и сетка сохраняют один порядок и все метрики. Время удаляется только у группы; обычные плитки сохраняют своё время.
- Применены проектные shadcn и react-best-practices; Browser plugin not available, UI проверяется установленным Playwright. Repowise get_risk сообщил индекс возрастом 10 дней; запущено обновление index-only без LLM/генерации AGENTS.
- Обновление Repowise не завершилось подтверждённо и остановлено; сгенерированные им посторонние .mcp/.vscode/.github конфигурации удалены. Индекс не считается свежим. get_change_risk использовал live_git: прежняя critical-сложность CatalogResults и длина нового E2E callback рассмотрены вручную; ошибка поведения из этих метрик не следует. CSS не поддерживается анализатором, diff проверен вручную. Сведения о старом изменении package-lock относятся к отставанию индекса, в этой задаче зависимости не менялись.
- Проверка на demo: /cards → выбор двух карточек → создание группы → сворачивание/раскрытие → сетка; название страницы/непустой контент/отсутствие vite-overlay подтверждены, pageerror и console.error отсутствуют. Осмотрены /tmp/price-watch-groups-list.png, /tmp/price-watch-groups-collapsed.png, /tmp/price-watch-groups-grid.png и /tmp/price-watch-groups-grid-1024.png при 1536/1024 px. Проверены собственный диалог группы, цены и статусы представителя.
- Первый полный E2E: 59/62 прошли, три падения из-за прежнего ожидания «3 товаров» и формулы колонок с интервалом 12 px. Ожидания обновлены по новой подписи/интервалу. Дополнительно большой групповой E2E проверяет реальный интервал 8 px между рядами плиток. Новый E2E покрывает длинные теги/название, пустую группу, отсутствие времени, границы и раскрытие клавиатурой.
- Финальные unit: 88/88; build:desktop (TypeScript + Vite) прошёл. Native Tauri/WebView, API/worker/БД не менялись и отдельно не запускались; demo не проверяет живые службы.
- Финальный полный E2E: 62/62 passed (3.2 min), output /tmp/price-watch-group-design-final-e2e. Включены три формы каталога по 5000 товаров, реальный интервал между рядами группы, клавиатура, pinned action owner, восстановление позиции, фильтры и цены. Финальные npm run lint, npm test, npm run build:desktop и git diff --check прошли. Предупреждение React Router HydrateFallback встречается в существующих сценариях, ошибок pageerror/console.error в целевой визуальной проверке нет.
- Следующее действие: оценка и явная приёмка пользователем реализованного приложения (второй gate vibe-flow). После приёмки обновить соответствующее описание каталога в docs/UI_SPECIFICATION.md и этот статус отдельным коммитом. OpenSpec не создавался, синхронизация/архивирование не требуются.
