- Дата начала: 2026-10-22.
- Область: REL-01–REL-05 из `docs/BACKLOG.md`.
- Workflow: `vibe-flow`; один исполнитель.
- Фаза: принятая реализация завершена; Gate 1 и Gate 2 пройдены.
- Одобрение реализации: пользователь ответил «да» на полный план и пороги производительности 2026-10-22.
- Приёмка реализации: пользователь ответил «Хорошо» 2026-10-22 после итогового отчёта.
- OpenSpec change: `openspec/changes/archive/2026-10-22-harden-collection-reliability/`.

## Подтверждённый контекст

- CLI создаёт `running` без владельца; восстановление worker отбирает только
  запуски с владельцем. Аварийная CLI-запись может блокировать расписание.
- Повтор выбирает карточки из индивидуальных ошибок; необработанные цели после
  аварии не представлены. Успех без изменения цены не создаёт историю,
  поэтому историю нельзя использовать как полный журнал результатов сбора.
- Heartbeat проверяет владельца, но сохранение наблюдения, прогресса и
  завершения не защищено от исполнителя, потерявшего владение.
- UI фиксирует ID уведомлённого запуска до успешной загрузки deals. Закрытие
  панели через две секунды также нужно учесть при организации повторов.
- CardsPage независимо загружает cards, groups и deals. Внутри list_groups
  уже используется REPEATABLE READ; /cards читает карточки и метрики отдельно.
- Кнопка повтора в ActiveCollectionPanel показывается только при ошибке
  с cardId. Для аварии до первой карточки недостаточно исправить backend.
- Основные specs scheduled-collection, desktop-background-lifecycle и
  group-card-metrics прочитаны. Шестичасовой отсчёт, сохранение истории,
  выбор представителя группы и восстановление служб должны сохраниться.
- Repowise соответствует текущему HEAD; архитектурного решения о точном
  учёте результатов целей в нём нет. Предыдущие выводы сверены с текущим кодом.

## Решения пользователя

- 2026-10-22: пользователь выбрал единый снимок каталога и потребовал избежать
  существенного падения производительности. Это выбор направления REL-05,
  не одобрение полного плана реализации.
- 2026-10-22: по прямому запросу пользователя в AGENTS.md добавлено правило
  полного перехода без обратной совместимости: переводить потребителей и
  удалять заменённые решения. Защита пользовательских данных сохраняется.

## Предлагаемое направление, весь план ещё не одобрен

1. Общий механизм владения запуском и heartbeat для worker и прямого CLI;
   фиксировать состав целей до выполнения и восстанавливать устаревшие записи.
2. Отдельные результаты целей pending/succeeded/failed и unknown для
   недоказуемых исторических результатов. Сохранять успешное
   наблюдение, результат цели и счётчики атомарно, включая успех без новой
   точки истории. Повторять failed и pending; успешные цели не повторять.
3. Проверять владельца и активное состояние при каждой записи исполнителя;
   после потери владения отменять оставшиеся задачи и закрывать сеанс.
4. Независимая от видимости панели обработка уведомлений с повтором запроса;
   отмечать обработанный запуск только после успешного получения и обработки
   данных. Сохранять существующее правило отбора выгодных цен.
5. REL-05: GET /api/catalog с cards/groups/deals в одном снимке БД и единым
   обновлением кеша UI. Все потребители переводятся, заменённые GET списков
   cards/groups/deals, старые hooks/mock и дублирующие проекции удаляются.
   Нужен baseline до изменений и after на том же стенде. Предлагаемый порог
   Gate 1: p95 не выше max(1.20 × baseline, baseline + 50 мс), bounded SQL
   без N+1; отдельно контролируются RSS и write-throughput.

## Риски и переход

- Подготовлен Proposed ADR 0004. Нужна forward-only миграция с переносом
  целей в таблицу результатов и удалением заменённого массива. Не менять price_history и не
  восстанавливать недоказанные успехи старых запусков по отсутствию ошибки.
- Для старых запусков отдельно определить достоверный состав повтора;
  не расширять исторический запуск сегодняшним составом каталога.
- Проверить queued desktop/API/worker, прямой main.py collect, интерактивную
  проверку, оба CLI-импорта и numeric JSON mode без DATABASE_URL.
- Сохранить существующий запрет удаления целей активного запуска и импорта
  во время сбора, единственный повтор источника и правила deals_enabled.
- PostgreSQL-проверки проводить только на отдельной одноразовой
  TEST_DATABASE_URL; старые процессы остановить перед обновлением схемы.
- Производительность, разбиение RuntimeState и фабрика коннекторов остаются
  отдельными блоками backlog.

## Реализация и проверка

- Реализованы REL-01–REL-05: общий RunExecutor, lease на всех записях, атомарный журнал целей и полный retry, persistent очередь уведомлений, единый согласованный каталог. Заменённые runtime-пути удалены.
- Исправлена обнаруженная E2E гонка быстрого изменения URL-фильтров; fixtures переведены на новый каталог и хранилище уведомлений.
- Python: 104/104 в полном наборе; затем 17/17 в затронутых наборах после двух дополнительных проверок waiting/terminal challenge. Frontend: 54 unit и 38 E2E. Rust: 8 passed/3 ignored; desktop release build прошёл.
- Live native smoke на временных данных с fake connector прошёл: отказ до первой цели → кнопка повтора → цена в WebView → автоматическое восстановление API и каталога.
- Все пороги baseline/after пройдены. HTTP p95 быстрее на 23–45%, SQL 9→3. Запись на M/L медленнее на 18.4%/16.8%, в пределах одобренных 20%; RSS в пределах порога.
- Подробный review, команды, таблица замеров и снимки: [verification](harden-collection-reliability/verification.md). Затронутые guides и architecture overview обновлены, ADR 0004 принят, REL-блок отмечен выполненным.
- Gate 2 пройден. Спецификации синхронизированы; после проверки 23/23 change архивирован штатным CLI в 2026-10-22-harden-collection-reliability. Все изменения принятой реализации сохраняются отдельным commit. Push/merge не разрешены.
- Исходный аудит всех трёх блоков сохранён отдельным commit bdbc318; реализация меняет статусы только REL-01–REL-05.
