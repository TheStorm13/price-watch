## Запрос

## Проверенные факты

- OzonConnector → AsyncOzonClient → OzonProductParser → OzonMapper получает один точный SKU из composer page/json/v2. Parser уже читает webAspects. Mapper отдаёт соседей, но оставляет только первый параметр повторного SKU.
- CollectionService обрабатывает pending-цели до исчерпания; RunRepository.save_result/_discover_variants расширяет варианты только WB/Ali, требует общий префикс артикула и ':'. CardsRepository, PostgreSQL transfer и другие валидаторы должны быть согласованно обновлены для Ozon.
- Текущая модель card_variants/primary_variant_id и UI уже предоставляют отдельные цены, истории, изображения, главный SKU и графики. Массовая группировка пользовательских карточек не требуется для начала поддержки Ozon.
- CodeGraph использован с явным projectPath и текущим on-disk source без предупреждений stale. Repowise MCP вернул индекс 9f3876d возрастом 10 дней. Локальные index-only working-tree update и узкий risk не завершились за время исследования и остановлены через SIGINT (exit 130). Актуальный Repowise risk не получен; перед реализацией нужно восстановить/завершить обновление. Это ограничение инструмента, а не свидетельство безопасности изменения.

## Предложенный план и критерии

Одна карточка с исходным SKU, обход подтверждённых связей вариантов через текущие цели сбора, полные параметры каждого точного ответа, независимые истории и существующий выбор главного. Предел 500, явная неполнота, точный retry, согласованная проверка владения в add/discovery/import. Старые данные сохраняются; при другом владельце SKU — конфликт с ID, без автоматического объединения. Numeric JSON сохраняет одиночный снимок; все варианты добавляются в сценарии отслеживания БД.

Критерии и тест-план: proposal/design/tasks и delta product-variants. Архитектурное решение — proposed ADR 0012. Требуется явное согласование этого плана перед кодом; после реализации — проверки и коммиты перед второй приёмкой.

## Реализация после согласования

Согласование плана/ADR: ответ «Да»; после прерывания пользователь подтвердил «Продолжи». Выполнены задачи 1–3 и live-проверка 4.2. Проверки реализации завершены; результат передаётся на приёмку после коммита. Приёмка ещё не получена.

- OzonMapper объединяет именованные аспекты одного SKU, проверяет точные ссылки и сообщает неизвестное продолжение через `variant_discovery_error`, сохраняя точную цену. Старый обход произвольных вложенных словарей для списка SKU заменён разбором `aspects[].variants[]`.
- RunRepository расширяет pending-цели Ozon до исчерпания связей; каждый SKU запрашивается один раз за обычный запуск. Подтверждённые параметры/фото не затираются неполными метаданными соседей. Предел 500 и конфликт владельца сообщаются как `VariantDiscoveryIncomplete`, сохраняя валидные цены. Retry остаётся точным и не расширяет состав; следующий обычный сбор обнаруживает новые связи.
- Add/discovery/import берут общий advisory lock перед run/card locks. Новой миграции нет: таблицы уже поддерживают варианты, в том числе сохранение прежних ID, главного и истории. Transfer v3 допускает разные Ozon SKU; preview/import отклоняет чужого владельца HTTP 409 без частичных изменений, включая конкурентные add/import и add/discovery.
- Форма принимает артикул или ссылку Ozon, поясняет автоматическое обнаружение, валидирует ссылку выбранного главного. CLI list различает исходный артикул и `primary_external_id`. Numeric JSON/raw выполняет один запрос без БД.

Дополнительная live-проверка структуры: `1306372289` — один аспект объёма, 2 SKU; `1604900984` — вес (4) и вкус (13); `1607687714`, `1641499399`, `1607686851` — четыре аспекта (состояние/комплект/мощность/температура). Во всех проверенных списках одинаковая структура без наблюдавшегося дополнительного продолжения. Универсальность на остальных категориях не доказана; неизвестные элементы управления не игнорируются.
