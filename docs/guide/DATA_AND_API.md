# Данные, очередь и API

[К содержанию](README.md)

## Таблицы PostgreSQL

| Таблица | Что хранит |
| --- | --- |
| `marketplace_cards` | Маркетплейс, внешний артикул, название, ссылку, изображение, теги, группу и флаг учёта в выгодных предложениях |
| `product_groups` | Название, теги и дату создания группы; участники ссылаются на неё из `marketplace_cards` |
| `collection_runs` | Очередь и результат запуска, владелец и heartbeat, полнота состава, связь с исходным запуском, счётчики, ошибки и состояние проверки |
| `collection_run_targets` | Фиксированные цели запуска с порядком и результатом pending/succeeded/failed/unknown |
| `price_history` | Наблюдения цены и наличия, время и снимок в `JSONB`; новый сбор пропускает неизменное состояние |

Пара `(marketplace, external_id)` уникальна. Удаление карточки удаляет и её
историю. Ссылки запуска на удалённую карточку обнуляются. Исключённая из выгодных предложений
карточка остаётся в базе и истории и участвует в новом сборе. Состав уже
созданного запуска не меняется. Удаление карточки из незавершённого запуска
возвращает `409`.

Миграции выполняются Alembic; цепочка ревизий в коде идёт от `0001_initial`
до `0017_bounded_diagnostics`. В неё входят, среди прочего, таблица групп, теги,
изображение, первоначальное 12-часовое расписание (текущий интервал задан кодом) и переход от `is_active` к
`deals_enabled`. Ревизия `0004_compact_price_plateaus` сокращает старые
повторы состояний в истории, сохраняя первую и последнюю точки каждого
участка. Удалённые ею наблюдения нельзя восстановить через `downgrade`.
Прежняя версия руководства также сообщала об отдельной ручной очистке рабочей
базы 27 сентября 2026 года; это сообщение нельзя подтвердить по репозиторию.
API применяет
миграции при старте; перед исполнением на существующей базе нужно изучить
конкретные ревизии и резервную копию.

`0017_bounded_diagnostics` сохраняет ограниченную диагностику только запуска с
максимальным ID и необратимо очищает подробности остальных. Карточки, история,
счётчики и результаты целей сохраняются. Перед обновлением нужно остановить
writers и завершить активные owned-запуски либо восстановить их старым worker:
миграция отказывается менять схему при owned `running`/`waiting_for_user`.
Откат схемы не восстанавливает удалённые диагностические подробности.

## Модели и денежный контракт

`MarketplaceCard` — общий результат получения товара из коннектора.
`TrackedCard` — локальная запись отслеживания, соответствующая существующей
таблице `marketplace_cards`; модели связаны парой marketplace/external_id.
Получение товара не перезаписывает группу, теги и настройки. Непустое локальное
название сохраняется; пустое заполняется из товара.

Все денежные поля API (`price`, `currentPrice`, `minimumPrice`, `maximumPrice`,
`averagePrice`, `savings`) и CLI передаются десятичными строками либо null.
Цена наблюдения содержит два знака, например `"199.90"`. В Python используется
Decimal, в истории — NUMERIC(14,2); округление цены ROUND_HALF_UP, допустимы
конечные неотрицательные значения меньше 10^12 после округления. Средние и
выгода не округляются до проверки выгодности; показ округляется до двух знаков.

Карточка показывает данные главного варианта: название, фото, ссылку, параметры,
цену, наличие и время сбора. Смена главного сразу переключает эти данные и
статистику без повторного сбора. Название и ссылка редактируются для выбранного
варианта; группа, теги и участие в выгодных общие для товара.
Каждый вариант хранит `productTitle` и `imageUrl`; коннекторный JSON вариантов
содержит `image_url`. Варианты без отдельного изображения могут использовать
общее фото источника. Недоступное изображение не мешает сбору цены.

Миграция `0019_variant_details` переносит прежние название и фото к главному
варианту, восстанавливает доступные данные соседей из их собственных snapshot,
затем удаляет заменённые колонки товара. История не переписывается. Перед
миграцией нужно завершить активный сбор. Неизвестные фото появятся при повторном
сборе. Экспорт v3 сохраняет фото и названия вариантов; существующие файлы без
этих полей импортируются с сохранением известных данных главного варианта.

Нормализованный товар имеет schema_version `2.0`; `--raw` выводит исходный
ответ без пересериализации. Импорт/экспорт документа v3 хранит товар, варианты, главный SKU и независимые
истории со строковыми ценами; числовая цена в импорте отклоняется. Варианты WB
имеют `nmId:optionId`, AliExpress — `productId:skuId`; записи до обнаружения
могут содержать только артикул. Их история сохраняется отдельно, точные SKU
находятся при сборе. [Переход AliExpress](ALIEXPRESS.md). Старые исторические
JSONB-снимки и пустые snapshots импорта не переписываются. Новая схема БД
для разделения моделей не требуется. API, worker, CLI и UI обновляются вместе;
старые Python-импорты и числовые денежные JSON-ответы больше не поддерживаются.

## Статусы запуска

| Статус | Значение |
| --- | --- |
| `queued` | Запрос записан, worker ещё его не взял |
| `running` | Исполнитель CLI или worker обрабатывает карточки |
| `waiting_for_user` | Площадка требует проверки в видимом Chrome |
| `completed` | Все карточки обработаны без ошибок |
| `completed_with_errors` | Хотя бы одна карточка не обработана |
| `failed` | Выполнить сам запуск не удалось |

Работа через UI использует очередь БД. Прямой `main.py collect` создаёт запуск
сразу в состоянии `running` и не ждёт worker. Ошибки отдельных карточек
учитываются точно в `failure_count` и результатах целей. Поле `errors` — временная
выборка только последнего созданного запуска (максимальный ID), независимо от
его статуса: до 20 примеров и 128 KiB JSON суммарно. Сообщение ограничено 1024
байтами UTF-8, traceback — 4096, пример — 6000 байт JSON. Общая ошибка остановки
сохраняется внутри того же лимита, при необходимости заменяя последний пример.
Создание нового запуска, включая queued/retry, атомарно очищает подробности всех
предыдущих, даже активных. Поздние результаты старого запуска не возвращают их.

`diagnosticsStatus` описывает выборку, а не состояние выполнения запуска:

| Значение | Значение для диагностики |
| --- | --- |
| `complete` | Пока нет пропущенных или сокращённых примеров |
| `limited` | Примеры или технический текст сокращены |
| `expired` | Подробности очищены после создания следующего запуска |

`GET /api/runs/{id}` по умолчанию возвращает сохранённую выборку;
`includeErrors=false` и список запусков не выбирают payload из БД.
Очистка и лимиты не меняют счётчики и состав повторного сбора.
Результаты целей сохраняются в `collection_run_targets`, включая успех без новой точки истории. Worker проверяет необходимость автоматического сбора раз в минуту:
если с начала последнего полного запуска прошло не менее 6 часов, нет незавершённого
запуска и
есть поддерживаемые карточки, он создаёт полный запуск. При отсутствии предыдущего
полного запуска сбор создаётся сразу; после долгого простоя создаётся только один
просроченный запуск. Общий `RunExecutor` CLI и worker обновляет heartbeat
каждые пять секунд, в том числе в ожидании пользователя. Worker восстанавливает
устаревшие запуски до проверки расписания, direct collect — до собственного старта.
Порог `RUN_STALE_SECONDS` по умолчанию 30 секунд, минимум 15. Восстановление
проверяет последнюю активность независимо от наличия владельца; уже сохранённая
история остаётся. Старый владелец больше не может менять данные запуска.

Повтор доступен для `failed`/`completed_with_errors` и создаётся один раз для
каждого источника. Успешные цели исключаются, удалённые карточки не возвращаются.
API сообщает `retryableCount` и `retryScopeIncomplete`: при неполных старых
данных UI предупреждает о повторе только известных карточек. После создания
повтора источник сообщает нулевой `retryableCount`. Повтор не переносит срок
полного сбора.

Ревизия 0014 переносит все известные цели из прежнего массива, requested ID,
ошибок и истории, затем удаляет `target_card_ids`. Недоказанные результаты
помечаются `unknown`; неполный состав не дополняется текущим каталогом.
Существующие карточки и история сохраняются; подробности ошибок подчиняются политике последнего запуска. Идентичность цели после
удаления карточки остаётся; удаление запуска удаляет его цели каскадно.
Переход forward-only: остановить старые процессы перед upgrade, использовать
только новую версию. Возврат прежней модели через downgrade не поддерживается.

Каталог читается в одной read-only транзакции `REPEATABLE READ`; cards, groups
и deals строятся из общих исходных данных. `PostgresCatalogReader` материализует
эти данные, а `CatalogService` применяет чистые правила выгодности и представителя
после закрытия транзакции. SQL-агрегации и денежные значения сохраняются;
дополнительного чтения для отдельных проекций нет. UI заменяет снимок целиком после
мутаций, импорта, завершения сбора и восстановления API. При ошибке refetch
сохраняется предыдущий целый снимок. Заменённые GET списков `/api/cards`,
`/api/groups`, `/api/cards/deals` удалены; отдельные мутации, details/history/chart
и import/export сохранены.

## История и статистика

«Текущая» цена и доступность на карточке берутся из самого нового по времени
наблюдения. История возвращается с новейшего наблюдения и ограничена периодом.
API истории принимает `days` только `7`, `30` или `90`, а `pageSize` — от 1 до
200. CLI `history` использует положительное число дней без этого ограничения.

Средняя цена (`averagePrice`) вычисляется по времени:
`Σ(цена × длительность) / Σдлительностей`. Каталог и статистика используют
последние два календарных года до момента расчёта в UTC; для 29 февраля начало
окна в невисокосном году — 28 февраля. Если история короче, учитывается только
известная часть. `minimumPrice` и `maximumPrice` относятся к тому же окну.
История старше двух лет не удаляется.

Состояние действует от сохранённой точки до следующего изменения, последнее —
до момента расчёта. Берётся также последняя точка перед началом окна, но её
длительность обрезается границей окна. Это модель последней известной цены:
перерыв в проверках не ограничивает её длительность. Интервалы `out_of_stock`,
`unknown` или неизвестной цены исключаются из числителя и знаменателя, прерывая
предыдущую доступную цену. Нулевая цена допустима. Будущие точки не участвуют.
При одинаковом времени состояние с большим ID действует дальше; предыдущие
точки имеют нулевую длительность.

Без положительной длительности валидной цены средняя — null. Одна валидная цена
с положительной длительностью даёт среднюю, равную ей. Новая текущая точка ещё
не имеет временного веса, но участвует в минимуме и максимуме. В экстремумы
входит и состояние, начавшееся до окна, если оно действовало внутри окна.
Повторные одинаковые точки не меняют среднюю. Расчёт выполняется через
NUMERIC/BigInt без float для денег; средняя округляется до 12 знаков после
запятой, половины — от нуля. Отображение рублей округляется отдельно.

В API истории поле `statistics` всегда относится к двум годам и содержит
`windowStart`/`windowEnd` вместо `days`. Параметр запроса `days` управляет только
`history`, `totalCount` и пагинацией; график имеет собственный период. CLI
`history --days N` также ограничивает только строки истории, а его statistics
содержит двухлетние границы `window_start`/`window_end`.

Верхний блок открытой карточки показывает минимум, максимум, середину диапазона
`(minimumPrice + maximumPrice) / 2` и разницу `maximumPrice - minimumPrice` за два
года по главному варианту. «Середина диапазона» — отдельный показатель, не новая
средняя по времени. Переключатель 7/30/90 дней меняет только график и таблицу
измерений; верхний блок от него не зависит.

В каталоге средняя и минимум также относятся к двум годам основного варианта.
`baselineDays` и `observedDays` считают дни UTC с сохранёнными валидными точками
в окне; `observationsCount` — число таких точек. Унаследованная точка до окна
в эти счётчики не входит. Это не длительность наблюдений и не число успешных
проверок; нулевой счётчик не отменяет среднюю унаследованной цены.
Интерфейс показывает положительную разницу между средней и текущей ценой
товара в наличии, в том числе при отключённом участии в выгодных предложениях.
Флаг участия управляет отбором и приоритетом выгодных предложений; сортировка
по выгоде использует отображаемую сумму.

В таблице столбец называется «Выгода / Максимальная выгода». Под текущей
выгодой меньшим шрифтом показана максимальная: `averagePrice − minimumPrice`.
Она отображается и при «Сейчас не выгодно»: нулевая разница — `0 ₽`,
отсутствие средней или минимума — `—`. Для строки группы используются средняя
и исторический минимум её представителя.

Группа берёт все товарные показатели у одной карточки с минимальной известной
текущей ценой: исторический минимум, среднюю, выгоду, наличие, даты,
маркетплейс и товарные теги. Наличие не ограничивает выбор; используется цена
последнего сохранённого состояния. При равных ценах выбирается меньший ID.
Если цен нет, выбирается участник с меньшим ID; пустая группа не имеет
представителя. Поля без данных остаются `null`. Исторический минимум группы
относится именно к выбранной карточке, а не к историям всех участников.

Фильтры и сортировка применяются к группам и отдельным карточкам одинаково,
после выбора представителя. Фильтр не подбирает другого участника; раскрытая
группа показывает весь состав. Поиск также учитывает собственное имя группы.
Её ID, имя, состав и редактируемые теги сохраняются как собственные данные;
товарный фильтр тегов использует теги представителя.

Выгодность и численная выгода группы совпадают с представителем. Выгодный
вложенный товар дополнительно повышает приоритет группы, но не меняет её
показатели и прохождение фильтра «Выгодные предложения». Список и плитка
используют один порядок: сначала выгодные объекты, затем выбранное поле;
отсутствующие значения внутри одного приоритета идут в конце при обоих
направлениях сортировки.

Ответы API групп содержат `representativeCardId`, обычную проекцию
`representativeCard`, `savings`, `baselineDays`, `isDeal` и `hasMemberDeals`.
Поле `savings` API относится к отобранному выгодному предложению и остаётся
`null` при отключённом участии представителя; отображаемую выгоду для такого
товара интерфейс вычисляет из его средней и текущей цен.
Поля `currentPrice` и `minimumPrice` верхнего уровня совпадают с представителем.
У пустой группы представитель и цены равны `null`, число дней базы — 0,
признаки выгодности — `false`. Даты группы принадлежат представителю;
обновление другого участника не освежает их, пока он не стал представителем.

При сохранении наблюдения цена и наличие сравниваются с последним
сохранённым состоянием карточки. Если оба значения совпадают, новая точка
не добавляется; пустое название заполняется с площадки, а ссылка обновляется,
если площадка её вернула. При статусе
`out_of_stock` цена равна `null`, даже если в ответе магазина осталась прежняя
цена. Переходы «в наличии → нет в наличии → в наличии» сохраняются в истории.
Поле `updatedAt` обновляется при каждом успешном сборе. Интерфейс показывает
его в колонке «Обновлено» и в деталях карточки; `lastObservedAt` остаётся
временем последней сохранённой точки истории. Для карточки без измерений дата
обновления в интерфейсе не показывается.
Обычный сбор не пересматривает уже записанную историю. График получает сохранённые точки через
отдельный маршрут; вертикальная ось имеет отступ 10% от диапазона видимых цен,
не опускаясь ниже нуля. Таблица измерений
остаётся постраничной, по 50 строк. Счётчики статистики отражают сохранённые
валидные точки за два года, а число успешных запусков сохраняет число
фактических успешных запросов.

Выгодное предложение появляется для карточки, участвующей в отборе, когда
последняя цена товара в наличии ниже средней по времени за два года основного
варианта. Возраст карточки и число дней с точками не являются дополнительными
порогами; без рассчитанной средней предложение не появляется. Одна постоянная
цена сама по себе не создаёт выгоду. При снижении 100 → 80 в момент новой точки
база ещё равна 100 и выгода равна 20; по мере действия новой цены база меняется.
Список вычисляется при запросе, поэтому его значения могут меняться со временем
даже без новых точек истории.

## Экспорт и импорт

«Экспорт» на странице карточек выгружает один JSON-файл версии 2 со всеми
карточками, группами и всей сохранённой историей. У карточки сохраняются `marketplace`,
`externalId`, `title`, `url`, `imageUrl`, `tags`, `dealsEnabled`, `createdAt` и `history`. Каждая запись
истории содержит только `price`, `availability` и `observedAt`. Внутренние ID,
запуски сбора и снимки ответа маркетплейса не экспортируются.
Экспорт читает карточки, историю и состав групп из одного снимка REPEATABLE READ;
в SQL выбираются только экспортируемые поля истории, без `snapshot`.

«Импорт» сначала рассчитывает результат без записи. Карточки сопоставляются по
маркетплейсу и артикулу; у совпавших карточек название, ссылка и состояние показа в выгодных предложениях
остаются местными. Наблюдения объединяются по времени, совпадающие по времени
и цене не повторяются, а подряд идущие одинаковые числовые цены сворачиваются
в первую точку серии. Пустая цена обозначает отдельное состояние доступности.
Разные цены с одинаковым временем для одной карточки вызывают ошибку; весь
импорт выполняется одной транзакцией. Пока сбор не завершён, импорт недоступен.
Импорт принимает только файлы версии 2 с полем `dealsEnabled`.

## HTTP API

Все маршруты имеют префикс `/api`. Поля JSON используют `camelCase`:
`externalId`, `currentPrice`, `cardId`, `pageSize` и так далее. При прямом запуске
API с портом по умолчанию интерактивная схема находится на
`http://127.0.0.1:8000/docs`. В desktop порт выбирается при запуске.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/health` | Готовность API |
| `GET /api/catalog` | Единый снимок `{cards, groups, deals}` с ценами, метриками и представителями групп |
| `GET /api/cards/export` | Все карточки и вся сохранённая история в JSON |
| `POST /api/cards/import/preview` | Проверить файл и рассчитать результат без записи |
| `POST /api/cards/import` | Объединить карточки и историю |
| `POST /api/cards` | Добавить карточку и запустить начальный сбор вариантов и цен |
| `GET /api/cards/{id}/thumbnail?profile=list&scale=1[&variantId=N]` | Подготовленный PNG главного фото или конкретного SKU |
| `GET /api/cards/{id}` | Одна карточка с последним наблюдением |
| `PATCH /api/cards/{id}` | Изменить название, ссылку, группу, теги или учёт в выгодных предложениях |
| `DELETE /api/cards/{id}` | Удалить карточку и её историю |
| `GET /api/cards/{id}/history` | История и статистика |
| `GET /api/cards/{id}/chart?days=30` | Сохранённые изменения цены за период |
| `POST /api/groups` | Создать группу |
| `PUT /api/groups/{id}` | Изменить группу |
| `DELETE /api/groups/{id}` | Удалить группу, сохранив карточки |
| `GET /api/runs` | Список запусков |
| `POST /api/runs` | Поставить сбор в очередь; `{}` — все карточки, `{"cardId": 1}` — одна |
| `GET /api/runs/{id}` | Статус, счётчики, текущая карточка, diagnosticsStatus и выборка ошибок; includeErrors=false исключает payload |
| `POST /api/runs/{id}/continue` | Продолжить после проверки площадки |
| `POST /api/runs/{id}/retry` | Повторить существующие поддерживаемые цели failed/pending/unknown |

Миниатюра требует тот же `X-Price-Watch-Token`, что остальные desktop-запросы.
Ответ — `image/png`, `Cache-Control: no-store`; браузерный кэш заменён
кэшем Blob в query client и дисковым кэшем API. `404 card_not_found` — нет
карточки, `404 image_not_found` — нет фото, `502 thumbnail_unavailable` —
источник, формат, лимиты или запись кэша недоступны. Ошибка даёт заглушку
во всех представлениях. URL выбирается сервером по главному варианту либо
`variantId`; чужой или отсутствующий SKU даёт `404 variant_not_found`, SKU без
фото — `404 image_not_found`. Произвольный URL не принимается. `imageUrl`
продолжает обозначать исходник в БД и экспорте.

Обязательные параметры: `profile=list|tile|detail`, `scale` (DPR, 0.25..8), иначе
422. Размер PNG — округлённый CSS-размер × scale, коэффициент качества ×1:
list/SKU 51×68; tile 276×368; detail 384×512. Все рамки и подготовленные
изображения портретные 3:4, включая заглушки. Плитка фиксирована 280×654 CSS px; при изменении окна меняется число колонок.
Pillow 13 декодирует оригинал полностью, вписывает Lanczos без увеличения и
кадрирования, центрирует по целым пикселям на прозрачном RGBA-поле нужной формы.
PNG без потерь занимает всю область; WebView не уменьшает отдельно узкое фото.
Максимальная сторона подготовленного PNG — 4096 px (detail при DPR 8).
При дробном DPR округление ограничивает точность соответствия физическим пикселям.
Общий исходник и ленивые производные хранятся в ограниченном дисковом кэше,
а не в PostgreSQL. Смена профиля не требует новой загрузки сохранённого исходника.

Создание запуска возвращает HTTP `202`, создание карточки — `201`, удаление —
`204`. Если карточек нет, `POST /api/runs` возвращает `409`.
Ошибки API имеют структурированный объект `error` с кодом и сообщением.
Публичное создание карточки принимает `marketplace = "ozon"`, `"wildberries"`,
`"aliexpress"` или `"yandex-market"`. Для AliExpress достаточно строкового productId,
для Wildberries — nmId; URL, если указан, должен соответствовать товару.
Первый сбор находит все SKU и добавляет точные варианты в тот же запуск.
Внутренние варианты используют `productId:skuId` и `nmId:optionId`. Для остальных
площадок нужен цифровой артикул. Ozon принимает SKU любого варианта: связанные
артикулы добавляются в одну карточку при первоначальном обновлении, исходный артикул остаётся
стабильным. У каждого SKU свои параметры, фото и история. Экспорт v3 сохраняет
разные артикулы внутри Ozon-карточки; конфликт владельца при импорте/preview
возвращает 409 `variant_ownership_conflict` без автоматического объединения.
Полный обход и ограничения: [Ozon](OZON.md).
Сбор доступен для Ozon, AliExpress, WB и Яндекс Маркета. Старые наблюдения без SKU не
переносятся в историю произвольно выбранного варианта.
Миграция WB и единственная цена: [Wildberries](WILDBERRIES.md).

API не содержит учётных записей. Desktop запускает его на свободном порту
`127.0.0.1` и передаёт интерфейсу секрет для запросов.


### Отслеживание вариантов

Создание Ozon/WB/AliExpress через API или CLI атомарно ставит первоначальный
сбор всех вариантов и начальных цен в очередь worker. Desktop подготавливает
сбор перед созданием. Сетевые запросы выполняются фоном; ошибки и проверка Chrome
отображаются в обычном прогрессе запуска.

`PATCH /api/cards/{id}/variant-tracking`: `{ "enabled": true, "variantId": 42 }`
меняет отдельный дополнительный вариант; без `variantId` — все известные
дополнительные варианты. Главный нельзя переключать: он всегда собирается.
`VariantResponse.trackingEnabled` — сохранённое предпочтение, `isTracked` —
предпочтение или статус главного. Массовые действия пропускают главный и не
включают будущие варианты. Обычный сбор фиксирует главный и включённые цели
при создании запуска; последующие изменения не меняют уже поставленный запуск.

Миграция `0020_variant_tracking` устанавливает false всем прежним предпочтениям,
сохраняя ID, главный, метаданные, историю и уже поставленные цели. Выключение
сохраняет данные. Transfer v3 экспортирует `trackingEnabled`; для новых
импортированных вариантов отсутствие поля означает false, а при слиянии
сохраняется локальное предпочтение. Numeric Ozon JSON не использует эти настройки.

## Цена и SKU Яндекс Маркета

Маркет хранит самостоятельные SKU внутри семейства по ссылкам витрины; главный
первоначально совпадает с введённым артикулом. `yandex_sku_unique` обеспечивает
одного владельца SKU. Миграция 0022 останавливается при конфликтах без удаления
данных. Добавление запускает initial collection всех обнаруженных вариантов.

В `price_history.price` записывается цена с картой плюс один лучший применимый
промокод. Основание находится в `snapshot.extensions.yandex_market`; дополнительные
ценовые колонки не нужны. Повтор цены/наличия не создаёт запись при смене кода.
Правила, ограничения и формат объяснения: [Яндекс Маркет](YANDEX_MARKET.md).


## Персональные условия покупки

Доменный evaluator `domain/purchase.py` оценивает главный вариант независимо от
`dealsEnabled` и существующего фильтра выгодных. Средняя A по времени, минимум L
и максимум H берутся из того же двухлетнего окна. Известный ценовой интервал
длится до следующего состояния; `historyStartedAt` — начало первого in-stock
интервала с ценой и положительной длительностью, обрезанное началом окна.
`historyEligible` означает строго больше 30×24 часов от этой даты до `evaluatedAt`.
Это возраст наблюдаемой истории, не число измерений или непрерывных дней наличия.

Для известной текущей цены P при in_stock выполняется логическое ИЛИ:

- `small_range`: включён T, месячная база есть, H − L ≤ T. Допустим T=0.
- `target_price`: задана цель C главного варианта, P ≤ C. Возраст истории не нужен.
- `historical_savings_share`: включён Q, месячная база есть, A > L,
  P ≤ A − Q/100 × (A − L). При A=L условие не выполняется.

Все сравнения десятичные, до округления для показа. Q=70 — это 70% пути от
средней к минимуму: A=1000, L=800 дают цену 860, а не скидку 70% от средней.
Персональная звезда не меняет фактическую экономию, порядок и фильтры каталога.
Unavailable/unpriced не удовлетворяют ни одному условию. Прогноза скидок нет.

GET/PATCH `/api/purchase-settings` возвращает/обновляет:
`smallRangeTolerance` (десятичная строка ≥0 или null),
`historicalSavingsShare` (десятичная строка >0 и ≤100 или null),
`targetNotificationsEnabled` (bool). Суммы меньше 10¹², точность до копеек;
процент с точностью до двух знаков. Все настройки изначально выключены.
Пропуск поля PATCH сохраняет значение, null выключает только числовое условие;
валидация и обновление атомарны. Ответ также содержит неизменяемый `instanceId`
данной БД; `instanceId` не принимается в PATCH. Singleton хранится в PostgreSQL.

PATCH `/api/cards/{id}` принимает `targetPrice`: десятичная положительная строка
меньше 10¹² с точностью до копеек; null удаляет цель, пропуск сохраняет.
При совместном `primaryVariantId` цель записывается новому главному варианту
в той же транзакции. Смена главного варианта не переносит чужую цель.
CardResponse возвращает цель текущего главного варианта.

`GET /api/catalog` дополнительно возвращает `instanceId`. Каждая карточка
получает `targetPrice`, `lastCollectionRunId` и `purchaseAssessment`:
`evaluatedAt`, `historyStartedAt`, `historyEligible`, `isMatch`, `matches`,
`currentPrice`, `minimumPrice`, `maximumPrice`, `averagePrice`, `targetPrice`,
`smallRangeTolerance`, `historicalSavingsShare`, `threshold` (порог цены для Q).
`matches` содержит все причины в порядке диапазон/цель/доля. Время и настройки
едины для всего снимка. Представитель группы несёт только свою оценку.
7/30/90 на неё не влияет. В пояснении каждая цена занимает отдельную строку;
дата наблюдения не выводится. Рамка имеет мягкую переливающуюся заливку звёздного
неба; при reduced-motion перелив отключён. Пояснение не обещает будущих скидок
или актуальную цену магазина без нового сбора.

Миграция `0023_purchase_criteria` добавляет настройки и nullable цель варианта,
не меняя price_history. Transfer v3 включает `targetPrice` внутри каждого variant:
отсутствие поля старого файла сохраняет локальную цель, null очищает, число
заменяет. Неверная цель отклоняется до записи. Настройки приложения в экспорт
карточек не входят. DB-free числовой JSON-режим не зависит от этих настроек.

Уведомления описаны в [desktop guide](NATIVE_DESKTOP.md#уведомления-о-целевой-цене).
