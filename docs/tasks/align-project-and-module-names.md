## Уточнение пользователя

У каждого маркетплейса своё представление результата парсинга, а ProductCard
должен быть общим объектом товара. Безусловное удаление ProductCard отменено.
Переименование проекта не даёт разрешения менять модель данных.

## План

1. Отображаемое название — Price Watch; репозиторий, команда и бинарник —
   price-watch; основной Python-пакет — price_watch. Сохранить identifier
   приложения, каталоги данных, имя БД и переменные окружения.
2. Уточнить технические имена: npm-пакет price-watch-ui; Rust library
   price_watch_desktop; обновить ссылки и lock-файлы.
3. Переименовать run_executor.py / RunExecutor в
   collection_run_executor.py / CollectionRunExecutor; native_services.rs /
   NativeServices в local_services.rs / LocalServices; frontend feature
   background в background-settings. Обновить всех потребителей.
4. Отдельно подготовить решение о едином ProductCard до любых изменений
   моделей. Целевая граница: специфический результат парсинга маркетплейса →
   преобразование → общий ProductCard → потребители приложения.
   Сейчас OzonMapper создаёт ProductSnapshot, а ProductCardNormalizer переводит
   его в прежний ProductCard. Сопоставить поля, валидацию, collected_at и
   сериализацию; выяснить, нужен ли отдельный снимок во времени.
   Предпочтение — один общий контракт с именем ProductCard, без потери полей и
   поведения действующего ProductSnapshot. Если снимок имеет самостоятельную
   роль, явно описать её и связь с ProductCard, затем согласовать решение.
   Не создавать новые классы парсеров других маркетплейсов ради симметрии.
5. Решение о переносе содержимого ozon_article_json принять после пункта 4.
   Предлагаемое место одиночного CLI —
   marketplace_connector/connectors/ozon/cli.py. Общую модель разместить в
   marketplace_connector/domain. Удалять только действительно заменённые
   обёртки, дублирующие модели и экспорты, после миграции всех потребителей.
   Не удалять функциональность по признаку её старого имени.
6. Обновить только затронутые тесты и актуальную документацию; исторические
   ADR не переписывать. Для согласованного изменения подготовить OpenSpec;
   при существенном изменении архитектуры — проект ADR с альтернативами.

## Критерии приёмки и риски

- Единая модель товара не заменяется без отдельного согласованного решения.
- Сохраняются данные, HTTP API и текущий JSON одиночного режима, включая raw.
- Доступны оба CLI; main.py <ozon_id> не требует DATABASE_URL;
  --raw, --output и настройки браузера сохраняются.
- Проверяются queued desktop/API/worker collection, main.py collect и
  одиночный числовой режим отдельно.
- Схема PostgreSQL и история цен не меняются в рамках переименований.
- Изменение Python-импортов потребует миграции внешних скриптов, если они есть;
  сохранение старых совместимых обёрток не планируется.

## Проверки

не запускались. При реализации: релевантные Python-тесты, проверка импортов и
числового режима без DATABASE_URL, TypeScript, frontend unit tests, demo E2E,
Rust tests и desktop build. Demo E2E не доказывает работу живых служб;
PostgreSQL integration tests допустимы только на отдельном TEST_DATABASE_URL.
