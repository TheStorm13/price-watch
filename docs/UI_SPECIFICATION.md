# UI-спецификация анализатора цен

## 1. Назначение

Локальное web-приложение позволяет управлять карточками маркетплейсов,
запускать сбор актуальных цен и анализировать историю. Интерфейс реализуется как
SPA на React, TypeScript и Vite и работает поверх HTTP API Python-приложения.

Первая версия ориентирована на одного локального пользователя. Авторизация,
уведомления, автоматическое расписание, сопоставление одинаковых товаров разных
маркетплейсов и управление пользователями не входят в UI MVP.

## 2. Продуктовые принципы

1. Одна карточка соответствует одному маркетплейсу.
2. Основной объект интерфейса — `MarketplaceCard`, а не абстрактный товар.
3. Главный экран отвечает на три вопроса: что отслеживается, какова текущая
   цена и когда данные обновлялись.
4. История никогда не скрывается за «текущим значением»: из строки карточки
   должен быть прямой переход к графику и измерениям.
5. Ошибка одной карточки не останавливает общий сбор.
6. Интерактивная проверка Ozon является явным состоянием процесса, а не
   зависшим запросом.
7. Интерфейс не показывает несуществующие возможности. WB и AliExpress могут
   отображаться как недоступные варианты до появления коннекторов.

## 3. Основные пользовательские сценарии

### 3.1 Добавление карточки

1. Пользователь нажимает «Добавить карточку».
2. Выбирает маркетплейс.
3. Вводит внешний ID карточки.
4. При желании вводит временное название и URL.
5. После сохранения новая строка появляется в списке со статусом «Нет данных».

### 3.2 Сбор всех цен

1. Пользователь нажимает «Обновить цены».
2. Backend создаёт запуск и сразу возвращает его ID.
3. UI открывает панель прогресса и опрашивает состояние запуска.
4. Когда Ozon требует участия, Chrome открывается на локальной машине, а UI
   показывает состояние «Требуется проверка».
5. Пользователь проходит проверку в Chrome и нажимает в UI «Проверка пройдена».
6. После завершения UI обновляет таблицу и показывает итоговые счётчики.

### 3.3 Сбор одной карточки

Запускается из строки таблицы или экрана карточки. Процесс идентичен общему
сбору, но содержит одну карточку.

### 3.4 Анализ истории

1. Пользователь открывает карточку.
2. Видит последнюю цену и состояние наличия.
3. Выбирает период 7, 30 или 90 дней.
4. Сравнивает текущую, минимальную, максимальную цену и середину диапазона.
5. Просматривает график и таблицу отдельных измерений.

## 4. Информационная архитектура

```text
Приложение
├── Карточки                 /
│   ├── Список карточек      /cards
│   └── Детали карточки      /cards/:cardId
└── Запуски                  /runs
```

Отдельный dashboard в MVP не нужен: список карточек уже является рабочим
центром приложения. Настройки также не выделяются в отдельный экран, пока у них
нет реального содержимого.

## 5. App shell

### Desktop, от 1024 px

- фиксированная боковая навигация шириной 224 px;
- логотип/название «Price Watch»;
- пункты «Карточки» и «Запуски»;
- основная область с максимальной шириной 1440 px;
- верхняя строка страницы содержит заголовок и основные действия;
- навигация остаётся компактной: без поиска, профиля и декоративных виджетов.

### Поддерживаемые размеры

Приложение предназначено только для ПК и ноутбуков. Минимальная поддерживаемая
ширина viewport — 1024 px. На ширине 1024–1179 px боковая навигация сворачивается
до панели иконок шириной 72 px, фильтры могут переноситься на вторую строку, но
таблица сохраняет табличную структуру. Mobile-композиция и нижняя навигация не
входят в область поддержки.

## 6. Экран «Карточки»

### Заголовок

- H1: «Карточки»;
- подпись: «Текущие цены и история отслеживаемых карточек»;
- основная кнопка: «Добавить карточку»;
- вторичная кнопка: «Обновить цены».
- кнопки «Экспорт» и «Импорт» для всех карточек и полной сохранённой истории.

Импорт открывает выбор JSON-файла и показывает до подтверждения число новых и
объединяемых карточек, добавляемых и пропускаемых наблюдений. Ошибочный файл
не меняет данные. В desktop режиме экспорт открывает системный выбор места
сохранения.

### Панель фильтров

- текстовый поиск по названию и внешнему ID;
- фильтр маркетплейса: «Все», «Ozon», «Wildberries», «AliExpress»;
- фильтр состояния: «Все», «В наличии», «Нет в наличии», «Нет данных»;
- кнопка сброса появляется только при активных фильтрах.

Фильтры являются клиентским состоянием и отражаются в query string, чтобы
ссылку на представление можно было сохранить.

### Таблица

Колонки:

1. `Карточка` — название, внешний ID и URL;
2. `Маркетплейс`;
3. `Цена`;
4. `Наличие`;
5. `Обновлено`;
6. меню действий.

Правила отображения:

- цена форматируется в российских рублях без копеек, если значение целое;
- `null` отображается как «—», а не `0`;
- `in_stock` — «В наличии»;
- `out_of_stock` — «Нет в наличии»;
- `unknown` — «Неизвестно»;
- отсутствие истории — «Нет данных»;
- относительное время («5 минут назад») сопровождается точной датой в tooltip;
- вся строка кликабельна и открывает детали;
- действие «Обновить» доступно из меню строки;
- действие «Приостановить» меняет `is_active`, но не удаляет историю.
- приостановленная карточка не участвует в сборе и не показывается в выгодных предложениях;

Сортировка MVP:

- по умолчанию — сначала активные, затем по `id`;
- пользователь может сортировать по цене и времени обновления;
- сортировка отражается в query string.

### Состояния

#### Loading

Скелетон сохраняет геометрию заголовка, фильтров и 6 строк таблицы. Не
используется полноэкранный spinner.

#### Empty

Текст: «Карточек пока нет».

Подсказка: «Добавьте первую карточку маркетплейса, чтобы начать собирать
историю цены».

Действие: «Добавить карточку».

#### Filtered empty

Текст: «По выбранным условиям ничего не найдено».

Действие: «Сбросить фильтры».

#### Error

Короткое сообщение об ошибке загрузки и кнопка «Повторить». Технический stack
trace пользователю не показывается.

## 7. Добавление карточки

Форма открывается в правой drawer-панели.

Поля:

1. `Маркетплейс` — обязательный select;
2. `ID карточки` — обязательное текстовое поле;
3. `Название` — необязательное поле;
4. `URL` — необязательное поле.

В первой версии Ozon активен. Недоступные коннекторы отображаются disabled с
нейтральной подписью «Коннектор ещё не подключён».

Валидация:

- marketplace и external ID не могут быть пустыми;
- Ozon ID состоит из ASCII-цифр;
- URL, если задан, должен быть абсолютным HTTP(S) URL;
- конфликт `(marketplace, external_id)` отображается как ошибка поля, а не
  общее уведомление.

Состояния кнопки: «Добавить», «Добавление…», disabled при невалидной форме.
После успеха drawer закрывается, строка появляется в списке и получает короткое
неблокирующее подтверждение.

## 8. Экран карточки

### Верхняя область

- возврат к списку;
- название карточки;
- маркетплейс и внешний ID;
- действия «Обновить» и меню управления активностью.

### Текущее состояние

Открытая горизонтальная область, не набор вложенных карточек:

- текущая цена — главный визуальный акцент;
- наличие;
- время последнего измерения;
- середина диапазона `(минимум + максимум) / 2` за выбранный период;
- минимум и максимум вторичным рядом.

### График цены

- линейный график `observed_at → price`;
- периоды 7 / 30 / 90 дней;
- разрывы при `price = null`, без подстановки нуля;
- tooltip показывает дату, цену и наличие;
- линия середины диапазона отображается пунктиром;
- ось Y охватывает видимый диапазон цен с отступом 10%; подряд идущие
  одинаковые цены представлены только первой точкой;
- при одном измерении показывается точка и объясняющий текст;
- при отсутствии данных отображается спокойное пустое состояние.

### История измерений

Таблица под графиком:

- дата и время;
- цена;
- наличие;
- ID запуска.

Показываются первые 50 строк с постраничной загрузкой. График использует
все изменения цены за период, независимо от текущей страницы таблицы.

## 9. Экран «Запуски»

Таблица содержит:

- ID запуска;
- статус;
- начало;
- длительность;
- обработано успешно;
- ошибки;
- всего карточек.

Статусы:

- `queued` — «В очереди»;
- `running` — «Выполняется»;
- `waiting_for_user` — «Требуется проверка»;
- `completed` — «Завершён»;
- `completed_with_errors` — «Завершён с ошибками»;
- `failed` — «Ошибка».

Экран деталей запуска показывает карточки с ошибками и их сообщения. Полный
traceback раскрывается отдельно и доступен для копирования после перезагрузки.

## 10. Панель активного сбора

Панель отображается поверх текущего экрана, но не блокирует навигацию.

### `queued` / `running`

- заголовок «Обновление цен»;
- обработано `N из M`;
- progress bar;
- текущий маркетплейс и внешний ID, если backend их сообщает.

### `waiting_for_user`

Этот статус возможен у worker, запущенного без скрытого дисплея. Desktop
сбор при проверке завершается с ошибкой; после ручной проверки в Chrome
пользователь повторяет сбор.

- заметный, но не тревожный статус «Требуется проверка Ozon»;
- инструкция: «Завершите проверку в открывшемся Chrome, затем продолжите»;
- основная кнопка «Проверка пройдена»;
- вторичная кнопка «Отменить запуск» появится только после поддержки отмены на
  backend; в MVP она не отображается.

### Завершение

- успешный итог: «Цены обновлены»;
- частичный итог: «Обновление завершено с ошибками»;
- счётчики успешных и неуспешных карточек;
- кнопки «Закрыть» и «Открыть запуски».

UI обновляет данные карточек после завершения через invalidation server-state
кэша, а не вручную изменяет отдельные строки.

## 11. Визуальное направление

Характер: спокойный аналитический инструмент, а не маркетинговый dashboard.

- фон приложения: светло-серый `#F6F7F9`;
- основные поверхности: настоящий белый `#FFFFFF`;
- основной текст: графитовый `#17191C`;
- вторичный текст: `#667085`;
- границы: `#E4E7EC`;
- основной action: насыщенный синий `#2563EB`;
- наличие/успех: зелёный `#16803C`;
- предупреждение: янтарный `#B54708`;
- ошибка: красный `#B42318`;
- sidebar: глубокий графит `#15171A` без градиента;
- табличные числа используют tabular numerals;
- радиусы: 8 px для контролов, 12 px для drawer и крупных областей;
- тени применяются только для overlay-поверхностей;
- декоративные badges, bento-сетка, glassmorphism и лишние градиенты не
  используются.

Типографика:

- UI: Inter или совместимый локальный sans-serif fallback;
- H1: 28/34, 650;
- H2: 20/28, 650;
- основной текст: 14/20, 400;
- controls: 14/20, 550;
- подписи и таблица: 13/18;
- цена на detail: 36/42, 650, tabular numerals.

Иконки — единое outline-семейство со stroke 1.75 px. Они используются только
для навигации и понятных действий, всегда имеют текстовый `aria-label` или
видимую подпись.

## 12. Motion

- drawer: 180–220 ms ease-out;
- изменение progress bar: 200 ms linear;
- обновлённая строка может получить одно мягкое фоновое выделение на 600 ms;
- график появляется без декоративной длинной анимации;
- `prefers-reduced-motion` отключает все необязательные переходы.

## 13. Доступность

- WCAG 2.2 AA по контрасту и клавиатурной навигации;
- видимый `focus-visible` для всех интерактивных элементов;
- drawer удерживает фокус и возвращает его инициатору после закрытия;
- статусы не кодируются только цветом;
- прогресс активного запуска имеет `aria-live="polite"`;
- ошибки формы связаны с полями через `aria-describedby`;
- таблицы имеют корректные заголовки и подпись;
- основные интерактивные controls имеют область не меньше 40×40 px.

Принципы React:

- `App` содержит только композицию providers и router;
- server state не копируется в глобальный client state;
- локальное состояние формы и drawer остаётся рядом с компонентом;
- загрузка карточек, истории и запусков оформляется отдельными query hooks;
- мутации инвалидируют связанные queries;
- тяжёлый модуль графика загружается только на detail route;
- компоненты не объявляются внутри других компонентов;
- derived values вычисляются во время render, а не синхронизируются через
  `useEffect`;
- фильтры URL являются единственным источником состояния списка.

## 15. Технический стек

- React + TypeScript;
- Vite;
- React Router для client-side маршрутов;
- библиотека server-state запросов с дедупликацией и invalidation;
- CSS Modules и общие CSS tokens, без тяжёлого UI-kit;
- библиотека доступных headless-примитивов только для dialog/drawer/menu;
- SVG chart library, загружаемая лениво;
- Vitest + React Testing Library;
- Playwright для основных пользовательских сценариев.

В development Vite проксирует `/api` на Python backend. В клиентский bundle
могут попадать только переменные с префиксом `VITE_`; `DATABASE_URL` и другие
секреты остаются исключительно на backend.

## 16. Типы frontend

```ts
type Marketplace = 'ozon' | 'wildberries' | 'aliexpress'
type Availability = 'in_stock' | 'out_of_stock' | 'unknown'

interface MarketplaceCard {
  id: number
  marketplace: Marketplace
  externalId: string
  title: string | null
  url: string | null
  isActive: boolean
  currentPrice: number | null
  currentAvailability: Availability | null
  lastObservedAt: string | null
  createdAt: string
  updatedAt: string
}

interface PriceHistoryPoint {
  id: number
  cardId: number
  collectionRunId: number | null
  price: number | null
  availability: Availability
  observedAt: string
}

interface PriceStatistics {
  cardId: number
  days: number
  averagePrice: number | null
  minimumPrice: number | null
  maximumPrice: number | null
  observationsCount: number
  observedDays: number
}
```

API использует camelCase. Преобразование из snake_case Python-моделей
выполняется на backend, чтобы frontend не содержал двух соглашений об именах.

## 17. Требуемый HTTP API

### Карточки

```text
GET    /api/cards
GET    /api/cards/export
POST   /api/cards/import/preview
POST   /api/cards/import
POST   /api/cards
GET    /api/cards/{cardId}
PATCH  /api/cards/{cardId}
DELETE /api/cards/{cardId}
GET    /api/cards/{cardId}/history?days=30&page=1&pageSize=50
GET    /api/cards/{cardId}/chart?days=30
```

`PATCH` используется для `isActive`, названия и URL. Удаление карточки требует
подтверждения; карточку незавершённого запуска удалить нельзя.

### Запуски

```text
GET   /api/runs?page=1&pageSize=50
GET   /api/runs/{runId}
POST  /api/runs                  body: { cardId?: number }
POST  /api/runs/{runId}/continue
```

`POST /api/runs` отвечает `202 Accepted` и не удерживает HTTP-соединение до
завершения браузерного сбора. UI опрашивает `GET /api/runs/{runId}` раз в одну
секунду во время активного процесса и прекращает polling после terminal status.

Пример состояния запуска:

```json
{
  "id": 12,
  "status": "waiting_for_user",
  "totalCount": 3,
  "successCount": 1,
  "failureCount": 0,
  "current": {
    "cardId": 2,
    "marketplace": "ozon",
    "externalId": "1604900984"
  },
  "challenge": {
    "type": "browser_verification",
    "message": "Завершите проверку в открывшемся Chrome"
  },
  "startedAt": "2026-09-21T13:00:00Z",
  "finishedAt": null
}
```

## 18. Реализация backend

Backend реализован на FastAPI, SQLAlchemy 2, Alembic и PostgreSQL. Сбор выполняет
отдельный локальный worker, а Ozon открывается через Playwright. API использует
camelCase DTO, структурированные ошибки и не передаёт в браузер `DATABASE_URL`,
путь профиля Chrome. Traceback ошибок сбора доступен только в деталях запуска.

## 19. Формат ошибок API

```json
{
  "error": {
    "code": "card_already_exists",
    "message": "Такая карточка уже добавлена",
    "field": "externalId",
    "requestId": "..."
  }
}
```

UI принимает решения по `code`, а не разбирает текст сообщения.

## 20. Критерии готовности UI MVP

1. Пользователь может добавить Ozon-карточку без терминала.
2. Список показывает последнюю цену и корректно различает `0`, `null` и
   отсутствие истории.
3. Можно запустить сбор всех карточек и одной карточки.
4. Состояние проверки Ozon явно отображается и продолжается из UI.
5. Ошибка одной карточки не ломает весь экран и не скрывает успешные результаты.
6. Detail screen показывает статистику, график и историю 7/30/90 дней.
7. Фильтры и сортировка сохраняются в URL.
8. Интерфейс полностью управляется клавиатурой и проходит базовые проверки
   accessibility.
9. Desktop viewport от 1024 px не имеет горизонтального overflow всей страницы.
10. Unit, component и ключевые Playwright-сценарии проходят стабильно.

## 21. Статус реализации

Desktop UI, HTTP API, PostgreSQL-очередь, worker и Playwright-коннектор
реализованы. Для полноценного сценария одновременно запускаются API, worker и
Vite dev server.
