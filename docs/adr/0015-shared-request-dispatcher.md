# ADR 0015: Последовательные маркетплейсы с отдельными request pools

- Статус: **Accepted** — план одобрен пользователем 2026-11-08; реализация в работе.
- Дата: 2026-11-08.
- Рабочий контекст и проверки: [shared-request-dispatcher](../../openspec/changes/shared-request-dispatcher/spec.md).
- Заменяет только concurrency/rate policy [ADR0006](0006-ozon-session-json-transport.md), [ADR0009](0009-wildberries-size-and-wallet-price.md) и [ADR0014](0014-ozon-unpaced-async-concurrency.md); ценовые и identity контракты сохраняются.

## Контекст

Сегодня CollectionService запускает площадки одновременно и ограничивает целые
товары, а транспорты имеют собственные concurrency/rate gates. Standalone пути
обходят card limits. Ozon/Ali используют browser fetch, WB — native SDK с fan-out,
общим состоянием и сетевыми hooks. Унификация всех HTTP через глобальный browser
routing добавляет влияние на cache и сложности интеграции native runtime.

Пользователь выбрал отдельные асинхронные request pools по 100 и последовательный
запуск площадок. Плановые M стартов/с запрещены; 100 — стартовое значение, не оптимум.

## Рассмотренные варианты

1. Сохранить card semaphores плюс transport limits: дублирующие ограничения и
   разное поведение direct/queued consumers.
2. Параллельные площадки с независимыми pools: до 300 запросов в одном run.
3. Глобальный HTTP dispatcher: даёт общий бюджет параллельных площадок, но требует
   общей очереди и межплощадочной интеграции, которые сейчас не нужны.
4. **Последовательные площадки и локальные request pools 100:** выбранный вариант.
   Общий предел run достигается последовательностью; адаптеры сохраняют специфику.

## Предлагаемое решение

CollectionService выполняет непустые этапы ozon → aliexpress → wildberries;
внутри этапа — асинхронная обработка целей и сохранение результатов по завершении.
Следующий этап ждёт завершения/отмены и дренирования предыдущего. Discovery/pending
обрабатываются без нарушения последовательности и frozen-target правил.

Одна production настройка max_in_flight_requests=100, у каждого транспорта свои
очередь и active state. Слот охватывает один управляемый HTTP-запрос до полного тела
или подтверждённого прекращения I/O; helper/retry учитывается наравне с основным.
Queue wait не расходует HTTP timeout. Parent get_product не удерживает вложенный
permit. Нет card limits, token bucket и планового starts_per_second.

Ozon/Ali допускают fetch перед browser I/O. WB использует собственные request hooks
с изолированным состоянием и индивидуальной отменой. Единый browser interception,
отключение cache и bypass Service Worker не вводятся ради общей абстракции.
Таймауты, конечные retries, Retry-After, profile/bootstrap/recovery locks сохраняются.

ChromeSession удерживает существующий стабильный профиль и процесс на время run;
bootstrap выполняется только активной площадкой. Перезапуск между этапами не нужен.
Ошибка цели не останавливает run; изолированный fatal stage отменяется/дренируется,
остаток получает ошибки, затем выполняется следующая площадка. Общая отмена,
LeaseLost или потеря общего browser прекращают весь run.

## Последствия и границы

- Общая активность одного run не превышает 100 управляемых запросов; нет гарантии
  между независимыми процессами/профилями или для фонового browser traffic.
- Время площадок складывается; медленный этап задерживает остальные до завершения
  либо конечной ошибки. Это осознанная цена более простой оркестрации.
- Лимит не ограничивает размеры response bodies и произвольной pending очереди.
- WB требует реального refactor shared state/cancellation, а не снятия lock.
  Невозможность безопасной native concurrency — блокер, не повод скрыть сериализацию.
- Диагностика прежнего Ali N=8 timeout отложена пользователем в [backlog](../BACKLOG.md#таймауты-aliexpress-в-эксперименте-с-n8). Для всех коннекторов выбран предел 100; проверки очереди, таймаутов и освобождения слотов сохраняются. Прежняя ошибка не объявляется исправленной.
- Все consumers мигрируются полностью; legacy knobs/fallback не сохраняются.
  Миграций данных и изменений SKU/кошелька/истории/API payload нет.

Для управляемых WB-запросов bridge заменяет timeout-сигнал native SDK своим
HTTP-таймером после admission: native fetchStatic иначе включает 30 секунд ещё
до очереди. Индивидуальная отмена передаётся контроллером владельца артикула,
общий profile/wallet bootstrap продолжает работу для остальных ожидающих.
