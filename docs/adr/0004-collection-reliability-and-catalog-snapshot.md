# ADR 0004: Владение сбором, результаты целей и снимок каталога

- Статус: **Accepted**, план и реализация приняты пользователем 2026-10-22.
- Дата: 2026-10-22.
- Change: `openspec/changes/archive/2026-10-22-harden-collection-reliability/`.
- Связанные ADR: 0001 (владение службами остаётся в Tauri), 0002 (desktop
  остаётся единственным live UI). Их решения не заменяются.

## Контекст

Прямой CLI и worker по-разному ведут активный запуск. Повтор знает только
индивидуальные ошибки, а история изменений не доказывает все успехи сбора.
Запись результатов не везде проверяет владельца. Каталог загружается тремя
независимыми ответами и может смешивать состояния во время сбора.

Пользователь выбрал единый снимок с ограничением регрессии производительности
и полный переход на новые решения без сохранения обратной совместимости.

## Решение

Один application runner для direct CLI и worker с отдельным токеном владения
каждой попыткой и heartbeat. Транзакционные записи проверяют токен и активное
состояние. Результаты целей хранятся отдельно; успех, включая неизменную цену,
фиксируется атомарно с историей и прогрессом. Повтор берёт ошибки и остаток.

GET /api/catalog читает cards/groups/deals одним стабильным снимком БД,
повторно используя общие исходные данные. UI хранит один объект каталога.
Заменённые endpoint, список целей в массиве и tokenless-записи удаляются
после перевода потребителей. Известные пользовательские данные переносятся;
неопределённость старых результатов отмечается явно в единой новой модели.

## Альтернативы

- Heartbeat только для CLI: не исправляет неполный retry и устаревшие записи.
- Поставить CLI в очередь: меняет прямой режим и требует отдельного worker.
- Считать успехи по истории: пропускает успешные неизменные цены.
- JSON-массив результатов: сложнее обеспечить атомарность и идемпотентность.
- Три согласованных endpoint: ответы всё равно получены в разные моменты.
- Revision-протокол или блокировка сборщика: сложнее и дороже выбранного снимка.

## Последствия и проверка

Нужна forward-only миграция схемы, остановка старых процессов и полный перевод
API/mock/UI. История цен сохраняется; полные исторические результаты не
выдумываются. Rust lifecycle, профиль Chrome, расписание и продуктовые CLI-
режимы остаются прежними. Новые зависимости не требуются.

Производительность проверяется baseline/after на одинаковых синтетических
наборах: p95 каталога не выше max(1.20 × baseline, baseline + 50 мс), без N+1
и повторных агрегаций. Пороги памяти и write-throughput, сценарии гонок и
миграции описаны в design.md. План и результаты реализации приняты пользователем.

## Проверка принятого решения

[Отчёт](../tasks/harden-collection-reliability/verification.md) содержит
результаты тестов, live smoke и baseline/after. Все согласованные пороги пройдены;
HTTP p95 быстрее на 23–45%, SQL 9→3. Скорость фиксации результатов на M/L
снизилась на 18.4%/16.8%, в пределах согласованного порога 20%.
