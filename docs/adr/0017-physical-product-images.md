# ADR 0017: Подготовленные фото под физический размер

Статус: Accepted (design), 2026-11-09. Реализация ожидает визуальной приёмки.
Заменяет фиксированный рецепт 204 px из [ADR0016](0016-cached-product-thumbnails.md).

## Причина

Один PNG 204 px выглядит сглаженно в Chromium и зернисто в системном WebKitGTK
при уменьшении до 68 px на DPR=1. Отдельная проба с исходным JPEG воспроизводит
эффект. CSS optimizeQuality и Canvas drawImage high его не устранили. Пользователь
сравнил ×1/×1.5/×2/×4 и выбрал ×1, затем одобрил все три роли и завершение решения.
Проба системного WebView не заменяет приёмку окна установленного Tauri-приложения.

## Решение

Три логических роли: list (каталог/SKU 68×68), tile (278×190), detail (158×158)
CSS px. Физический PNG = round(CSS × DPR), без дополнительного коэффициента
качества, DPR 0.25..8. Pillow Lanczos из оригинала, без upscale/crop; прозрачное
поле всей области и целочисленная центровка. Рамка detail 160×160 включает border;
плитка фиксирована 280×476, меняется только число колонок.

Один read-only защищённый endpoint с profile/scale и optional variantId; URL
выбирается сервером, принадлежность SKU проверяется. Общий сжатый исходник по URL
и ленивые размерные PNG хранятся на диске. Независимые LRU по 128 МиБ не позволяют
крупным исходникам вытеснить все готовые PNG. Singleflight объединяет загрузки
между ролями; общий предел параллельности 2. TTL 24 часа, conditional GET, digest,
atomic write и 30 секунд отрицательного кэша сохраняются. В PostgreSQL остаются
только оригинальные URL; карточки и история не модифицируются.

## Альтернативы и последствия

Постоянные три BLOB в БД усложняют миграции/бэкапы для восстанавливаемых данных.
Независимая загрузка для каждой роли расходует сеть. Получение detail из миниатюры
теряет детали. Перенос оболочки на Chromium несоразмерен этой задаче.

Три роли не означают ровно три файла навсегда: разные DPR имеют свои производные,
ограниченные LRU; одинаковый URL разделяет данные между карточками. После
вытеснения исходника новый профиль требует загрузки; готовый PNG остаётся доступен.
Округление при дробном DPR ограничивает идеальное 1:1, а качество малого оригинала
не улучшается искусственным увеличением. Изменения API полностью мигрируют UI,
mock, benchmark и существующие проверки; старый size-контракт не поддерживается.
