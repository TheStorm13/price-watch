# ADR 0014: Асинхронный сбор Ozon без планового лимита частоты

- Статус: Accepted (design), выбран пользователем 2026-11-08; пользователь также выбрал фиксированный N=8 и поручил внедрение. Приёмка реализации остаётся отдельным этапом.
- Дата: 2026-11-08
- Уточняет [ADR 0006](0006-ozon-session-json-transport.md): заменяет выбранную политику фиксированных 5 стартов/с. Исторический ADR не переписывается.

## Решение

Выбранный подход для Ozon — асинхронный браузерный JSON-сбор через существующий
профиль Chrome, без планового ограничения стартов запросов (`starts_per_second=None`),
с конечным настраиваемым пределом N одновременно выполняемых HTTP-запросов.
Сохраняются общий Retry-After/cooldown, таймауты, ограниченные повторы,
независимая отмена и согласованное восстановление сессии.
Проверка доступа/CAPTCHA не является поводом бесконечно повторять запросы.

Пользователь выбрал **фиксированный N=8** для обычного сбора после сравнения N=5/8/12.
Это выбранная настройка, не доказанный оптимум и не официальный лимит Ozon.
Адаптивный контроллер не вводится.
Это решение не распространяется на AliExpress и Wildberries.

## Основания и ограничения

На одинаковых 40 SKU проведены A/B/C/C/B/A и C/D/D/C, с паузами 30 секунд,
в видимом Chrome с существующим профилем. A=(5,5/с), B=(1,5/с),
C=(1,без плановой частоты), D=(5,без плановой частоты).
В отдельной C/D-серии среднее время C=5,919561 с, D=1,424168 с: ускорение 4,1565 раза.
Все 160 сборов этой серии успешны, HTTP 200, без 429, повторов и восстановления.
Наличие полей и их счётчики совпали во всех десяти прогонах; значения цен и
содержимое полей на равенство не сравнивались. Один SKU был не в наличии без цены.
B исключён пользователем из следующего исследования.

Это короткие серии по два прогона на режим на прогретых связанных SKU.
Длительная устойчивость и другие системы не проверены.
Нет основания объявлять снятие планового лимита универсально более надёжным.
Headless-попытка получила отказ доступа и не смешивается с видимыми измерениями.

Доказательства и история реализации: [результат эксперимента](../../openspec/changes/experiment-ozon-serial-dispatch/spec.md),
[сырые A/B/C-метрики](../../openspec/changes/experiment-ozon-serial-dispatch/measurements.json),
[сырые C/D-метрики](../../openspec/changes/experiment-ozon-serial-dispatch/measurements-cd.json).

## Внедрение

Обычный клиент и транспорт используют concurrency=8, starts_per_second=None.
Общий сборщик предоставляет Ozon восемь слотов попыток карточек; остальные
площадки сохраняют общий пул из пяти. В смешанном запуске возможно восемь попыток
Ozon плюс пять остальных; собственные ограничения транспортов WB/AliExpress
сохраняются. Пауза внешнего повтора освобождает слот карточки.

Один builder-клиент Ozon и один транспорт на сеанс обеспечивают общий предел
восемь для product/modal-запросов и HTTP-повторов. CLI collect и queued worker
используют общий CollectionService; числовой CLI без БД получает ту же политику
через AsyncOzonClient. Числовая частота остаётся явной настройкой стенда для
воспроизведения контрольных режимов, автоматического возврата к 5/с нет.
Схемы данных и история цен не меняются.

В фиксированной серии первые десять пакетов успешны (400 SKU, HTTP 200):
среднее время успешного пакета N5=1,491 с (3), N8=1,069 с (3), N12=0,805 с (4).
Последние два пакета N8/N5 не отправили товарных запросов: ошибка подготовки
сессии, лог сообщает о закрытом браузере/контексте; причина закрытия не установлена.
Первый N5 пересекался с запуском локальных тестов. Это неполная для сравнения
серия и не доказательство долговременной устойчивости; N12 быстрее на успешных
коротких пакетах, а N8 выбран пользователем для внедрения.
[Полный отчёт](../../openspec/changes/experiment-ozon-serial-dispatch/measurements-fixed-n.json)
сохранён вместе с ошибками. CPU/RSS измерены приближённо по группе процессов Chrome.
