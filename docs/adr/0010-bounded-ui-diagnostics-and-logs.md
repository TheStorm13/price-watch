# ADR 0010: Ограниченная отрисовка и текущая диагностика

- Статус: **Proposed**. Требуется согласование конкретных архитектурных решений до реализации.
- Дата: 2026-10-29. Уточнён 2026-10-30 по политике хранения пользователя.
- Change: [improve-ui-and-data-performance](../../openspec/changes/improve-ui-and-data-performance/proposal.md).
- Основание: пользователь разрешил все обсуждённые задачи производительности, кроме ускорения Ozon. Это разрешение на направление работ; этот ADR не считается отдельно принятым.

## Контекст

ADR 0004 требует lease, атомарной фиксации результата и согласованного каталога; ADR 0007 оставляет транзакции в PostgreSQL adapters. Эти границы сохраняются. `collection_runs.errors` растёт JSONB-конкатенацией; обычные чтения materialize весь ORM record. Ошибки требуются UI только при открытии диагностики.

Все процессы сейчас направляют вывод непосредственно в append-файлы. Переименование таких файлов само по себе не переключит открытые дочерние дескрипторы. Общий Chrome session теперь принадлежит `marketplace_connector/browser/session.py`, поэтому охват только старого Ozon client оставил бы CLI без ограничения.

Одиночные диагностические замеры development mock UI: 100/1000/5000 карточек дают 2853/27153/135153 DOM-узла. Это подтверждает линейный DOM, но не является production p95 и не доказывает процент будущего ускорения.

## Предлагаемые решения

### 1. Виртуализированное представление согласованного каталога

Сохранить существующий единый `/api/catalog` и полную модель фильтрации/сортировки. Выделить модель представления и отдельные memo-компоненты строки, плитки и группы. Добавить headless `@tanstack/react-virtual`: плоские видимые записи списка и визуальные ряды сетки с отдельными заголовками групп. Группа из 5000 карточек также виртуализируется; нельзя считать целую группу одним огромным элементом.

Измерять переменные высоты, учитывать число колонок при resize и заголовки над списком. Стабильные ключи основаны на типе и ID, а не позиции. Состояние выбора хранится вне виртуального окна. Сохранять позицию возврата из деталей; удерживать владельца фокуса/открытого меню в диапазоне до закрытия. Для табличного режима сохранить семантику и доступную клавиатурную навигацию. Редактор групп использует ту же идею ограниченного окна и Set выбранных ID.

Разделить context команд/состояния запуска и прогресса. Каталог не подписывается на счётчики; panel остаётся подписана. Стабильные методы мутаций вместо объектов hook в dependencies. `useDeferredValue` применяется вместе с memo-границей списка. Форматтеры Intl переиспользуются. PriceChart мемоизирует подготовку данных; min/max вычисляются проходом с точными денежными сравнениями, точки и разрывы наличия сохраняются полностью.

Альтернативы: memo без виртуализации оставляет исходную стоимость DOM; `content-visibility` уменьшает layout/paint, но сохраняет DOM и React-работу; client pagination меняет непрерывный просмотр и требует особых правил разбиения групп. Server pagination уменьшает payload, но затрагивает единый снимок, глобальные сортировки, выбор и уведомления; без отдельного snapshot-token протокола её нельзя вводить как локальную оптимизацию. Сейчас выбрать виртуализацию и измерять оставшуюся стоимость полного ответа отдельно.

### 2. Небольшая текущая диагностика в существующем поле

Пользователь 2026-10-30 уточнил: хранить все ошибки и архивы журналов не нужно. Отдельная таблица ошибок отменена. Оставить `collection_runs.errors` с жёсткой верхней границей: 20 примеров и 128 KiB сериализованного UTF-8 JSON суммарно, только для последнего созданного запуска (максимальный ID). Message до 1 KiB, traceback до 4 KiB, прочие строки также ограничены; проверять общий сериализованный размер. Сохранить первые 19 примеров и место для итоговой общей ошибки; если общей ошибки нет, можно сохранить двадцатый пример. Остальные сбои меняют точные счётчики и результаты целей, но не увеличивают диагностику.

По окончательному уточнению пользователя хранить ошибки только последнего созданного запуска, независимо от queued/running/terminal статуса. Создание нового запуска, включая enqueue/retry, атомарно очищает errors всех предыдущих и отмечает их expired; при rollback создания прежний набор остаётся. Конкурентные writers сериализуются с созданием: пример ошибки может сохранять только запуск с максимальным ID. Поздний результат старого запуска сохраняет цель и точные счётчики, но не восстанавливает подробности; позднее завершение также не переключает владельца диагностики. Lease, pending→failed, счётчик и доступный пример остаются атомарными; retry определяется сохранёнными targets, а не выборкой ошибок.

Добавить компактный diagnosticsStatus: complete/limited/expired. Довести через domain/API/mock/UI, чтобы интерфейс не выдавал примеры за полный список и различал очищенную диагностику. `includeErrors=false`, списки запусков и heartbeat не выбирают поле errors из БД; `true` возвращает доступную выборку. Все потребители переводятся на новый смысл без legacy fallback.

Alembic 0017 не создаёт таблицу и не удаляет errors: после остановки writers добавляет статус и нормализует старые массивы по новой политике. Подробности всех запусков, кроме последнего созданного, очищаются намеренно по запросу пользователя; только запуск с максимальным ID получает ограниченную выборку независимо от его статуса. Сами запуски, цели, счётчики, карточки и история цен сохраняются. Проверить миграцию/rollback на disposable DB; на этапе планирования данные не меняются.

Альтернативы: отдельная append-only таблица была избыточна для небольшой временной диагностики; только SQL projection не ограничивает хранение; cap для каждого исторического запуска всё равно копит подробности без конца; удаление сразу при завершении скрывает причину сбоя до просмотра. Выбран ограниченный JSONB только последнего созданного запуска и очистка предыдущих при создании следующего.

### 3. Один активный журнал без архивов

Для каждого API/PostgreSQL/Xvfb/worker/Chrome держать один файл до 10 MiB. При новом запуске процесса очистить прежний файл. При заполнении владелец записи обнуляет файл и продолжает, без rename и архивов. Последний файл после выхода/сбоя остаётся до следующего запуска, чтобы можно было прочитать причину остановки. Возрастные архивы, три копии и хранение 14 дней отменены.

Вывод дочерних процессов передаётся через pipes одному владельцу записи; оба потока сериализуются. Чтение фиксированными блоками до 64 KiB, запись делится по свободному месту до лимита, длинные строки не накапливаются в памяти. Владение файлом позволяет безопасно очистить его: дочерний процесс не держит старый inode, нет гонки внешнего copytruncate с прямыми writers. Rust helper охватывает native services, worker, ручной Chrome и lifecycle сообщения; Python helper — общий ChromeSession queued/direct/numeric.

После выхода дочитать доступный вывод и освободить обработчики; остановка не зависит от бесконечного ожидания EOF от потомков. При I/O-сбое продолжать дренирование, ограничить сообщения об ошибке и разрешить повторную попытку записи. Никаких безразмерных очередей или внешней службы. Прежний файл очищается только при новом запуске принадлежащего приложению процесса, не произвольного владельца профиля.

Альтернативы: очистка только при старте не ограничивает долгую работу; удаление открытого файла оставляет inode занятым; архивирование не соответствует уточнённой потребности; удаление сразу после сбоя лишает текущей диагностики. Выбран один ограниченный файл, который заменяется при переполнении/новом запуске.

## Экспорт и история

В REPEATABLE READ выбирать только экспортируемые поля истории (не snapshot), заранее строить members-by-group. Для history/chart также выбирать только возвращаемые поля. HTTP/JSON format v2, порядок, Decimal и согласованность сохраняются. Потоковый экспорт пока не вводить: он требует отдельного согласования HTTP/Tauri/UI контракта; сначала измерить эффект projection и убрать лишние одновременные materializations.

## Риски и проверка

- Виртуализация сложнее пагинации: E2E обязаны покрыть последние элементы, resize, большие группы, фокус, меню и возврат из деталей; native WebView проверить отдельно.
- Полный snapshot остаётся O(N) по сети/памяти: отчёт явно показывает этот предел; server pagination потребует нового ADR, если согласованные пороги не проходят.
- Очистка старой диагностики необратима по новой политике: явно обозначать expired/limited; проверить сохранность целей, точных счётчиков и истории, отказ миграции и исторические ревизии только на disposable DB.
- Неполный охват logs: перечислить все actual spawn paths Rust/Python; проверить stdout+stderr, без EOF, disk error, continuous truncation и process recovery.
- Не менять ограничения и транспорт Ozon. Проверить CLI imports, queued/direct collect и numeric без БД.

## Приёмка

ADR остаётся Proposed до явного одобрения владельцем. После реализации отдельная приёмка по vibe-flow; затем обновление документов, sync/archive и commit без push.
