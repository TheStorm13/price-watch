# ADR 0008: AliExpress SKU и общий Chrome-сеанс

- Статус: Accepted — план и реализация приняты 2026-10-26.
- Дата: 2026-10-26.
- OpenSpec: [add-aliexpress-connector](../../openspec/changes/archive/2026-10-26-add-aliexpress-connector/proposal.md).

## Контекст

Пользователь выбрал конкретный SKU и одну цену по приоритету купонная →
акционная → обычная. AliExpress productData принимает productId и sku_id,
возвращает оба идентификатора и набор вариантов. Текущий ProductRef содержит
строковый external_id; уникальность карточек — marketplace/external_id.
API/UI допускают только цифровой ID. Сбор передаёт коннектору только external_id,
поэтому извлекать идентичность из редактируемого URL при каждом сборе нельзя.

Chrome lifecycle находится внутри Ozon. CollectionService открывает сессии
всех площадок до запуска запросов: два самостоятельных Chrome с одним профилем
конфликтовали бы. Live probe с внешним Chrome/CDP подтвердил JSON fetch с
главной AliExpress после ручной CAPTCHA; независимый HTTP-транспорт не проверен.

## Варианты идентичности

1. Только productId: не различает варианты и допускает смену комплектации.
2. Только skuId, productId брать из URL: делает обязательную идентичность
   зависимой от отображаемого редактируемого поля; standalone lookup неполон.
3. Новая отдельная колонка SKU и третья часть ProductRef: распространяет
   AliExpress-специфику на модели всех площадок, ключи и transfer.
4. Канонический external_id `productId:skuId`: выражает полную идентичность
   в существующем строковом ключе и сохраняет общий интерфейс коннектора.

Предлагается вариант 4. UI показывает два понятных поля и разбирает полную
ссылку aliexpress.ru с sku_id. API/CLI/transfer используют пару. Числовой
product-only AliExpress больше не является допустимым новым вводом. Ozon
сохраняет цифровой ID. URL должен соответствовать паре, но не определяет её.

## Варианты браузерного lifecycle

1. Отдельный профиль для AliExpress: дублирует настройки/авторизацию и
   требует второго управляемого браузера вместо существующего общего профиля.
2. Последовательно запускать Chrome для каждой площадки: мешает общему
   параллельному сбору и привязывает orchestration к площадкам.
3. Наследовать AliExpress от AsyncOzonClient или копировать lifecycle:
   сохраняет зависимость нового адаптера от Ozon либо дублирует владение.
4. Выделить общий Chrome-сеанс и передавать его обоим адаптерам:
   один процесс/профиль, раздельные страницы и независимые JSON-транспорты.

Предлагается вариант 4. Сеанс создаёт фабрика текущего запуска; он имеет
согласованное acquire/release и закрывается после последнего потребителя.
Standalone Ozon/Ali создают собственный экземпляр такого же сеанса. Глобальный
singleton не нужен. Общий lock ручных проверок не сериализует обычные fetch.
Ozon composer/parser/mapper и его параметры запросов сохраняются.

## Цена и данные

Из строки выбранного skuInfo.priceList берётся только одна сумма:
priceWithCoupon.amount → activityAmount → amount. isCouponAssigned=false
не влияет на выбор. Decimal вычисляется из cents, не из float/value/formatted.
RUB проверяется явно. Отсутствие/null допускает следующий источник; повреждение
присутствующей суммы — ошибка схемы. Таможня/доставка не прибавляются.
При доказанном отсутствии выбранного SKU цена null по общему контракту.
Сырой ответ может содержать несколько сумм, но нормализованный товар, snapshot
и история не добавляют дополнительные цены или их копии в extensions.

Необязательные поля берутся из productData, без открытия карточек ради
дополнительного обогащения. При отсутствии имени продавца seller=null;
sellerId можно оставить как специфический идентификатор без выдуманного имени.

## Переход и последствия

Нужны изменения AliExpress-валидации, UI, импорта и фабрик сборки коннекторов,
а также перенос profile_lifecycle с обновлением Rust-вызова и всех Python
импортов. Старый Ozon-owned lifecycle после переноса удаляется, shim не остаётся.
Общий JSON 2.0 и transfer v2 уже допускают строковые ключи: версия не меняется.

Data-only Alembic migration сначала проверяет все AliExpress-записи. Пара
вычисляется только из валидной сохранённой ссылки с совпадающим productId и
однозначным sku_id. Карточки без определённого SKU пропускаются без изменений
и не блокируют миграцию. При сборе они получают ошибку «Не указан SKU» до
товарного запроса; поля карточки, updated_at, цена и история не меняются,
остальные цели продолжают обрабатываться. Конфликт преобразуемых идентичностей
по-прежнему останавливает миграцию до изменений с диагностикой.
Никакого присвоения «первого» SKU, удаления карточек, объединения историй или
переписывания исторических snapshot JSON. Локальные ID и FK остаются прежними.
Старые exports с product-only AliExpress требуют явной подготовки; скрытой
импортной совместимости с product-only режимом не добавляется.

Миграции и lifecycle проверяются на disposable данных/профилях. Live цены и
CAPTCHA остаются внешней зависимостью; одно успешное исследование не доказывает
работу всех товаров, регионов и режимов. План одобрен пользователем до реализации, проверенный результат принят
2026-10-26: «Да, сделай коммиты».
