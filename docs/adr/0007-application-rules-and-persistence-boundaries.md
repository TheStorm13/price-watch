# ADR 0007: Правила приложения и явные границы хранения

- Статус: **Accepted**. План и реализация приняты пользователем 2026-10-26.
- Дата: 2026-10-26.
- Change: [separate-business-rules-from-postgres](../../openspec/changes/archive/2026-10-26-separate-business-rules-from-postgres/proposal.md).
- Подробности: [design](../../openspec/changes/archive/2026-10-26-separate-business-rules-from-postgres/design.md).

## Контекст

ARCH-03: PostgreSQL-адаптеры определяют выгодность, представителя и расписание; facade с множественным наследованием скрывает связи SQL-областей. API, worker и challenge handler знают concrete storage. Нужно проверять правила без БД и понимать транзакционные границы при изменении кода.

ADR 0004 закрепляет lease, атомарный результат цели и единый снимок каталога; ADR 0005 — общий MarketplaceCard, локальный TrackedCard и Decimal. Эти решения сохраняются. Этот ADR предлагает устройство кода, а не новые продуктовые правила.

## Решение

1. Чистые domain rules для выгодности, представителя, шестичасового срока и устаревания. Явные Decimal-входы и время; ни SQL, ни HTTP, ни чтения окружения внутри правил.
2. CatalogService в application собирает cards/groups/deals из типизированного CatalogInputs. PostgreSQL reader материализует общие данные в одном REPEATABLE READ снимке, не передавая ORM наружу. SQL-агрегации остаются в PostgreSQL.
3. Политика расписания вызывается адаптером внутри транзакции под прежней advisory lock. Нельзя отделять решение от защищённого чтения и создания запуска. Clock и конфигурация передаются явно.
4. Порты по потребителям вместо универсального repository Protocol. Один RunRepository реализует несколько нужных портов; adapters создаются в API/CLI composition roots, concrete storage не импортируется рабочими application-компонентами.
5. Удаление multiple-inheritance facade: самостоятельные adapters и явные SQL helpers. `save_result` принадлежит RunRepository и сохраняет всю транзакцию цели/карточки/истории/прогресса с lease. HistoryRepository отвечает за чтение. Общие ошибки находятся вне инфраструктуры.

## Альтернативы

- Только переименовать фасад или расширить общий Protocol: сохраняет скрытые зависимости и смешение обязанностей.
- Только вынести функции правил, оставив фасад: меньше изменений, но не даёт явных контрактов и владельца writer.
- Перенести SQL и transaction management в application: раскрывает инфраструктуру и увеличивает риск разорвать блокировки/атомарность.
- Ввести generic UoW/DI framework и сервис на каждый метод: больше механизмов без самостоятельной потребности.
- Вычислять каталог последовательными запросами application: без общего снимка нарушает согласованность; с UoW добавляет ненужную сложность.

Выбрана композиция небольших адаптеров с чистыми правилами и сохранением атомарных операций внутри PostgreSQL.

## Последствия

Больше явно описанных типов, но исчезают скрытые cross-mixin вызовы. Внутренние Python API/imports меняются полностью, включая tests/scripts; старые wrappers не сохраняются. HTTP, CLI-возможности, JSON, таблицы и данные остаются прежними, миграций нет. Продолжают работать queued API/worker, direct collect и numeric JSON без БД.

Текущие фильтры/метрики групп, средние, смысл дат, ограничения Ozon и desktop lifecycle не пересматриваются. Проверки поведения, конкурентности и performance обязательны по design; результат без них не считается подтверждённым.
