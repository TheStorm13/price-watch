# Design

## Context

См. proposal.md. Текущий `wildberries/runtime.js` отбрасывает данные изображения,
а `WildberriesMapper.to_card` не заполняет `image_url`. `ProductVariant`,
`CardVariantRecord` и `TrackedVariant` не содержат фото. Товар имеет своё поле
фото; `RunRepository.save_result` обновляет его для главного варианта.
Обнаружение вариантов и неизменная цена имеют ранние возвраты: метаданные нужно
сохранять до них. AliExpress mapper читает общую gallery, но не фото свойств.

## Goals / Non-Goals

Цель — провести фото варианта через существующие границы коннектора, сохранения,
API, transfer и UI. Охват — текущие обнаруживаемые варианты; объединение других
артикулов WB по цветам и изменение правил обнаружения в задачу не входят.
Технические идентификаторы и параметры URL сохраняют свой смысл.

## Decisions

1. Добавить nullable `image_url` варианту в общем контракте и таблице
   `card_variants`, `imageUrl` в UI. Отдельная колонка позволяет читать актуальное
   фото без разбора истории. Альтернатива — извлечение из snapshot — не покрывает
   discovery и изменение фото при неизменной цене. Это расширение существующих
   моделей в текущей архитектуре; новый архитектурный паттерн и ADR не нужны.
2. WB получает главное фото через механизм витрины в существующем runtime.
   Точный helper и его фактические аргументы проверяются наблюдением текущей
   витрины перед реализацией; их нельзя придумывать или заменять статической
   таблицей basket-хостов. Получение необязательно, ограничено по времени.
   Размеры одного nmId используют общее фото. У AliExpress сопоставить фото
   свойств с точной комбинацией варианта; общую gallery использовать, только
   если своего фото нет. Остальные адаптеры заполняют поле по доступным данным.
3. Сохранять URL при discovery и точном сборе до проверки изменения цены.
   Пустой результат фото не стирает сохранённое. Отдельные фото вариантов
   не изменяются при выборе главного; товарное фото обновляется согласованно
   с текущим главным и не заменяется снимком соседнего варианта.
4. Общий компонент миниатюры принимает необходимые данные изображения и подписи,
   чтобы каталог и список вариантов одинаково обрабатывали ошибки загрузки.
   Миниатюры лениво загружаются. Сохранить цветовые маркеры графика и его легенду.
5. Расширить API, transfer и demo API вместе. Существующие экспорты без нового
   поля импортируются с пустым фото варианта; сохранить их данные — требование
   безопасного переноса, отдельный старый механизм хранения не сохраняется.
   Номер схемы JSON/transfer менять только если это требует действующий контракт,
   без введения параллельного формата или endpoint.

## Risks / Trade-offs

- Витрина WB меняет внутренние helper → подтвердить текущий источник фото,
  сохранить синтетический браузерный регрессионный тест и сделать live-проверку
  без БД; ограничение live-проверки явно указать, если WB блокирует доступ.
- Фото свойств AliExpress может отсутствовать → использовать общее фото товара,
  не брать фото соседней комбинации; покрыть сопоставление тестами.
- Старое товарное фото нельзя однозначно распределить по всем вариантам →
  не копировать его произвольно в миграции; новые поля заполняет повторный сбор.
- Обновление фото может затронуть историю → проверить неизменную цену,
  частичный сбой, повтор и экспорт/импорт на одноразовой тестовой БД.

## Migration Plan

Добавить nullable-колонку без изменения идентичностей и исторических JSON.
Обновить коннекторы, сохранение, API/transfer и frontend одним переходом.
Фото существующих вариантов появляются после повторного сбора. Миграцию
проверять только на отдельной `TEST_DATABASE_URL`. Откат с удалением данных и
переписывание пользовательской БД не входят в реализацию.

Затронуты queued desktop/API/worker, расписание/retry через общее сохранение,
`main.py collect` и database-free коннектор. Числовой Ozon без `DATABASE_URL`
и оба CLI-импорта должны продолжить работать. Demo проверяет UI, но не live.
