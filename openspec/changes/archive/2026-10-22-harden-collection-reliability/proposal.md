# Proposal

## Why

Блок REL-01–REL-05 закрывает зависшие CLI-запуски, неполный повтор после
аварии, запись устаревшим исполнителем, потерю уведомления после ошибки
запроса и несогласованный каталог во время сбора. Эти ошибки затрагивают
общий путь сохранения результатов, поэтому требуют согласованного изменения
исполнения, хранения и UI.

## What Changes

- Общий механизм владения запуском и heartbeat для queued worker и прямого
  `main.py collect`; замороженные цели фиксируются до браузерных операций.
- Отдельный результат каждой цели: pending, succeeded, failed, unknown для
  достоверно не классифицируемых сохранённых данных. Сохранение наблюдения,
  результата и счётчиков выполняется атомарно, в том числе при неизменной цене.
- Повтор включает ошибки и незавершённые цели; проверка владельца защищает
  все записи исполнителя, включая историю. Потерявший владение исполнитель
  прекращает работу без изменения итогового состояния запуска.
- Доступность повтора отражается в API и UI независимо от наличия cardId
  в диагностике общей ошибки. Сохраняется один повтор на исходный запуск.
- Обработка уведомлений переживает временную ошибку запроса и закрытие
  панели; успешная обработка фиксируется после получения данных.
- Единый `GET /api/catalog` возвращает cards, groups и deals из одного
  снимка БД; UI обновляет каталог одной записью кеша. Общие исходные данные
  читаются однократно и используются всеми проекциями.
- **BREAKING:** удалить заменённые GET `/api/cards`, `/api/groups`,
  `/api/cards/deals`, старую загрузку трёх списков, дублирующие проекции и
  tokenless-пути записи исполнителя. Перевести все потребители и mock API
  в этом change, без адаптеров и fallback на старое решение.
- **BREAKING:** перенести сохранённые цели из `target_card_ids` в таблицу
  результатов целей и удалить заменённый столбец. Цены, карточки, группы,
  исходные ошибки и история запусков сохраняются.

## Capabilities

### New Capabilities

- `collection-run-execution`: владение запуском, heartbeat, атомарные
  результаты целей, восстановление и повтор после аварии.
- `catalog-snapshot`: согласованный ответ каталога и его атомарная замена в
  UI без существенной регрессии производительности.
- `deal-notifications`: повтор получения данных для уведомлений и защита от
  повторного показа после успешной обработки.

### Modified Capabilities

- `scheduled-collection`: устаревший прямой CLI-запуск перестаёт бессрочно
  блокировать автоматический сбор; шестичасовой отсчёт остаётся прежним.

## Impact

- Backend: application collection service и общий runner, worker/challenge,
  CLI, доменные модели и persistence port, PostgreSQL repositories/models,
  новая Alembic-ревизия после `0013_deals_enabled`, API schemas/routes.
- Frontend: API client/types/mock, queries и invalidation, CardsPage,
  CollectionProvider, ActiveCollectionPanel, bulk/import/group consumers.
  Rust IPC, профиль Chrome и лимит пяти вкладок не перепроектируются.
- Пользователь выбрал единый снимок и полный переход без обратной
  совместимости. Старые процессы API/worker/CLI должны быть остановлены
  перед миграцией; смешанные версии не поддерживаются.
- Исторические успехи без новой точки нельзя восстановить по price_history.
  Миграция отмечает неопределённость, не выдумывает успехи и не подменяет
  старые цели текущим каталогом. Известные цели сохраняются в новой модели.
- Новых внешних зависимостей не требуется. Proposed ADR фиксирует выбор
  модели исполнения, данных и согласованного чтения.
- Приёмка: CLI/worker восстанавливаются после аварии; повтор обрабатывает
  остаток; устаревший владелец не пишет историю и состояние; временный сбой
  загрузки не теряет уведомление; карточки и группы согласованы с deals.
  Основные сценарии групп, истории, импорта и numeric JSON mode сохраняются.
- Производительность — обязательная проверка: baseline до изменений,
  одинаковые синтетические fixtures и нагрузка после; p95 полной загрузки
  каталога не выше max(1.20 × baseline, baseline + 50 мс), число SQL-запросов
  не зависит от числа карточек, без повторной агрегации истории. Превышение
  порога требует исправления или нового согласования плана.
- Проверки БД выполняются только на отдельной disposable TEST_DATABASE_URL;
  миграция пользовательской базы и реальный сбор Ozon в плановую фазу не входят.
