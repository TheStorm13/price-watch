# Design

## Context

Мотивация и область REL-01–REL-05 описаны в proposal.md. Исходные точки:
`CollectionService._collect_cards`, `CollectionWorker.run_once`,
`RunRepository`, `HistoryRepository.save_observation`,
`GroupRepository.list_groups`, `CollectionProvider` и `CardsPage`.

Сейчас CLI создаёт running без worker_id; worker отдельно обслуживает
heartbeat. История хранит изменения состояния, поэтому отсутствие новой
точки не доказывает отсутствие успешного сбора. Прогресс и история пишутся
разными транзакциями. Источник повтора — cardId в массиве ошибок.
UI дополнительно скрывает кнопку повтора при одной общей ошибке.

Пользователь выбрал единый снимок каталога и требует полного перехода на
новые решения без обратной совместимости. AGENTS.md обновлён отдельно по
прямому запросу; approval реализации всего блока ещё не получен.

## Goals / Non-Goals

**Goals:** один механизм исполнения CLI/worker, атомарная фиксация результатов,
защита от устаревших записей, достоверный состав повтора, повтор уведомлений
и согласованный каталог с обязательным сравнением производительности.

**Non-Goals:** перепроектирование Rust runtime/Chrome profile, изменение
шестичасового расписания и лимита пяти вкладок, новые коннекторы, новые
критерии выгодности, пагинация/виртуализация, отдельная таблица диагностических
ошибок, системные уведомления или доставка исторических скидок.

## Decisions

### 1. Общий исполнитель и владение каждой попыткой

В application добавить общий runner исполнения. Worker забирает queued,
прямой CLI атомарно создаёт running с выбранными целями; оба получают
`RunLease(run_id, owner_token)` и проходят один lifecycle: heartbeat,
создание коннекторов, исполнение, завершение, cleanup. CLI остаётся прямым
и не начинает ожидать очередь другого worker. Фабрика коннекторов здесь
переводится на новый вызов, но её общее выделение остаётся ARCH-04.

owner_token — новый случайный идентификатор на каждое получение владения,
хранится в существующем worker_id, а не только hostname/PID процесса.
Интервал heartbeat 5 секунд и порог RUN_STALE_SECONDS сохраняются.
Восстановление вызывается перед расписанием worker и перед созданием
прямого запуска, используя один общий алгоритм; standalone CLI способен
убрать протухшую блокировку без отдельного worker.

Все записи исполнителя требуют lease и активного состояния. Транзакции
блокируют строку запуска и проверяют owner_token; затем блокируют цель и
карточку в одинаковом порядке. Восстановление блокирует ту же строку запуска.
Тем самым запись либо полностью произошла до отзыва владения, либо полностью
отклонена после. Это относится к снимкам, метаданным карточки, прогрессу,
ошибкам, waiting, heartbeat и finish, а не только к финальному статусу.

touch возвращает признак владения; отсутствие владения отменяет общий runner
и его fetch-задачи. Специальная ошибка потери владения не оборачивается в
ошибку карточки и не запускает повторную попытку finish с прежним токеном.
Heartbeat-сбой связи логируется, повторяется с прежней частотой, а записи
всё равно защищены транзакционной проверкой. Закрытие коннекторов идёт в
finally, как сейчас. Cancellation после KeyboardInterrupt завершает
принадлежащий запуск при доступной БД; при недоступной БД его восстановит
проверка устаревания.

`continue_run` остаётся пользовательской командой под API-аутентификацией,
а не записью исполнителя. Она блокирует строку и допускает только
waiting_for_user с действующим владельцем и актуальным heartbeat. Она не
может оживить failed. DatabaseChallengeHandler получает lease и проверяет
владение при переводе в waiting и ожидании продолжения.

Альтернативы: только исправить heartbeat CLI — не закрывает REL-02/03;
превратить CLI в постановщика очереди — меняет прямой режим и требует
отдельного worker; общая блокировка на весь браузерный запрос — держит
долгую транзакцию. Выбран короткий контроль владения на каждой записи.

### 2. Единственная модель результатов целей

Добавить `collection_run_targets` с PK (run_id, card_id), порядком цели и
status pending/succeeded/failed/unknown. run_id ссылается на collection_runs
с CASCADE. card_id хранит исходный ID без каскадного удаления результата при
удалении карточки: исторический состав сохраняется. Для новых запусков
все цели создаются pending одной транзакцией с запуском, порядок и total_count
фиксируются тогда же. Индекс card_id/run_id поддерживает проверку участия
в активном запуске. Проверка существования карточки выполняется при создании
под теми же блокировками, что и запрет удаления.

Успешная фиксация результата — одна транзакция: проверка lease; обновление
карточки и, при изменении состояния, истории; pending → succeeded;
увеличение success_count. При неизменной цене цель всё равно succeeded.
Ошибка конкретной цели атомарно фиксирует failed, диагностику и failure_count.
Повторный результат уже завершённой цели — идемпотентный no-op после проверки
владения, а не второе увеличение счётчика. Счётчики обновляются в БД, а не
заменяются локальными абсолютными значениями из параллельных задач.

Сохранение снимка становится внутренней частью операции результата;
tokenless-вход исполнителя и отдельное обновление прогресса после успешной
записи удаляются. Тестовые fixtures и импорт пишут через свои явные операции,
а не через обход lease в production-методе. Ошибки запуска по-прежнему
хранятся в текущем JSONB: нормализация диагностик — PERF-03.

При общей аварии pending остаются pending, известные результаты не
переклассифицируются. Счётчики показывают завершённые цели, поэтому failed
может иметь success_count + failure_count < total_count. Успешное завершение
нового запуска допустимо только после обработки всех его целей.

`create_retry_run` использует единый запрос целей failed/pending/unknown,
фильтрует существующие поддерживаемые карточки и создаёт новый frozen набор.
Уникальный retry_of_run_id и advisory lock сохраняются. Новый повтор не
считается полным запуском расписания. Последующие ошибки повторяют уже
повторный запуск, а не создают второго ребёнка исходного.

RunResponse получает retryableCount и retryScopeIncomplete. Они отражают
тот же отбор, что и POST retry, включая уже созданного ребёнка; расчёт списка
запусков не должен создавать запрос на каждый элемент. UI показывает
«Повторить ошибки и оставшиеся» по числу целей, а не cardId в диагностике.
Удаление карточки между чтением и POST повторно проверяется сервером.

Альтернативы: считать успех по price_history — теряются неизменные цены;
хранить только массив успешных ID в JSONB — усложняет идемпотентность и
продолжает перезапись растущего документа; повторять весь новый запуск —
повторно читает доказанные успехи. Выбрана таблица целей.

### 3. Восстановление и данные прежних запусков

Восстановление выбирает running/waiting_for_user по
coalesce(heartbeat_at, started_at) независимо от наличия owner_token.
Устаревший запуск получает failed, finished_at и общую диагностику;
owner_token снимается. Живой CLI и интерактивное ожидание поддерживают
heartbeat. Запись результата и восстановление сериализованы блокировкой
строки запуска; новый автоматический сбор проверяется после восстановления.
Расписание по-прежнему отсчитывается от начала последнего полного запуска,
включая failed. Потеря процесса сама по себе не создаёт автоматический retry.

Миграция переносит в таблицу целей объединение известных ID: frozen массив,
requested_card_id, индивидуальные ошибки и наблюдения, связанные с запуском.
Источники дедуплицируются; порядок массива сохраняется, остальные ID идут
стабильно. Ошибка конкретной цели даёт failed; прочие результаты исторических
терминальных запусков консервативно unknown. История не используется для
выдумывания полной картины успехов. Исторические агрегатные счётчики и ошибки
сохраняются, даже если распределить их по целям уже невозможно.

В collection_runs добавить факт `targets_complete`: true при достоверном
frozen наборе, согласованном с total_count, либо достоверном одиночном наборе;
иначе false. Новые запуски всегда true. Это качество сохранённых данных,
не ветка совместимости с предыдущей реализацией. Старые queued с полным
набором становятся pending; queued с неполным набором при захвате завершаются
failed с диагностикой до браузерного I/O. Исторический retry берёт известные
failed/pending/unknown и явно предупреждает о targets_complete=false.
Неизвестные ID не подменяются текущим каталогом.

После переноса удалить target_card_ids и все runtime-обращения к массиву.
Модели, порт, CLI, worker, tests и проверка активных целей используют только
новую таблицу. Дублирующей старой схемы и веток исторического отбора нет.

### 4. Один снимок каталога и общий кеш

Новый GET /api/catalog: `{ cards: CardResponse[], groups: GroupResponse[],
deals: DealResponse[] }`. Транзакция READ ONLY / REPEATABLE READ открывается
до первого запроса. Общий loader читает группы, текущие карточки с последней
точкой (включая collection_run_id) и метрики истории; из этих общих данных
строит три проекции. Полная агрегация исторических метрик выполняется один
раз. Для загрузки целевой верхний предел — 5 SQL-запросов, без N+1.

Правила представителя группы, all-time minimum, средних предшествующих
дневных цен, наличия, deals_enabled, сортировки и дат не меняются. Текущие
дублирующие SQL/построители deals и group projection заменяются общими
проекциями; полезные низкоуровневые запросы сохраняются при наличии реального
потребителя. Независимые детали/история карточки и мутации остаются отдельными
операциями продукта.

Frontend получает один useCatalog/query key. CardsPage читает единый объект;
мутации не патчат отдельные массивы кеша раздельно. Invalidation переводятся
в queries, CollectionProvider, bulk actions, import/export и сохранении групп.
При refetch сохраняется предыдущий целый снимок, новый публикуется целиком.
После смены API-токена обновляется общий кеш существующим bootstrap-механизмом.
Mock строит один ответ синхронно из одного состояния и лишь затем применяет
искусственную задержку; он не вызывает три independently delayed метода.

Все потребители чтения списков, включая свежую проверку группы перед bulk
действием, переводятся на каталог. Удаляются старые GET `/api/cards`,
`/api/groups`, `/api/cards/deals`, listCards/listGroups/listDeals в HTTP/mock
клиенте и отдельные list-query hooks. POST/PATCH/DELETE, чтение одной
карточки, history/chart и export/import сохраняют свои назначения.
Запросы старых списков больше не получают прежние данные; точный код
отказа может зависеть от соседних маршрутов, адаптеров не добавлять.

Альтернативы: REPEATABLE READ отдельно на три endpoint — не даёт единого
состояния экрана; revision + согласование трёх ответов — требует повторов и
нового протокола; блокировка worker на время чтения — мешает сбору.
Выбран один короткий снимок без нового кеширующего сервиса.

### 5. Уведомления независимо от панели

Вынести обработку в небольшой feature hook/service, живущий столько же,
сколько CollectionProvider, с очередью ожидающих terminal run IDs независимо
от runId видимой панели. Сохранять очередь, watermark обработанных запусков
и последние уведомлённые цены единым versioned localStorage-документом.
Однократно перенести известные значения старых ключей и удалить старые ключи;
runtime не читает оба формата. Повреждённое хранилище не должно ломать UI.

После обнаружения eligible terminal-состояния добавлять работу в очередь.
Обрабатывать последовательно, получать свежий каталог через общий query
loader, с запросом, начавшимся после обнаружения завершения. Старый кеш,
полученный до завершения сбора, не считается успешной проверкой. Перекрывающиеся
обновления должны использовать общий in-flight запрос там, где он достаточно
свежий. Ошибка не меняет watermark и цены, повтор — с увеличивающейся
задержкой до 30 секунд; никаких tight loops. Автозакрытие панели и появление
следующего запуска не удаляют ожидающую работу. После перезапуска UI очередь
возобновляется. При успешном ответе удалить только обработанные элементы,
сохранив добавленные во время запроса, и согласованно записать цены/watermark.

Сохраняется существующий отбор: актуальный deal, lastCollectionRunId нужного
запуска, цена отличается от предыдущей. Это не доставка исторических скидок:
если к повторной загрузке предложение исчезло, уведомлять уже не о чем.
Начальное обнаружение старых запусков не расширяется в рассылку всей истории.
Гарантия касается сетевых ошибок и повторного состояния, а не exactly-once
показа при аварийном закрытии браузера между записью localStorage и рендером.

### 6. Измеримая защита производительности

До изменения application code сохранить baseline на исходной реализации
и синтетических данных отдельной БД. Фикстуры: S — 100 карточек/10 000 точек,
M — 1 000/100 000, L — 5 000/500 000; одинаковые группы, наличие и доля deals.
Сравнивать время полной параллельной загрузки прежних трёх списков с одним
каталогом, включая HTTP-сериализацию. На каждую комбинацию: 5 прогревочных
и 30 измеряемых загрузок; без writer и с одинаковым темпом синтетической
записи результатов в пять конкурентных задач, без Ozon.

Записать окружение, объём ответа, p50/p95, количество/время SQL, peak RSS
API, время до целого каталога в UI и скорость фиксации результатов. Нагрузку
writer и seed зафиксировать в harness для воспроизведения; baseline снимается
до удаления старых путей, сами старые пути ради benchmark не сохраняются.

Обязательный порог для каждого набора/режима:
`new_p95 <= max(1.20 * old_p95, old_p95 + 50ms)`.
Число SQL не зависит от числа карточек, цель не более пяти. Рост peak RSS
более max(20%, 25 MiB) или замедление фиксации результатов более 20% —
дополнительный блокер для разбора и повторного согласования, даже при
прошедшем HTTP-пороге. UI-профиль не должен показывать публикацию смешанных
снимков или новый длинный синхронный этап преобразования данных.

Порог 20%/50 мс — предложенный критерий Gate 1, а не уже измеренный результат.
Если стенд не позволяет снять baseline/after, задача не считается прошедшей
проверку производительности; ограничение представить на приёмку явно.

## Risks / Trade-offs

- Больше данных результатов целей → индексированные короткие операции;
  не держать транзакцию во время Chrome I/O, измерить write-throughput.
- Восстановление по heartbeat при длительном зависании → после отзыва
  владения прежний процесс не пишет данные; heartbeat продолжает работать
  во время интерактивного ожидания.
- Дедлоки при новом порядке блокировок → зафиксировать run → target → card,
  проверить гонки с удалением, retry, импортом и восстановлением реальной БД.
- Исторический состав неполон → unknown/targets_complete и предупреждение;
  не расширять область старого запуска текущими карточками.
- Единый ответ крупнее отдельного списка → UI уже загружает все три;
  повторное использование общих проекций, ограничение SQL и обязательные замеры.
- Конкурентные старые процессы не знают новую схему → полная остановка перед
  миграцией; смешанные версии не поддерживаются.

## Migration Plan

1. Gate 1: одобрить этот план и Proposed ADR. Снять baseline до изменения кода.
2. Создать новую Alembic-ревизию после 0013: таблица целей, constraints/indexes,
   targets_complete; перенести известные ID и классифицировать неопределённость.
   Проверить сохранность всех скопированных ID до удаления target_card_ids.
3. Перевести все runtime-потребители на новую модель и единый каталог;
   удалить заменённые пути, тестовые обходы и старый формат notification state.
4. Проверить upgrade на disposable базе с предыдущей схемой и new-install
   с нуля. Сравнить карточки, price_history, ошибки и историю запусков до/после.
5. Перед обновлением реального окружения остановить API, workers и direct CLI;
   сохранить резервную копию по существующему порядку, применить миграцию и
   запускать только новую версию. Эта плановая фаза не применяет её к данным.
6. Переход forward-only: старый runtime и схемные fallback не сохраняются.
   Downgrade новой ревизии явно не поддерживает возвращение старой модели;
   ошибки устранять forward-миграцией. Транзакционная отмена неуспешного
   upgrade и резервные копии остаются защитой данных, не режимом совместимости.
7. После реализации — тесты, performance after, diff/risk review и Gate 2
   (приёмка). Только затем финализировать затронутые документы/ADR/backlog,
   sync specs, archive и создать коммит(ы). Не push/merge.
