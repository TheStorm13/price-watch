# Design

## Context

См. `proposal.md`. Текущий backend и mock вычисляют два минимума группы отдельно. Каталог фильтрует карточки до построения групп, у группы большинство ключей сортировки отсутствует, а плитка выносит группы вперёд. Эти места уже проверены в текущем source через CodeGraph; Repowise указал риск регрессий `CardsPage` и незавершённые изменения рабочего дерева.

Уточнение пользователя заменяет ранее предложенную агрегацию: цена — минимум среди карточек, остальные показатели — значения именно этой минимальной карточки. Новая дневная база, групповые средние и максимальные даты больше не нужны.

## Goals / Non-Goals

**Goals:** группа — объект общего каталога с единым источником товарных данных, общими фильтрами и сортировкой, собственными ID/названием и вложенными карточками.

**Non-Goals:** отдельная история группы, новые правила выгодности карточек, миграции, срок годности наблюдений, переключатель группировки. Архитектурного изменения нет, ADR не требуется.

## Decisions

### Выбор представителя

Выбор выполняется до любых пользовательских фильтров по полному составу группы. Среди карточек с известной текущей ценой выбрать минимум `(currentPrice, id)`; ноль — известная цена. По буквальному уточнению пользователя дополнительного ограничения `in_stock` нет: наличие является полем выбранной карточки. Используется текущая цена последнего состояния, а не последняя историческая цена в наличии.

Если известных цен нет, представитель — участник с меньшим ID: цена остаётся null, остальные поля берутся из его сохранённого состояния. Пустая группа не имеет представителя. Эти граничные решения явно вынесены на согласование вместе с планом.

Альтернатива — выбирать из отфильтрованных карточек — отклонена: смена фильтра меняла бы сам объект, его цену и показатели. Суммирование/усреднение полей других участников противоречит уточнению пользователя.

### Поля и контракт

Группа сохраняет свои `id`, `name`, `tags`, `cardIds`. Добавить `representativeCardId` и `representativeCard` с обычной проекцией карточки. Прежние верхнеуровневые `currentPrice` и `minimumPrice` остаются для совместимости и равны соответствующим полям представителя. Нормализованный объект каталога получает все товарные поля из `representativeCard`:

| Поля | Источник |
| --- | --- |
| Текущая, минимальная, средняя цены | Представитель, без пересчёта по остальным карточкам |
| Выгода, участие в выгодных, выгодность, дни базы | Действующие карточечные показатели/правила представителя |
| Наличие, lastObservedAt, updatedAt | Представитель; не максимум дат группы |
| Маркетплейс, внешний ID, ссылка, изображение, товарные теги | Представитель |
| ID и отображаемое название группы, состав, редактируемые теги группы | Собственные данные группы |

Выгоду/дни базы/признак выгодности передать в проекции группы дополнительными полями, рассчитанными тем же правилом, что и для карточки; не менять карточечный endpoint ради группы. Все денежные сравнения backend делать до округления. Не вычислять метрики повторно в браузере на неполной истории.

Без представителя товарные поля и выгода null, участие/выгодность false, дни базы 0. Если представитель есть, но не имеет измерений, сохраняются его метаданные, nullable товарные значения и обычное правило показа даты: без lastObservedAt дата обновления не показывается. Участник без новых наблюдений не теряет прежние значения; повторный успешный сбор может обновить updatedAt без новой точки истории. Обновление другого участника не меняет даты группы, пока он не стал представителем.

### Выгодность и приоритет

Собственная выгодность и savings группы в точности совпадают с представителем. Участие в выгодных не влияет на выбор минимальной карточки. Если самый дешёвый участник исключён, группа также исключена по своему полю dealsEnabled; более дорогого включённого представителя не подбирать.

Исходное требование о приоритете участников сохраняется отдельно: `hasMemberDeals` истинен, когда любой участник проходит действующее карточечное правило. Общий флаг приоритета — выгодность представителя ИЛИ hasMemberDeals. Выгоду других участников не переносить в колонку группы и не использовать как её численное поле сортировки. Приоритет — единственное исключение, использующее весь состав, и он не меняет фильтры. При необходимости показать отдельную подпись «Есть выгодный товар внутри».

### Единый каталог и фильтры

Сначала построить объекты верхнего уровня: группы и отдельные карточки вне групп. Нормализовать поля карточки/группы, затем применить один набор фильтров и один компаратор. Никакого отбора членов с последующим решением о видимости родителя.

- Цена, минимум, средняя, выгода, наличие, дата, маркетплейс, dealsEnabled, внешний ID и товарные теги группы берутся у представителя.
- Название для показа/сортировки — собственное имя группы; поиск проверяет его и обычные поисковые поля представителя. Совпадение только у другого вложенного участника не делает группу подходящей.
- Фильтр «Выгодные» проверяет выгодность представителя. Выгодный более дорогой участник влияет на приоритет, но не заставляет группу проходить фильтр.
- Товарные фильтры тегов проверяют теги представителя; собственные редактируемые теги группы сохраняются как метаданные. Это явное изменение прежнего фильтра по тегам группы/любого участника.
- Если группа прошла фильтры, раскрытие показывает полный состав с собственными данными карточек; внутренние строки не подменяют верхнеуровневый объект. Массовый выбор и действия остаются карточечными, группу выбирать как карточку нельзя.
- Пустая группа доступна без ограничивающих товарных фильтров и по своему имени; товарные фильтры работают как с обычным объектом без данных.

Сначала положительный приоритет, затем выбранный ключ/направление. Внутри приоритета null всегда в конце. По умолчанию после приоритета сохранить смысл карточечного порядка: dealsEnabled, ранг наличия, выгода по убыванию, цена по возрастанию. Для равенства — стабильный ключ типа и ID. Список и плитка используют один массив без повторной перегруппировки. Внутри группы применять карточечный порядок отдельно.

### Реализация

Пакетно переиспользовать текущие overview, price metrics и результат карточечных deals; выбрать представителя и присоединить показатели, избегая запросов на каждого участника. Согласованность данных обеспечить единым запросом/снимком чтения для проекции. Новая групповая история не нужна.

Mock должен использовать согласованную историю и те же правила; текущие фиксированные средняя/выгодность карточки №1 не подходят для проверки произвольного представителя. Инвалидировать группы после сбора, изменения цены/участия, состава, импорта и удаления карточки.

## Risks / Trade-offs

- [Исторический минимум меняет смысл] → Явно описать и проверить: он принадлежит представителю, даже если у другого участника был меньший минимум.
- [Смена представителя меняет сразу все поля] → Обновлять проекцию целиком; тесты цены, дат, маркетплейса, выгодности и тегов при переключении.
- [Данные вложенного участника больше не определяют фильтр родителя] → Проверить противоположные свойства представителя и другого участника; раскрытие сохраняет полный состав.
- [Приоритет участников и фильтр выгодности различаются] → Не смешивать hasMemberDeals с собственной выгодностью, явно подписывать участниковую причину приоритета.
- [Равные/отсутствующие цены] → Стабильный ID исключает произвольное переключение между запросами.
- [Чужие текущие изменения] → Сверить diff перед реализацией, не откатывать существующие правки.

## Migration Plan

Миграции БД и формат transfer не меняются. Расширить backend/demo контракт представителем, затем подключить нормализованный каталог. Цена верхнего уровня и minimumPrice получают новую согласованную проекцию. Откат не требует восстановления данных. Проверить GET/POST/PUT групп, смену состава, импорт, удаление и сбор без новой точки. Пути desktop/API/worker collection, `main.py collect` и numeric Ozon JSON mode не меняются; проверить импорты обеих CLI без DATABASE_URL.
