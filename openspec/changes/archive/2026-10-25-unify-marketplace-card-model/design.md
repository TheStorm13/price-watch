# Design

## Context

Мотивация и границы изменения: [proposal.md](proposal.md).
Проверено текущее рабочее дерево поверх 9f3876d, включая уже существующий
переезд price_analyzer → price_watch. Предшествующие правки не принадлежат
этому change автоматически. CodeGraph отказывает в чтении изменённых файлов;
Repowise предупреждает об устаревшем графе. Критические связи проверены в коде.

Сейчас OzonConnector передаёт payload из RawMarketplaceResponse в OzonMapper,
который разбирает Ozon-структуры и сразу создаёт ProductSnapshot. В mapper
Decimal превращается в int/float, в HistoryRepository — обратно в Decimal.
API DTO используют float, UI — number. Старый ProductCardNormalizer переводит
ProductSnapshot в другую модель и обрезает цену через int. Числовой CLI уже
выводит ProductSnapshot, а не старый ProductCard.

Источники: marketplace_connector/{domain,serialization,connectors/ozon},
ozon_article_json, price_watch/domain/models.py, application/collection_service.py,
infrastructure/postgres/{repository_common,history_repository,models}.py,
api/schemas.py, frontend/src/{types/domain,utils/format}.ts.
Связанные требования: collection-run-execution, catalog-snapshot,
group-card-metrics, deal-selection. Их продуктовая семантика сохраняется.

## Goals / Non-Goals

**Goals:** единый товарный тип для всех коннекторов, отдельная локальная запись,
явная конвертация Ozon-данных, точные денежные пути и полный перевод потребителей.

**Non-Goals:** реальные коннекторы WB/AliExpress/Яндекс Маркета; мультивалютность;
новые правила выгодности, расписания или хранения истории; ARCH-03 из backlog;
блокировка профиля Chrome и переработка восстановления служб; переименования
RunExecutor, NativeServices, frontend background, npm/Rust-пакетов из отдельного
плана именования. Этот change использует текущее имя пакета price_watch.

## Decisions

### 1. Две роли и одна товарная модель

В marketplace_connector/domain/models.py ProductSnapshot заменяется
неизменяемым MarketplaceCard. Общий пакет не импортирует price_watch, ORM,
HTTP или код конкретной площадки. MarketplaceCard описывает полученное
состояние товара; отдельный дублирующий класс «снимка» не вводится.

| Роль / поле | Целевое представление |
| --- | --- |
| Идентичность товара | ProductRef(marketplace, external_id) |
| Название, URL, изображение | MarketplaceCard.title/url/image_url |
| Цена и наличие | MarketplaceCard.price: Decimal или None; Availability |
| Продавец, рейтинг, характеристики | Seller, Rating, Attribute без потери нынешних полей |
| Описание, варианты, расширения | description, ProductVariant, extensions как сейчас |
| Время получения | collected_at с часовым поясом |
| Версия JSON | 2.0 задаётся сериализатором; не бизнес-поле модели |
| Локальная запись | TrackedCard в price_watch/domain/models.py |
| ID, настройки, даты записи | TrackedCard.id/group_id/tags/deals_enabled/created_at/updated_at |
| Идентичность записи | TrackedCard.ref: ProductRef; ORM хранит прежние два столбца |
| Локальные отображаемые данные | TrackedCard.title/url/image_url с прежними правилами обновления |
| Каталог / детали | TrackedCardOverview вместо CardOverview; HTTP CardResponse, TS TrackedCardView |

Title в локальной записи сохраняет существующую семантику: заполняется из
товара только когда пуст, редактируется пользователем и не перезаписывается
каждым сбором. Не переименовывать его в title_override и не пытаться вывести
авторство старого значения. URL и изображение обновляются по прежним правилам.
Товарное название коннектора и локальное отображаемое название могут отличаться.

TrackedCardOverview содержит локальную запись и текущие цену/наличие/время
наблюдения. Не восстанавливать полный MarketplaceCard из истории при чтении
каждой строки каталога: существующий SQL выбирает нужные поля без загрузки
всех характеристик. HTTP остаётся плоской проекцией с прежними именами полей
и маршрутами; отличие денежного формата описано ниже. TS-имя TrackedCardView
отличает проекцию UI от общего результата коннектора без неиспользуемой копии
полной модели товара в frontend.

Альтернативы: один плоский тип смешивает жизненные циклы и необязательные
поля; сохранение трёх нынешних моделей оставляет дубли и потери данных.
Две роли выбраны пользователем 2026-10-25; полный план затем одобрен
до реализации. Реализация затем принята пользователем перед коммитами всех изменений.

### 2. Ответ площадки → специфическая модель → mapper → общий товар

В connectors/ozon/models.py определить OzonProductData и необходимые вложенные
Ozon-типы для фактически используемых данных. Они содержат SKU, heading,
cardPrice и признаки наличия Ozon, seller/review, gallery, characteristics,
aspects и SEO-данные, а также received_at и запрошенный external_id.
Не переносить сырой payload под новое имя единственным полем модели.
Не дублировать весь внешний API: моделируются только используемые части;
полный исходный текст доступен отдельно для raw.

В connectors/ozon/parser.py OzonProductParser декодирует ответ и строковые
widget JSON/SEO JSON, извлекает специфические данные и проверяет структуру.
Текущие helper разбора переносятся из mapper, а не копируются. OzonMapper
получает только OzonProductData и создаёт MarketplaceCard; методы to_snapshot
и разбор произвольного raw внутри mapper удаляются.

AsyncOzonClient остаётся транспортом. OzonConnector организует parser → mapper,
передавая исходный текст и полученное время без двойного декодирования.
RawMarketplaceResponse и transport payload заменить Ozon-специфическим ответом
с raw_text/external_id/received_at, если после перевода общий тип больше никому
не нужен. JSON числового raw-режима не декодировать/пересериализовывать ради вывода.

Сохранить: источник цены исключительно cardPrice, проверку SKU, распознавание
подтверждённого отсутствия, unknown для неоднозначного наличия, обработку строк
false, приоритет изображения gallery и идентичность вариантов. Общий коннектор
возвращает MarketplaceCard. Другие площадки получают собственные parser/model/mapper
при реализации; сейчас достаточно тестового второго коннектора с отличающимся
входным форматом для проверки общей границы.

### 3. Decimal от декодирования до JSON

В common domain добавить money.py: единая нормализация цены и сериализация
денежного Decimal. JSON с денежными литералами декодировать с parse_float=Decimal
на всех уровнях Ozon, включая строковые widgets и SEO; целые int переводить
в Decimal точно. Float/bool не являются допустимыми входами доменной цены.
Нечисловую, отрицательную, NaN/infinite цену отклонять; отсутствие поля допускает None.
Цена quantize(0.01, ROUND_HALF_UP), после округления < 10^12 — предел NUMERIC(14,2).
Out_of_stock сохраняет None. Финальную проверку выполняет общая модель,
HistoryRepository не делает повторный переход Decimal(str(float)).

Средние и savings остаются Decimal с точностью существующих вычислений
PostgreSQL. Не округлять их до сравнения выгодности и выбора порядка.
Показ округляется до двух знаков ROUND_HALF_UP. Новая финансовая арифметика
для рейтингов или мультивалютность не вводятся.

JSON цен: "199.90" / null, всегда два знака у цены наблюдения. Средние/выгода:
format(value, 'f') без экспоненты и без округления до двух знаков; исключить
избыточные завершающие нули, чтобы сравнение и уведомления не зависели от записи
одного числа. При форматировании целые цены можно показывать без копеек,
как сейчас. Decimal сериализуется явными правилами, не default=str для любого типа.

Обновить все price/currentPrice/minimumPrice/maximumPrice/averagePrice/savings
в Pydantic DTO и CLI, Python сериализатор товара и JSON Schema (включая image_url,
который сейчас выводится, но отсутствует в schema с additionalProperties=false).
Нормализованный товар schema_version 2.0. Экспорт/импорт v2 сохраняет структуру
и строковые цены; before-валидация отклоняет числовой ввод цены до Pydantic coercion.
Ранее принимавшийся числовой импорт становится явной ошибкой валидации.

Альтернативы: float только на API всё равно теряет точность; целые копейки
не выражают неокруглённые средние; JSON numeric Decimal потребует точного
нестандартного декодирования в JS. Строки однозначны и не требуют зависимости.

### 4. Frontend: точные строки и отдельная проекция графика

В types/domain.ts денежный тип DecimalString; CardResponse представляется
TrackedCardView с прежними плоскими полями. В utils/money.ts централизовать
проверку десятичной записи, сравнение и округление/форматирование. Сравнение
знаков, целой и дробной частей выполнять точно; для округления использовать
строки/BigInt, без реализации универсальной decimal-арифметики. IDs, даты,
рейтинги и счётчики остаются number. Внешняя decimal-библиотека не планируется:
денежные вычисления live-приложения остаются на сервере.

Перевести catalogItems, отображение каталога/групп/деталей, mock API и тестовые
данные. В PriceChart number используется только для координат; экстремумы,
сравнения и подписи опираются на исходные строки. Recharts tooltip получает
исходный point по payload, а не форматирует обратно числовое value.
Изменение счётчиков уведомлений не должно зависеть от различий "199.9"/"199.90".

Mock — отдельный потребитель: mockPriceMetrics.ts сейчас складывает и делит
цены, mockApi.ts вычисляет savings и статистику, сравнивает группы и объединяет
импорт. Перевести эти места на точные операции. Для тестового стенда использовать
ограниченные BigInt-операции над десятичными коэффициентами и рациональными
средними; округление при сериализации периодической средней — до 20 знаков
ROUND_HALF_UP. На fixtures с конечными средними сверять значения с backend,
включая дробные цены и импорт. Не переносить эти вычисления в live-клиент
и не оставлять float-ветку ради mock. Это не обещает побитового совпадения
последних знаков периодических средних с PostgreSQL; точность live задаёт сервер.

LocalStorage уведомлений перевести на следующую версию однократной миграцией:
перенести конечные прежние number в канонические цены, сохранить pending IDs
и processed watermark, не использовать старый формат в штатной обработке.
Если цена повреждена, убрать только её; корректная очередь остаётся.

### 5. PostgreSQL сохраняет структуру и транзакции

TrackedCard не требует новой таблицы. ORM MarketplaceCardRecord сохраняет
имя и колонки; _card меняется на _tracked_card и строит ref из существующих
marketplace/external_id. Потребители TrackedCard используют ref; общий товар
не получает DB ID. Сохраняются индексы и FK групп, целей запусков и истории.

save_result(lease, tracked_card, product) по-прежнему в одной транзакции
проверяет run/target/card, сопоставляет ref, обновляет разрешённые локальные
поля, добавляет изменение истории и фиксирует успех. Сетевого I/O внутри нет.
ProductNotFound в CollectionService создаёт общий недоступный MarketplaceCard
на основании идентичности цели и доступного локального названия.

Новые JSONB snapshots используют новый сериализатор. Исторические version 1.0
и импортированные пустые snapshots сохраняются как данные: runtime не читает
их денежные поля для каталога/истории. Ранее применённые Alembic-ревизии,
включая 0009 с image_url, не переписываются. Миграция БД не планируется.
Не создавать fallback parser для старого контракта. Если реализация выявит
необходимость изменения схемы, пересогласовать план до такой правки.

### 6. Полный переход CLI и удаление заменённого кода

Перенести ozon_article_json/cli.py в connectors/ozon/cli.py, обновить main.py,
логику путей профиля (нельзя полагаться на прежнее число parent), тесты,
release/aur packaging и актуальные импорты. Оба CLI main остаются доступны.
В CLI списков и добавления сохранить плоские marketplace/external_id:
сериализацию TrackedCard делать явно вместо утечки вложенного ref через asdict.
Удалить ozon_article_json, ProductCardNormalizer, OzonRawCardParser, старые
экспорты ProductSnapshot и snapshot_to_* после перевода функций в card_to_*.
Проверки legacy-обёрток перевести на сохраняемое поведение новых parser/client.
Не оставлять alias или compatibility facade. Используемые challenge helpers
удалять только после проверки всех потребителей.

## Risks / Trade-offs

- Широкий набор потребителей → последовательный перевод домена, коннектора,
  persistence, API/CLI, UI; один согласованный выпуск без смешанных версий.
- Разбор Ozon может поменять смысл данных → сравнить прежние fixtures и новые
  результаты по каждому полю, добавить дробные цены и вложенные JSON literals.
- Смена имени путает типы → TrackedCard/TrackedCardOverview/TrackedCardView
  только для локальных представлений; MarketplaceCard только для общего товара.
- Новые строки ломают внешние клиенты → явно описать breaking contract;
  не добавлять двойные поля, маршруты и старые форматы ответа.
- Смешивание с существующими правками → зафиксировать начальный diff; при
  коммите включать только принятые изменения этого change. Если общий hunk
  нельзя отделить безопасно, сообщить об этом перед коммитом.

## Migration Plan

1. После явного одобрения плана зафиксировать baseline тестов и diff рабочего
   дерева. Ранее зависавший тест terminal confirmation проверить с timeout;
   не считать весь Python-набор зелёным по частичному выводу.
2. Реализовать модели, точные денежные границы и перевод потребителей по tasks.md.
3. Проверить существующую схему и новые записи на отдельной disposable БД,
   включая базу с version 1.0/пустыми snapshots; сравнить ID, данные и связи.
4. Выпускать API/worker/CLI/UI вместе, остановив прежние процессы. Использовать
   действующий механизм backup; не запускать миграции/тесты на пользовательской БД.
5. При ошибке исправлять вперёд; заменённые реализации для rollback не хранить.
   Восстановление пользовательской БД из backup — отдельная операция с разрешением.
6. Представить diff, проверки и ограничения, дождаться принятия реализации;
   затем обновить актуальные руководства, принять ADR, sync/archive specs,
   создать проверенные коммиты только задачи. Не push/merge.

## Verification

Unit: parser/mapper/общая модель, exact decimal и schema validation; fake второй
площадки; настройки без первого сбора; mismatch, missing/unknown, cancellation,
lease и unchanged success. API: все денежные поля строками, strict import v2,
export roundtrip. Frontend: числовой порядок строк, null, округление, группы,
график и миграция notification state с pending работой.

Интеграция: имеющиеся postgres, reliability, migration и group metrics tests
только с disposable TEST_DATABASE_URL. Проверить прежние цены/ID/snapshots,
dedup, rollback, concurrent retry и REPEATABLE READ. Сравнить число запросов
и p95 каталога на одинаковых синтетических данных: без N+1, p95 не выше
max(1.20 × baseline, baseline + 50 мс), как требует catalog-snapshot.

Режимы: queued API/worker и direct CLI с fake connector отдельно; числовой
CLI без DATABASE_URL с нормализованным/raw/output; импорт обоих CLI.
Frontend lint/unit/mock E2E, Rust tests и desktop build. Изолированный live
smoke с fake connector после сборки проверяет Tauri → API → worker → PostgreSQL;
mock E2E этого не доказывает. Настоящий Ozon не является условием unit-тестов.
