# Proposal

## Why

PostgreSQL-репозитории одновременно читают данные, управляют транзакциями и определяют выгодность, представителя группы и расписание. Множественное наследование скрывает зависимости областей хранения, а API и worker зависят от конкретной реализации; ARCH-03 должен сделать правила проверяемыми без БД и сохранить уже принятые гарантии исполнения.

## What Changes

- Выделить чистые правила выгодности и выбора представителя в домен; сборку согласованного каталога перенести в application. SQL-агрегации и чтение единого снимка оставить PostgreSQL-адаптеру.
- Выделить политику шестичасового расписания и устаревания владельца, передавать время явно. Решение о постановке запуска вычислять внутри защищённой транзакции на актуальных данных.
- Заменить общий `PriceWatchRepository` небольшими типизированными портами по потребителям. API получает порты чтения/изменения, executor — контракт исполнения, worker — очередь/расписание, challenge handler — операции ожидания пользователя.
- Заменить фасад с множественным наследованием явной сборкой независимых областей хранения. Общие SQL-запросы и атомарный writer результата передавать явно; не делить одну транзакцию между независимо фиксируемыми репозиториями.
- **BREAKING (Python):** удалить заменённые фасад, протокол и старые импорты после миграции всех внутренних потребителей, тестов и служебных скриптов. Совместимые обёртки не оставлять.
- Сохранить HTTP/JSON, схемы БД, данные, правила групп/выгодности, Decimal, очередь, retry и все три пути сбора. Новых зависимостей и миграций не требуется.

## Capabilities

### New Capabilities

Нет. Это рефакторинг существующих обязанностей без новых пользовательских возможностей.

### Modified Capabilities

Нет. `catalog-snapshot`, `deal-selection`, `group-card-metrics`, `scheduled-collection` и `collection-run-execution` сохраняются. В `.openspec.yaml` установлен `skip_specs: true`: дельты поведенческих требований не создаются.

## Impact

- Python: `price_watch/domain`, `application`, `ports`, `infrastructure/postgres`, API dependencies/routes/app, CLI, worker и challenge handler. Точки сборки явно создают реализации и политики.
- Потребители общего фасада: Python unit/integration tests, `scripts/benchmark_catalog.py`, изолированный desktop smoke и другие найденные импорты. Frontend и Rust-контракты не меняются.
- Критерии приёмки: правила исполняются и тестируются без SQLAlchemy/HTTP/БД; runtime-потребители не импортируют PostgreSQL вне точек сборки; нет multiple-inheritance фасада и скрытых межобластных вызовов `self`; идентичные каталог, Decimal-значения, статусы и retry на одинаковых данных.
- Безопасность данных: REPEATABLE READ для каталога, порядок блокировок run → target → card, lease и идемпотентное атомарное сохранение результата/карточки/истории/счётчиков остаются обязательными. Импорт сохраняет защиту от активного сбора и свою транзакцию.
- Проверка: чистые unit-тесты правил, существующие API/collection/Decimal/CLI-тесты, PostgreSQL-гонки и rollback только на disposable `TEST_DATABASE_URL`, сравнение каталога и производительности до/после, queued API/worker, direct collect и numeric JSON без `DATABASE_URL`.
- Риски: потеря транзакционной защиты при разнесении кода, утечка ORM в application, N+1, расхождение денежных вычислений, незамеченные импорты фасада. Подробные границы, альтернативы и пороги — в design и проекте ADR 0007.

План требует явного согласования по vibe-flow. Код приложения до согласования не изменяется.
