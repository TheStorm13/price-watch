# Design

## Context

Мотивация — в proposal.md. Frontend — Vite SPA с React, TypeScript, React Router, Lucide и Recharts. Tailwind и `components.json` пока отсутствуют, alias `@` не настроен. `Button.tsx` использует собственные варианты `primary/secondary/ghost/danger` и prop `icon`. Тема находится в `src/styles/tokens.css`, общие стили — в `global.css`, где есть глобальные селекторы `button`, `table`, `th`, `td`.

`AddCardDrawer`, `GroupDialog` и `CardActionsMenu` самостоятельно управляют открытием, Escape и восстановлением фокуса. Каталог содержит кликабельные строки, сортировку, выбор, группы и массовые операции. В E2E уже проверяются основные сценарии, частичные сбои, геометрия при 1024 px и карточки с разными данными. Эти тесты используют mock API; desktop-поведение отдельно покрывается App/BackgroundSettings tests и ручной проверкой WebView.

## Goals / Non-Goals

**Goals:** единые примитивы и тема, последовательная миграция, воспроизводимый workflow Codex с skill и MCP, сохранение поведения и компактности.

**Non-Goals:** новые продуктовые функции, тёмная тема, мобильная версия, смена маршрутизации, логики запросов, Recharts или backend; массовая установка неиспользуемых компонентов; добавление Storybook.

## Decisions

### 1. Предлагаемое ADR: shadcn как слой UI-примитивов

Предлагается ADR 0003, статус **Proposed** до согласования плана. Решение: компоненты официального `@shadcn` хранятся в `src/components/ui`, предметные компоненты остаются отдельно, зависимости и lockfile фиксируются. Существующие предметные компоненты из `ui` постепенно вынести в отдельный каталог, обновляя импорты.

Рассмотрены: сохранение собственного UI (меньше начальных изменений, больше собственного сопровождения); Mantine/MUI (готовые библиотеки, другой способ настройки); shadcn с Base UI либо Radix (единый исходный код компонентов). Предлагается **Radix** как единая база миграции с API `asChild`; преимуществ по качеству или производительности над Base UI без измерений не заявляем. Base UI также допустим, но переход между базами позже потребует отдельного изменения. До реализации пользователь согласует предложенную базу вместе с планом. Skill миграции Radix→Base здесь не нужен: Radix в текущем приложении отсутствует.

### 2. Тема и безопасное сосуществование CSS

Tailwind 4 через Vite plugin, alias `@/*` согласован в TS и Vite, `components.json` с `rsc: false`, TypeScript, CSS variables и Lucide. Использовать существующий `global.css` как точку входа. Инициализацию выполнить в существующем `frontend`, без генерации нового приложения и без замены всех старых стилей.

Светлая нейтральная основа с синим primary, текущими радиусами 8/12 px, существующим font stack. Объединить токены темы с shadcn semantic variables, временно сопоставить старые имена новым. Управление темой — в одном месте. На первом этапе явно ограничить legacy-селекторы, особенно таблицы/поля/кнопки: unlayered CSS может перекрыть Tailwind. После каждого переноса удалять только больше не используемые правила. Зафиксировать визуальные состояния на тестовых данных перед переносом.

### 3. Перенос по потребителям

| Сейчас | Предлагаемый компонент |
| --- | --- |
| Button и icon-button | Button с вариантами и размерами |
| Поля и ошибки | Field, Input, NativeSelect/Select по текущей семантике |
| Выбор и переключатели | Checkbox, Switch, ToggleGroup |
| AddCardDrawer | Sheet справа |
| GroupDialog | Dialog |
| CardActionsMenu | DropdownMenu |
| Подтверждения удаления | AlertDialog |
| Статусы, ошибки, загрузка | Badge, Alert, Skeleton |
| Таблица, плитки | Table, Card с предметным содержимым |

У старого Button и shadcn разные API. Во время перехода допустим небольшой адаптер для старых потребителей; к завершению убрать адаптер и старые варианты. Не переписывать фильтрацию, сортировку, selection hooks и mutation flows. Не добавлять TanStack Table только ради оформления таблицы. Recharts сохранить с цветами из темы, без изменения расчётов.

При переходе на порталы проверить propagation внутри кликабельных строк. Сохранить подтверждения, предупреждение об удалении истории, pending/disabled и обработку частичных ошибок. Закрытие и возврат фокуса должны учитывать удаление исходного trigger и переход между меню и AlertDialog. Native file input для импорта допустим.

### 4. Работа через Codex: skills + MCP

Использовать `.agents/skills/shadcn/SKILL.md` как профильный skill, `vibe-flow` как процесс. Для React-изменений применять react-best-practices, для проверки в браузере frontend-testing-debugging. Context7 уже доступен; официальный shadcn MCP в текущем списке инструментов отсутствует.

После согласования добавить в проектный `.codex/config.toml` отдельный сервер, сохранив существующие настройки:

```toml
[mcp_servers.shadcn]
command = "npx"
args = ["-y", "shadcn@latest", "mcp"]
cwd = "/home/ilya-groza/DevProjects/price-watch/frontend"
```

Это настройка инструментов разработки, не runtime-зависимость. После подключения требуется перезапуск/новая сессия Codex и проверка реального наличия tools. До появления инструментов не заявлять, что shadcn MCP использован. Нынешняя sandbox-защита `.codex` может потребовать отдельного системного разрешения на запись.

В `frontend/AGENTS.md` закрепить: сверять `components.json`/CLI info; использовать существующие компоненты; искать примеры через MCP и читать docs через CLI/Context7; добавлять из согласованного `@shadcn` через CLI; проверять сгенерированный diff; при обновлении сначала dry-run/diff; не перезаписывать локальные компоненты автоматически. Использовать семантические токены, общие variants, предметные композиции и доступные заголовки диалогов. MCP не заменяет CLI, тесты и браузерную проверку.

## Risks / Trade-offs

- CSS reset, cascade layers и legacy rules → безопасно настроить каскад и сравнивать смешанные экраны после каждого этапа.
- Overlay/portal меняют фокус и bubbling → тесты клавиатуры, Escape, возврата фокуса, кликов внутри строки, перехода menu→confirmation.
- Новые event API для Select/Checkbox → проверять значения фильтров и сохранение выбора, а не механически заменять JSX.
- Tailwind 4 требует современной WebView → проверить установленную WebKitGTK/Tauri среду и реальный запуск. При несовместимости остановить перенос и пересогласовать подход.
- Изменения DOM могут затронуть E2E → предпочтительны роли и labels; сохранять проверки геометрии, а не ослаблять их ради прохождения.
- Код компонентов принадлежит проекту → обновления upstream просматривать через CLI diff и проверять совместимость.
- Repowise на момент чтения показывал индекс на `50c7ffe`, HEAD `d6dd5f3`; обновление не завершилось и остановлено. Оценки истории — ориентиры, план основан на текущих исходниках и существующих тестах.

## Migration Plan

1. Согласовать план и Proposed ADR; записать согласование в workflow-run. Получить baseline unit/E2E и изображения текущих экранов на mock-данных.
2. Подключить shadcn MCP и проверить инструменты после перезапуска; настроить Tailwind, тему, aliases, components.json и инструкции Codex. Проверить сборку и существующий UI.
3. Перенести базовые контролы и компактный участок каталога, проверить общую тему, затем перенести оставшихся потребителей этих контролов.
4. Перенести меню, подтверждения, добавление карточки и диалог группы; проверить клавиатуру и неизменность mutations.
5. Перенести детали карточки, состояния сбора, настройки фона и оставшееся оформление каталога; убрать устаревший CSS и временные адаптеры.
6. Выполнить `npm --prefix frontend run lint`, `npm --prefix frontend test`, `npm --prefix frontend run test:e2e`, `npm --prefix frontend run build:desktop`, `npm --prefix frontend run desktop:build`. Проверить WebView на изолированных тестовых данных, не запуская сбор/удаление пользовательских данных. Если desktop smoke недоступен, явно сообщить об этом.
7. Представить diff, изображения, результаты и ограничения пользователю. Дождаться приёмки, затем обновить затронутую документацию, статус ADR и архивировать change; sync specs не нужен при skip_specs.

Изменения вести самостоятельными проверяемыми этапами; коммиты создавать по запросу пользователя. Для отката вернуть файлы frontend и lockfile предыдущего этапа согласованным коммитом. База данных и API не мигрируют. Ничего не пушить и не публиковать без отдельного указания.
