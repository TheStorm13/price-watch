# Design

## Context

См. `proposal.md`. `CardsPage` уже получает полный список карточек и групп, строит строки для отдельных карточек и участников групп, хранит параметры поиска и сортировки в URL. `GroupDialog` уже отправляет полный массив `cardIds` через `useSaveGroup`; `PUT /api/groups/{id}` заменяет полный состав группы, а репозиторий переносит карточки между группами. `PATCH /api/cards/{id}` меняет `dealsEnabled`; `DELETE /api/cards/{id}` удаляет карточку вместе с историей и может вернуть `409` при активном сборе. Табличная строка кликабельна целиком, поэтому чекбокс требует отдельной обработки события.

## Goals / Non-Goals

**Goals:**

- Сохранить единый источник выбранных ID в пределах страницы и использовать его для панели действий и предварительного состава новой группы.
- Сделать поиск и сортировку в диалоге локальными операциями над уже загруженными карточками.
- Добавить карточки в существующую группу без потери её нынешних участников.
- Явно обработать частичный успех при массовом изменении и удалении карточек.

**Non-Goals:**

- Серверная операция массового обновления или удаления, транзакция на несколько карточек или изменение порядка карточек в самой группе.
- Изменение сеточного вида и существующих API/БД-контрактов.

## Decisions

1. `CardsPage` хранит `Set<number>` выбранных ID. У каждой строки карточки появляется первая узкая ячейка с доступным чекбоксом; строка группы получает пустую ячейку. Обработчик чекбокса останавливает переход по клику строки. Панель действий видна при непустом выборе, остаётся доступной после фильтрации и позволяет снять весь выбор. После обновления данных удалённые ID исключаются из выбора. Альтернатива — хранить выбор только видимых строк; она теряет выбранные карточки при поиске и сворачивании группы.
2. Создание группы из панели передаёт в `GroupDialog` первоначальные ID и вызывает существующее `createGroup`. Обычная кнопка «Создать группу» продолжает открывать пустой диалог. При успешном сохранении панель очищает обработанный выбор; отмена и ошибка его сохраняют. Диалог показывает число выбранных и предупреждение о переносе из других групп. Альтернатива — создавать группу сразу из панели; она не даёт задать название и проверить состав.
3. Отдельное действие «Добавить в группу» открывает выбор существующей группы. Перед отправкой `PUT` интерфейс получает её актуальные `cardIds`, объединяет их с выбранными ID без повторов и передаёт действующие название и теги без изменений. Успех очищает обработанный выбор, ошибка оставляет его. Интерфейс предупреждает о переносе карточек из других групп. Альтернатива — открыть редактор группы с исходным составом; там пользователь может случайно снять отметки с прежних участников. Поскольку `PUT` заменяет полный состав, остаётся небольшой риск конкурентного изменения между чтением и записью; однопользовательский desktop-режим и повторное чтение перед записью уменьшают его без изменения API.
4. `GroupDialog` фильтрует загруженный список по нормализованным названию и внешнему ID, сортирует русским `Intl.Collator` по отображаемому названию, с ID как запасным ключом и стабильным разрешением равенства. Начальный порядок — название по возрастанию, пользователь может переключить на убывание. Множество выбранных ID независимо от отфильтрованного списка. Альтернатива — серверный поиск; существующий каталог уже загружен целиком, а новый API добавил бы контракт без необходимости.
5. Массовое включение и исключение применяет существующий `PATCH` к каждому выбранному ID, задавая одно целевое булево значение. Результат каждого запроса учитывается отдельно; успешные ID удаляются из выбора, неуспешные остаются, сообщение показывает частичный сбой. Инвалидация карточек, групп и выгодных предложений выполняется после серии. Пока операция идёт, повторный запуск действий отключён. Альтернатива — одна новая серверная транзакция; это меняет API и обработку отказов за пределами задачи.
6. Массовое удаление открывает отдельный `alertdialog` с количеством карточек и предупреждением об утрате их истории. До подтверждения запросы не отправляются. После него интерфейс вызывает действующий `DELETE` для каждого ID, учитывает успех и отказ отдельно, удаляет успешные ID из выбора и сохраняет неуспешные для повтора. Во время выполнения повторный запуск заблокирован. `409` от карточки в активном сборе показывается как частичная ошибка. Альтернатива — удалить без подтверждения или одним новым endpoint; первое скрывает необратимые последствия, второе расширяет backend-контракт.

## Risks / Trade-offs

- [Массовые запросы не атомарны] → Показывать частичный результат, оставлять неуспешные карточки выбранными и разрешать повтор.
- [Удаление карточки каскадно удаляет её историю] → Перед первым запросом показывать явное подтверждение с числом карточек; ошибки удаления не скрывать.
- [`PUT` группы заменяет состав целиком] → Получать текущую группу перед добавлением, объединять ID без повторов и сохранять существующие название и теги.
- [Скрытый фильтром выбор может удивить] → Постоянно показывать общее число выбранных и действие «Снять выбор»; в диалоге показывать число участников независимо от поиска.
- [Новая ячейка меняет ширину таблицы и индексы существующих тестов] → Проверить адаптивную таблицу и обновить тесты, которые обращаются к ячейкам по индексу.
- [`CardsPage` является частым источником регрессий] → Ограничить изменение логикой выбора и таблицей; проверить существующие сценарии групп, фильтров, меню карточки и сетки.

## Migration Plan

Миграций и новых зависимостей нет. Изменение поставляется только с frontend; действующие FastAPI и PostgreSQL совместимы. Откат frontend возвращает прежний интерфейс, но не восстанавливает карточки и историю, которые пользователь уже подтвердил к удалению. Сбор цен через desktop/API/worker, `main.py collect`, CLI и режим JSON не меняются.
