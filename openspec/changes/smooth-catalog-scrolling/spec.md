# Task: Плавная прокрутка каталога с целью 120 FPS

## Goal and acceptance criteria

Уменьшить задержки прокрутки desktop UI. Цель пользователя — 120 FPS
(8,33 мс на кадр), без ухудшения фото, изменения данных или потери действий.
На текущей машине оба активных экрана настроены на 60 Гц, поэтому достижение
видимых 120 FPS нельзя подтвердить на имеющейся конфигурации. Цель сохраняется;
проверка на 120+ Гц остаётся отдельным неподтверждённым критерием, а 60 FPS
не выдаются за его выполнение. Настройки экранов автоматически не меняются.

Критерии: убрать лишний sticky при отсутствии горизонтального переполнения;
сохранить доступность правых действий при горизонтальной прокрутке узкого окна;
уменьшить задержки относительно baseline в том же системном WebKit на прогретых
изображениях; сохранить ограниченный DOM больших каталогов, группы, выбор,
клавиатуру/меню и возврат из карточки. Зафиксировать FPS/frame intervals и условия,
отделить длительность синхронного scroll handler от полной стоимости кадра.
Проверки: production native before/after, существующий performance E2E и
проверка resize/горизонтального переполнения, TypeScript и production build.

## Agreed solution

Пользователь после исследования явно поручил: «Нужно достичь 120 fps, это цель.
Приступай к улучшениям». Разрешены предложенные изменения таблицы и scroll path.

1. Каталог определяет горизонтальное переполнение своего table container при
   resize/переключении вида. Только при переполнении действует sticky правых
   столбцов; обычные таблицы/другие экраны не меняются. Observer реагирует на
   размеры, а не подписывается на каждый scroll; освобождается при unmount.
2. Сохраняется виртуализация больших каталогов. Малые коллекции отключают
   ненужные TanStack scroll observers. Порог natural layout — 100 логических
   строк только для списка без горизонтального переполнения; в узком окне
   со sticky и в плитке остаётся 40. Это устраняет row churn для текущих 75
   карточек, сохраняя bounded DOM больших коллекций и защиту от дорогой
   полной таблицы со sticky. Проверить отказ от принудительного
   flushSync и стабильные функции ключей/оценок; оставить только варианты,
   подтверждённые сравнением и поведением. Видимая область списка округляется
   наружу до блоков по 4 строки: полный overscan и focus pins сохраняются,
   добавляется не более 6 строк относительно исходного range. Это уменьшает
   частоту изменений DOM таблицы без отказа от виртуализации. Не вводить задержку обновления
   изображений, не уменьшать качество, не переписывать таблицу в div/grid.
3. Сохранить существующие данные, фото ×1 CSS×DPR и их три профиля, фиксированные
   плитки, selection/focus pinning, сортировку, группы, возврат позиции.
4. Не добавлять зависимости и постоянную телеметрию. Диагностические скрипты,
   фото, временные сборки и сырые результаты — `/tmp`. Обновить существующие
   architecture/testing guides по фактическому изменению. Дополнительный ADR
   не нужен: границы компонентов и архитектура остаются прежними.

Материальные альтернативы: отключение виртуализации отклонено экспериментом;
замена WebKit/таблицы требует иной архитектуры и не входит в это разрешение.
Если текущая оптимизация не докажет 120 FPS, сообщить фактический результат,
не считать целевой критерий выполненным и не менять движок автоматически.

## Execution state

Реализованы условный sticky, порог natural layout 100 только для широкого списка,
отключение TanStack observers в natural layout, useFlushSync=false, стабильные
функции ключей/оценок, блоки по четыре строки для виртуального списка.
Геометрия overflow вынесена в отдельную функцию; ResizeObserver отфильтровывает
изменения только высоты, освобождается при смене вида/unmount.

Фактически выполнено:
- Production native before/after, WebKitGTK 2.54.2, 1488×948 CSS, DPR=1,
  75 карточек/10 групп, read-only API proxy, прогретые фото. Два прогона списка
  по 5 секунд: baseline ~26 FPS, p95 51/52ms, max 57/60ms;
  финальный вариант ~60 FPS, p95 17/19ms, max 24/22ms, 0 кадров >25ms,
  0 DOM mutations и 0 scroll handler вызовов. Плитка ~59 FPS, p95 21ms.
  Все интервалы округляются WebKit до миллисекунд. Контроль idle ~60 FPS.
  Эти абсолютные числа отличаются от первого исследования из-за другого
  инструментирования и фоновой нагрузки; сравниваются только парные прогоны
  одинаковым `/tmp/pw-scroll-benchmark.py`. Это не запись рабочего Tauri окна
  и не проверка 120 Гц.
- Сырые результаты `/tmp/pw-scroll-before.json`, `/tmp/pw-scroll-final.json`;
  промежуточные `/tmp/pw-scroll-after.json` и `/tmp/pw-scroll-blocks.json`.
  Блоки без адаптивного порога дали ~48 FPS, но сохранили длинные кадры.
- TypeScript passed; production Vite build passed. Первая попытка Vite из корня
  отказала из-за index.html; повтор из frontend успешен.
- Existing unit checks: 2 passed (CardsPage performance, catalogRows).
- Performance E2E: 9 passed, включая новый resize/overflow/actions тест с
  переходом 100 natural строк → virtual narrow → natural wide, 5000 карточек,
  выбор offscreen, группы, progress isolation, Tab/меню, возврат из details.
- Repowise history risk возвращает устаревший 9f3876d и не знает новые файлы,
  хотя status показывает 1d58ab4. История сверена через git log; live diff risk
  корректно видит текущий HEAD/diff. Его complexity finding обработан выделением
  observer из CatalogResults. Оставшиеся complexity 27 и size 66 —
  структурные рекомендации для существующего сложного компонента, проверены
  вручную; дальнейшая переработка не нужна для текущей оптимизации.
  Ложные package-lock/all-tests советы относятся
  к старому индексу и чужой задаче, а не к изменению зависимостей здесь.

После выделения observer TypeScript и точечный resize regression повторены:
оба passed (1 E2E, 15.6s). Финальный diff проверен. Следующие шаги:
коммит только этой задачи, knowledge refresh и
пакет из изолированного чистого worktree, чтобы не включить чужие правки средней.
