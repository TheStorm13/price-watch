# Task: AliExpress — асинхронный сбор без планового лимита, N=1 и N=4

## Goal and acceptance criteria

Исследовать, как отказ от планового ограничения частоты и рост параллельности с 1 до 4 влияют на скорость и блокировки AliExpress. Это новая экспериментальная задача; выбор постоянной политики приложения в неё не входит.

Критерии: воспроизводимый стенд без БД; одни и те же зафиксированные productId:skuId для обоих режимов; подтверждённый потолок активных запросов N; отсутствие плановой задержки старта; отдельный учёт капчи, HTTP 401/403/429, повторов, ошибок подготовки, отмен и успехов. Проверки: барьерные тесты транспорта/стенда и сохранённый очищенный live-отчёт. Остановка по блокировке считается полезным результатом эксперимента, но не доказательством устойчивости. После отчёта задача остаётся открытой до решения пользователя и приёмки.

## Current system and evidence

- `marketplace_connector/connectors/aliexpress/client.py:32-65`: уже async, defaults concurrency=1, starts_per_second=5; None сейчас отвергается транспортом. Один транспорт/страница на сеанс, standalone вызовы также разделяют сеанс.
- `marketplace_connector/connectors/aliexpress/json_transport.py:95-123,208-252`: token bucket и ограничение одновременно активных запросов; общий cooldown по Retry-After; max_attempts=3, max_retry_wait=30, request_timeout=30.
- Там же `:255-288`: 401/403, HTML, challenge-маркеры и неожиданный адрес ответа вызывают ограниченное восстановление; это признаки отказа доступа, а не всегда доказанная CAPTCHA.
- `client.py:117-190`: проверка главной, ожидание антибота, обработчик ручной проверки. Фоновые режимы отвергают ручную проверку; обычный обработчик по умолчанию также RejectChallengeHandler.
- `price_watch/application/collection_service.py`: Ozon имеет свой пул 8, остальные площадки общий пул 5. Для эксперимента N=4 он не должен стать скрытым ограничением; production orchestration не меняется.
- [ADR 0008](../../../docs/adr/0008-aliexpress-sku-and-shared-browser.md): точная идентичность productId:skuId, общий Chrome и точная цена выбранного SKU обязательны. [Backlog](../../../docs/BACKLOG.md#ограничение-запросов-aliexpress) требует замеров перед пересмотром политики.
- Git 917823db подтверждает отдельный прошлый переход defaults на N=1; причина капчи этим коммитом не доказана. Repowise get_why вернул исторический эпизод, но его MCP indexed_commit=9f3876d устарел, несмотря на локальный checkpoint 8185ab1. Это ограничение источника, не свидетельство текущего риска. CodeGraph актуален, критичные факты подтверждены выданным текущим исходником.
- [Старый live-отчёт](../../../docs/tasks/add-aliexpress-connector/verification.md) содержит один проверенный SKU 1005009868651525:12000061135122688; он только начальная точка discovery, не готовая репрезентативная выборка. Прежние цены и доступность не переносятся на новый эксперимент.

## Agreed solution

**Предложение для согласования; одобрения плана пока нет.** Пользователь запросил сначала N=1 без лимита частоты, затем N=4 с наблюдением за капчей.

1. Добавить явное starts_per_second=None в AliExpress client/transport по образцу уже действующей семантики Ozon: отключается только token bucket. Defaults приложения остаются 1 и 5/с до отдельного решения. Числовой режим остаётся действующей production политикой, а не автоматическим fallback эксперимента. Сохранить ограниченные попытки, timeout, общий Retry-After/cooldown, отмену и единственное восстановление в обычном коде.
2. Создать отдельный DB-free стенд `experiments/parallel_aliexpress.py`, используя существующие клиент, коннектор, parser/mapper и Chrome lifecycle. Не рефакторить общий браузер или Ozon-стенд ради этого эксперимента. Настройки эксперимента передаются явно, не через глобальные production defaults.
3. Использовать только существующий стабильный профиль `~/.local/share/price-watch/chrome-profile`, видимый Chrome, без сброса, клонирования, нового профиля или экспорта cookies. При занятом профиле не удалять lock и не завершать чужие процессы. БД и историю пользователя не читать и не менять.
4. Discovery публичных товаров/SKU отделить от замеров. Зафиксировать 40 уникальных пар productId:skuId до сравнений; стремиться к нескольким товарам, явно записать количество productId и SKU, доступность и ограничения выборки. Если выборка не собрана, не подменять её повтором одного SKU; остановиться и обсудить препятствие. Discovery также прекращается при challenge/отказе доступа.
5. В одном Chrome-сеансе выполнить N=1 → N=4 → N=4 → N=1 на одном наборе. Каждый batch имеет явный сеанс клиента/транспорта, подготовку учитывать отдельно от времени запросов. Первый N=4 разрешён только после полного N=1 без challenge/401/403/429. Второй проход нужен для видимости прогрева и изменения состояния сессии; не считать его устранением всех сетевых/кэшевых факторов. Промежуточные N=2/3 и подбор оптимума не входят в этот этап.
6. В стенде первый наблюдаемый challenge, HTTP 401/403/429 или запрос ручной проверки останавливает выдачу новых запросов и весь эксперимент; отменить и дождаться своих активных задач, сохранить частичный отчёт. При N=4 уже стартовавшие запросы могут успеть завершиться. Не запускать следующую ступень, автоматически не проходить капчу и не продолжать через восстановление. Отдельная экспериментальная остановка срабатывает до штатного recovery/retry; это намеренное отличие измерительного режима от production, должно быть отражено в отчёте. Закрытие Chrome/ошибка bootstrap также завершает эксперимент с отдельной причиной. Продолжение после ручной проверки — только после обсуждения с пользователем.
7. Отчёт: конфигурация, порядок, исходный список пар, версии/commit, preparation/batch duration, logical success/failure/cancel/not-started, HTTP attempts и статусы, challenge marker class, recovery/retry counts, actual peak, задержка допуска и p50/p95 запросов/карточек. Сводка не должна прятать неуспешные batch или смешивать discovery и нагрузку. Тела ответов, cookies, headers и challenge URL/token не сохранять; только безопасные признаки. Успех требует штатной валидации identity, price/availability, а не просто HTTP 200.
8. Сравнить скорость успешного сбора и поведение доступа; не объявлять N=4 лучшим/устойчивым по короткому тёплому прогону. Это проверка двух фиксированных N, не долгий soak-тест. Не менять политику других коннекторов, API/UI/worker/CLI, SKU/ценовой контракт и persistence; миграции не нужны.

Альтернатива — сразу повысить production N или проводить длинный нагрузочный прогон. Для начала выбран изолированный короткий эксперимент: у Ali уже была ручная CAPTCHA, перенос успеха Ozon не обоснован. Существенной новой архитектуры нет, отдельный ADR сейчас не требуется. Документация: добавить проверенные команды и stop policy стенда в `docs/guide/TESTING_AND_TROUBLESHOOTING.md`; результаты/решения задачи остаются здесь и в приложенном JSON, backlog обновляется только после приёмки соответствующего результата.
