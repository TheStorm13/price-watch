# Task: AliExpress — весь пул товаров асинхронно без лимитов

## Goal and acceptance criteria

Исследовать скорость и блокировки AliExpress при одновременном асинхронном запуске всего конечного пула товаров без программного ограничения частоты и числа активных запросов. Это новая экспериментальная задача; выбор постоянной политики приложения в неё не входит.

Критерии: воспроизводимый стенд без БД; зафиксированные уникальные productId:skuId; весь пул запущен через async-задачи без worker pool, семафора и ограничения транспорта по числу активных запросов; отсутствие плановой задержки старта; отдельный учёт капчи, HTTP 401/403/429, повторов, ошибок подготовки, отмен и успехов. Проверки: барьерные тесты транспорта/стенда и сохранённый очищенный live-отчёт. Остановка по блокировке считается полезным результатом эксперимента, но не доказательством устойчивости. После отчёта задача остаётся открытой до решения пользователя и приёмки.

- `marketplace_connector/connectors/aliexpress/json_transport.py:95-123,208-252`: token bucket и ограничение одновременно активных запросов; общий cooldown по Retry-After; max_attempts=3, max_retry_wait=30, request_timeout=30.
- Там же `:255-288`: 401/403, HTML, challenge-маркеры и неожиданный адрес ответа вызывают ограниченное восстановление; это признаки отказа доступа, а не всегда доказанная CAPTCHA.
- `client.py:117-190`: проверка главной, ожидание антибота, обработчик ручной проверки. Фоновые режимы отвергают ручную проверку; обычный обработчик по умолчанию также RejectChallengeHandler.
- `price_watch/application/collection_service.py`: Ozon имеет свой пул 8, остальные площадки общий пул 5. Эксперимент должен обходить этот прикладной пул, иначе сохранится скрытое ограничение; production orchestration не меняется.
- [ADR 0008](../../../docs/adr/0008-aliexpress-sku-and-shared-browser.md): точная идентичность productId:skuId, общий Chrome и точная цена выбранного SKU обязательны. [Backlog](../../../docs/BACKLOG.md#ограничение-запросов-aliexpress) требует замеров перед пересмотром политики.
- Git 917823db подтверждает отдельный прошлый переход defaults на N=1; причина капчи этим коммитом не доказана. Repowise get_why вернул исторический эпизод, но его MCP indexed_commit=9f3876d устарел, несмотря на локальный checkpoint 8185ab1. Это ограничение источника, не свидетельство текущего риска. CodeGraph актуален, критичные факты подтверждены выданным текущим исходником.
- [Старый live-отчёт](../../../docs/tasks/add-aliexpress-connector/verification.md) содержит один проверенный SKU 1005009868651525:12000061135122688; он только начальная точка discovery, не готовая репрезентативная выборка. Прежние цены и доступность не переносятся на новый эксперимент.

## Agreed solution

Пользователь сначала согласовал исходный план, затем явно исправил требуемое поведение: «У нас есть пул товаров и они асинхронно обрабатываются без лимитов». Это отменяет N=1/4, последовательную выдачу товаров и ограничение активных запросов. Исправленный технический план ниже подготовлен для повторного согласования по vibe-flow; одобрение исходного плана не считается одобрением новой реализации.

1. Добавить явный экспериментальный режим `concurrency=None, starts_per_second=None` в AliExpress client/transport: отключены проверка потолка активных запросов и token bucket. Сочетание concurrency=None с числовым pacing в этой задаче не требуется; отклонять его при валидации, чтобы не вводить неоговорённую семантику ёмкости bucket. Defaults приложения остаются 1 и 5/с. Числовой режим остаётся действующей production политикой, а не fallback эксперимента. Сохранить timeout, конечные попытки, отмену и штатный recovery/cooldown обычного клиента.
2. Создать DB-free стенд `experiments/parallel_aliexpress.py`, использующий существующие клиент, коннектор, parser/mapper и Chrome lifecycle. После подготовки общей страницы создать async-задачи для всего пула и ожидать их вместе. Никаких семафоров, worker pool, последовательного ожидания каждого товара, ограничения active requests или искусственных задержек старта. Подготовка страницы разделяется всеми задачами и не сериализует сами запросы. Лимиты соединений/планирование браузера и сервера не контролируются приложением; фактическое перекрытие измеряется, не обещается равным размеру пула.
3. Использовать только существующий стабильный профиль `~/.local/share/price-watch/chrome-profile`, видимый Chrome, без сброса, клонирования, нового профиля или экспорта cookies. При занятом профиле не удалять lock и не завершать чужие процессы. БД и историю пользователя не читать и не менять.
4. Discovery публичных товаров/SKU отделить от замера. Зафиксировать 40 уникальных пар productId:skuId; стремиться к нескольким товарам, записать количество productId/SKU и ограничения выборки. Если выборка не собрана, не заменять её повтором одного SKU; остановиться и обсудить препятствие. Discovery прекращается при challenge/отказе доступа. Размер конечной выборки — объём эксперимента, а не лимит его параллелизма.
5. Сначала один измерительный batch всего пула без лимитов. Сравнение N=1/4 и дальнейшее повышение параллельности исключены. Измерять подготовку отдельно от товарных запросов; сохранять частичный отчёт при остановке. Не объявлять устойчивость или превосходство по одному короткому прогону.
6. Сохранить ранее согласованную остановку стенда по первому challenge, HTTP 401/403/429 или запросу ручной проверки: отменить и дождаться собственных задач, сохранить отчёт. Уже отправленные запросы могут успеть завершиться. Не проходить капчу автоматически и не продолжать через recovery. Этот stop срабатывает до retry/cooldown/recovery и не вводит плановый limiter. Ошибка bootstrap/закрытие Chrome также завершает эксперимент с отдельной причиной. Дальнейший запуск после остановки обсуждается с пользователем.
7. Отчёт: конфигурация (оба ограничения null), размер пула, список пар, commit/версии, preparation/batch duration, logical success/failure/cancel/not-started, HTTP attempts/статусы, безопасный класс challenge, retry/recovery counts, actual peak, p50/p95 запросов/карточек. Не смешивать discovery с измерением и не скрывать неуспешные результаты. Не сохранять тела ответов, cookies, headers, challenge URL/token. Успех требует штатной валидации identity, price/availability, а не только HTTP 200.
8. Миграции не нужны. Постоянные настройки Ali, других коннекторов, API/UI/worker/CLI, SKU/ценовой контракт и persistence не меняются. Обновить testing guide проверенными командами и stop policy; результаты находятся здесь и в приложенном JSON. Backlog обновляется после приёмки соответствующего результата.

Асинхронный запуск всего пула даёт всплеск нагрузки, зависящий от его размера; он может вызвать капчу даже там, где небольшой фиксированный N работает. Пользователь явно выбрал исследовать именно этот режим. Альтернатива с фиксированным N не входит в текущий эксперимент. Новый архитектурный слой не вводится; отдельный ADR для изолированного стенда не требуется.
