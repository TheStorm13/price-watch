# Task: Корректный смысл средней цены в каталоге

## Goal and acceptance criteria

Устранить неоднозначность показателя «Средняя»: пользователь видит текущую цену выше минимума, но среднюю равной минимуму.
Пользователь уточнил формулу: `(min + max) / 2` по всем сохранённым значениям. Пользователь явно согласовал формулу и её применение к выгоде и статистике периода ответом «да».

- При двух доступных наблюдениях 100 → 120 ₽ показанная средняя равна 110 ₽; проверить PostgreSQL и demo.
- Средняя каталога равна `(minimumPrice + maximumPrice) / 2` по всей истории основного варианта, включая последнее наблюдение. Повторы и частота сбора на результат не влияют: 100, 100, 160 → 130 ₽. Единственная цена даёт её же; отсутствие валидных цен — null. Проверить PostgreSQL и demo.
- Отбор выгодных предложений и суммы текущей/максимальной выгоды используют ту же середину диапазона, без отдельной базы предыдущих наблюдений; проверить товар, группу и отключённое участие в выгодных.
- Данные истории не изменяются, миграция сохранённых данных не требуется.

## Agreed solution

Формула пользователя принята как требование: `(минимум + максимум) / 2` по всей сохранённой истории, включая последнее наблюдение. Прежнее предложение разделять среднюю и отдельную базу предыдущих наблюдений отменено.

Согласовано пользователем: применять эту же формулу для отбора выгодных предложений и вычисления выгоды. Сохранить `averagePrice` как поле середины диапазона; не добавлять отдельную базу. Для каталога учитывать всю историю основного варианта; для статистики истории — значения в запрошенном периоде выбранного варианта, сохраняя существующие границы периода. Сохранить фильтрацию `in_stock`/non-null, точность Decimal и прежнее правило представителя группы. Повторы наблюдений не влияют на середину диапазона. С одним наблюдением текущая цена равна средней, поэтому выгоды нет.

Затронуты SQL метрики каталога (`queries.py`), статистика истории (`history_repository.py`), demo (`mockPriceMetrics.ts`) и связанные тесты/контракты. Форма API сохранена. Смысл `baselineDays`: число дней с валидными ценами всей истории вместо предыдущих наблюдений. Удалить утратившие смысл исключение последнего наблюдения и вычисление дневных средних.

Постоянная документация: `docs/guide/DATA_AND_API.md`, затронутые контракты `openspec/specs`, в частности `deal-selection`. Сбор, worker, CLI collect и JSON-режим не меняются; CLI history получает новую формулу через общий репозиторий статистики. Миграция данных не нужна.
