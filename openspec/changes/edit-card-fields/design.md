# Design

## Context

См. proposal.md. AddCardDrawer уже содержит поля создания и проверку ссылок AliExpress/WB; изменение ссылки автоматически заполняет идентификаторы. CardDetailsPage содержит отдельный CardTagsEditor. useUpdateCard обновляет каталог и запросы карточек. CardUpdate запрещает лишние поля; PATCH принимает nullable title/url и tags, а CardRepository обновляет только явно переданные поля и проверяет идентичность ссылок AliExpress/WB.

## Goals / Non-Goals

**Goals:** переиспользовать форму и существующий PATCH, разделить редактируемые метаданные и фиксированную идентичность, сохранить создание и доступность панели.

**Non-Goals:** редактирование цены, фотографии и истории; смена товара или варианта; новая архитектура хранения или сбора.

## Decisions

1. Обобщить существующую форму карточки для создания и редактирования, сохранив отдельные входы/обёртки при необходимости. Две независимые копии формы отклонены из-за расхождения валидации и интерфейса. Использовать текущие Sheet/Field/Button, без новых зависимостей.
2. Разместить явную кнопку «Изменить» в шапке деталей. Не добавлять отдельные точки редактирования в виртуализированный каталог. Удалить встроенный CardTagsEditor и связанные стили, импорты и устаревшие проверки, если они больше не используются.
3. В edit-режиме идентичность отображать только для чтения, отключить автозаполнение идентификаторов из URL. Проверять ссылку относительно исходного товара/варианта. Ozon и Яндекс сохраняют действующие правила HTTP(S) URL; не расширять контракт без отдельного решения.
4. Отправлять только title, url, tags: пустые строки преобразовать в null, пустые теги в []. Не включать groupId/dealsEnabled. Проверить тип UpdateCardInput и mock API на поддержку null и явного удаления URL; устранить расхождения с действующим API, если найдены.
5. Инициализировать черновик при каждом открытии, не перезаписывать его фоновыми обновлениями. После ошибки сохранять черновик; не закрывать панель до успешного ответа. Сохранение повторно не отправлять. Использовать существующий возврат фокуса; edit-фокус направить в первое редактируемое поле.

## Risks / Trade-offs

- [Общая форма меняет создание] → существующие тесты добавления и новые проверки обоих режимов.
- [URL меняет вариант] → отключить автозаполнение в edit, проверить AliExpress/WB на клиенте и существующем сервере.
- [Очистка теряется в mock или типах] → контрактные тесты с null и пустым массивом.
- [Результат E2E ошибочно принят за live] → браузерные сценарии проверяют только mock UI; API проверяется отдельно.
- [Индекс Repowise устарел и MCP указывает старый путь] → локальный CLI index-only update и проверка текущего исходного кода; исторические рекомендации считать вспомогательными.

## Migration Plan

Миграции БД не требуются. Повторно используется PATCH существующей записи. API/worker, main.py collect и числовой JSON-режим не меняются; проверить отсутствие затрагивающих их изменений в diff. PostgreSQL-проверки при необходимости запускать только с отдельным disposable TEST_DATABASE_URL. После принятия реализации обновить относящееся к редактированию руководство, синхронизировать спецификации, архивировать изменение и создать Git-коммит. Старую отдельную форму тегов не сохранять как запасной путь. Значительного изменения архитектуры нет, ADR не требуется.
