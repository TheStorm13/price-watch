# Design

## Context

Мотивация и границы — в proposal.md. UI использует React/Tauri, shadcn/Radix и общий CSS с legacy-слоем. Каталог и детали используют независимые query-ключи, но детали объединяют их ошибки в полноэкранное состояние. Выбор принадлежит CardsPage и сохраняется при смене вида; в плитке отсутствует контрол выбора. Минимальный размер desktop-окна — 1024×700, стартовый — 1440×900.

## Goals / Non-Goals

**Goals:** исправить навигацию и ошибки без изменения контрактов данных; привести плотность и читаемость списка/сетки к общим правилам; закрепить результат проверками.

**Non-Goals:** мобильная версия, новая тема, смена UI-библиотеки, обновление зависимостей, переработка API, алгоритма выгодности или выбора представителя группы. Поиск по всем участникам группы не входит: текущая фильтрация по представителю явно закреплена в group-card-metrics.

## Decisions

1. **Локальные изменения существующих компонентов.** Сохраняем нейтральный фон, синий акцент, системные шрифты и установленные primitives. Полный редизайн и переписывание CardsPage целиком увеличат риск без необходимости для найденных дефектов. Значимого изменения архитектуры нет, ADR не нужен.

2. **Контекст возврата в состоянии маршрута.** Передавать внутренний адрес `/cards` с query-параметрами при открытии товара из строки и плитки; принимать только внутренний путь каталога. Прямое открытие использует `/cards`. Не полагаться исключительно на history.back: предыдущей страницей может быть внешний сайт. Применить тот же контекст после удаления товара. Скролл и межстраничное сохранение выделения не добавлять в этот этап.

3. **Семантическая ссылка в строке.** Название — Link с сохранением обычных возможностей ссылки. Клик по свободной области строки можно сохранить, но исключить интерактивные элементы из повторной навигации. Чекбокс, ссылка и меню получают различимый фокус; вложенные ссылки не создавать.

4. **Независимые разделы деталей.** Шапка зависит от запроса карточки; история и график имеют локальные skeleton/error/retry. Статистика принадлежит истории и не подменяется текущей ценой при её отказе. Пустая история не равна ошибке; прежний график не выдаётся за данные нового периода. Проверка card_not_found остаётся на уровне страницы.

5. **Панель сбора.** В CollectionProvider открыть для панели состояние continueMutation и его ошибку, привязанную к текущему runId; повторный запрос блокируется до ответа. Не менять серверные переходы. В ActiveCollectionPanel убрать искусственный минимум 34%; в Progress передавать значение также доступному корневому примитиву, сейчас оно используется только в transform индикатора. При totalCount=0 показывать неопределённое состояние.

6. **Таблица и фильтры.** Сохранить горизонтальную прокрутку таблицы, закрепить наличие и меню справа с непрозрачным фоном выбранной/групповой/hover-строки. Это сохраняет читаемые значения вместо сжатия всех девяти столбцов в 960 px. Фильтры разложить по явным адаптивным строкам; поиск и вторичные фильтры выравнивать от левого края. Сброс не должен создавать отдельную пустую полосу.

7. **Сетка и метаданные каталога.** Колонки 220–280 px с выравниванием слева, одинаковая схема для вложенных групп. Неполная строка оставляет свободное место справа — осознанная замена растягиванию единственного товара до 960 px. Фото остаётся высотой 190 px, верхний отступ минимум 8 px. Основная цена 18 px, прочие цены минимум 14 px, подписи минимум 12 px. Удалить видимые ID из `row`/`tile`, убрать `.cards-grid__id`, его строку 24 px и соответствующие grid-template-rows; пересчитать высоты, не оставляя пробел на месте артикула. Название плитки сохраняет общую двухстрочную зону; теги имеют общую однострочную зону даже при отсутствии тегов, остальные подписи и цены не сдвигаются между карточками. В списке у названия одинаковый верхний отступ внутри ячейки независимо от тегов/статуса; блок метаданных выровнен по верху, а значения остальных столбцов — по центру строки. Теги не обрезать контейнером поперёк плашки: оба размещать в доступной ширине, сокращая текст внутри каждой через ellipsis и предоставляя полный текст через доступное имя и подсказку. Убрать лишний резерв ID, но сохранить одинаковые высоты плиток с двумя тегами и статусом. Чекбокс сверху слева отдельно от ссылки, меню справа; выделение видно и фоном/рамкой, и отметкой. Поиск по артикулу, идентификаторы в деталях, формах, импорте/экспорте и API сохраняются; отсутствие названия в каталоге отображается как «Без названия».

8. **Детали и формы.** В узком desktop-окне блок действий переносится целиком под идентичность товара; статистика перестраивается в несколько колонок до возникновения тесных подписей. В списке GroupDialog убрать накопление общего FieldGroup gap между уже отделёнными строками, сохранить прокрутку и доступные footer-действия. Поля WB/Ali, значения, валидация и предупреждения не меняются.

9. **Проверки.** Использовать существующий Playwright, сначала добавить проверки воспроизводимых дефектов. Визуальные эталоны ограничить ключевыми экранами и состояниями; зафиксировать время, locale, viewport, изображения и анимации. Для снимков использовать одно Linux/Chromium-окружение; пиксельное сравнение не заменяет поведенческие проверки. Эталоны предложить пользователю для визуальной приёмки. Новый Browser plugin и сторонний сервис не требуются. Существующий E2E явно требует сброс ниже фильтров и заполнение сеткой всей ширины: эти проверки меняются вместе с одобренным новым layout, остальные проверки контрактов сохраняются.

## Risks / Trade-offs

- Sticky-ячейки могут закрыть соседние значения → проверить начало/середину/конец горизонтальной прокрутки, фон и z-index строк всех типов.
- Изменение размеров сетки меняет плотность → принять явный максимум ширины и проверить 1, 2 и много товаров, вложенные группы и длинные значения.
- Переходы и частичные ошибки затрагивают query-состояния → тестировать прямой вход, возврат, смену периода, повтор, card_not_found и удаление.
- Полевая проверка Chromium не доказывает поведение Tauri WebKitGTK → отдельно выполнить имеющийся native smoke в disposable XDG/БД; при невозможности указать причину.
- Repowise после локального index-only update продолжает отдавать MCP-метаданные старого коммита → не считать его оценки полнотой набора тестов; доказательства взяты из текущего исходника и воспроизведения.

## Migration Plan

Изменяется только frontend и его проверки. Миграций данных, смены API и действий над пользовательской БД нет. Старые UI-ветки заменяются целиком в пределах одобренного плана. После приёмки обновить только относящиеся к UI/тестированию документы, синхронизировать specs и архивировать change. Не публиковать и не устанавливать пакет без отдельного запроса.
