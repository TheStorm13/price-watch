# Task: Кэшированные миниатюры 204 px в списке каталога

## Goal and acceptance criteria

Показывать фото в строках рабочего каталога с тем же качеством, которое пользователь выбрал в демо: Lanczos, длинная сторона 204 px, сохранение пропорций, PNG без потерь. Размер области списка остаётся 68 × 68 CSS px. Миниатюры не должны заново создаваться при каждом открытии каталога.

Критерии и проверки:

- Строки обычных и вложенных товаров используют подготовленное фото 204 px; крупные фото плиток и детального просмотра остаются исходными. Проверка компонентов и визуальный сценарий на образце 1623388135.
- Обработка соответствует демо: Pillow thumbnail с Lanczos и теми же параметрами, без кадрирования, повышения резкости и дополнительного JPEG-сжатия. Для образца получается 153 × 204. Проверка размеров, пропорций и рецепта на синтетической тестовой фотографии; визуальная проверка результата в рабочем списке. Отдельный экран сравнения и сохранение экспериментальных файлов не требуются.
- Повторное чтение и перезапуск API используют дисковый кэш; параллельные запросы одного фото объединяются; не более двух одновременных загрузок/обработок разных фото. Проверки счётчиками загрузчика, конкурентными запросами и новым экземпляром сервиса на том же временном каталоге.
- Старые карточки получают миниатюры без повторного сбора товара и миграции данных. Смена основного варианта/URL обновляет фото; отсутствие или ошибка фото показывает штатную заглушку. Проверка API на тестовых сервисах и UI с mock API.
- 100 карточек с уже подготовленными фото не вызывают повторного уменьшения; новые фото обрабатываются с ограниченной параллельностью. Измерить холодную/повторную загрузку на локальных фикстурах и сообщить числа без переноса их на все маркетплейсы.
- Рабочая БД, история, сборщики, CLI и standalone numeric JSON mode не меняются. Проверки используют временный кэш, фиктивные сервисы и фото; пользовательские данные не используются для тестовых записей.

## Agreed solution

Решение одобрено пользователем и реализовано. Архитектурное решение: [ADR 0016](../../../docs/adr/0016-cached-product-thumbnails.md).

### Backend и кэш

Добавить изолированный инфраструктурный сервис миниатюр и защищённый GET `/api/cards/{card_id}/thumbnail`. Endpoint читает URL фото текущего основного варианта через существующие сервисы; клиент не может передать произвольный URL для серверной загрузки. Карточка/фото отсутствуют — 404; недоступный или некорректный источник — контролируемая ошибка изображения, без падения каталога. Не менять imageUrl, export/import и schema БД.

Миниатюры создаются по первому запросу, а не при сборе цен. Это сразу покрывает уже существующие карточки и не добавляет работу в worker/CLI. httpx выполняет асинхронную загрузку; Pillow работает вне event loop. PNG соответствует принятому демо (thumbnail 204 × 204 с Resampling.LANCZOS, без дополнительных преобразований качества; исходники меньше 204 не увеличиваются).

Дисковый кэш — `$XDG_CACHE_HOME/price-watch/thumbnails` или `~/.cache/price-watch/thumbnails`, отдельный временный путь в тестах. Ключ — SHA-256 URL и версии рецепта. Запись атомарная; повторы одного ключа ожидают одну операцию. Лимит две одновременные операции загрузки/обработки; кэш ограничен 256 МиБ с удалением давно не использованных собственных файлов. Через 24 часа выполняется повторная проверка источника с ETag/Last-Modified, если сервер их поддерживает; неизменное содержимое не перерабатывается. Ошибки кратковременно запоминаются, чтобы прокрутка не создавала бесконечных повторов. Не удалять файлы вне собственного кэша.

Загрузка ограничена HTTPS публичных CDN: отклонять localhost, приватные/служебные IP и небезопасные редиректы, проверять каждый переход и сетевой адрес. Согласованное исключение: DNS Fake-IP 198.18.0.0/15 только для ozone.ru, wbbasket.ru, aliexpress-media.com и их поддоменов; не доверять одному лишь URL из БД. Лимиты: 15 секунд на загрузку, 20 МиБ входных данных, 40 мегапикселей декодированного изображения. Ошибки формата/лимитов дают штатную ошибку миниатюры. Не передавать API token внешним серверам или в URL.

### Frontend

В API client добавить чтение бинарного PNG через fetch с действующим токеном. Кэшировать Blob через существующий query client; object URL создавать/освобождать в жизненном цикле компонента, не копить ссылки при виртуализации. Ключ запроса включает cardId и исходный imageUrl; смена baseUrl/token также сбрасывает связанные запросы. При смене варианта/фото использовать актуальное изображение, исключив закрепление ответа старого запроса за новой карточкой.

Ввести компактный компонент для фото строки, использующий подготовленный PNG и существующее отображение ProductImage. Подключить в CatalogProduct.row (включая вложенные строки); при загрузке/ошибке — штатная заглушка. Не оставлять параллельную legacy-ветку исходника в этом списке. Не менять крупные ProductImage и небольшие фото таблицы вариантов, которые не участвовали в сравнении. Существующий mock API поддерживает новый контракт через синтетическую тестовую фикстуру, без реального API и БД. Экспериментальный экран и фотографии товара в приложение не возвращаются.

Новая зависимость Pillow добавляется через установленный порядок обновления lock-файла. Durable docs: API-контракт в docs/guide/DATA_AND_API.md; границы и поток в существующих архитектурных документах; путь/восстановимость кэша в NATIVE_DESKTOP.md и тесты в TESTING_AND_TROUBLESHOOTING.md. Миграций, изменений сборщиков и массовых запросов к реальной БД не требуется.
