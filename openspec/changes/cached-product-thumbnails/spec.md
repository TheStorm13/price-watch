### Backend и кэш

Добавить изолированный инфраструктурный сервис миниатюр и защищённый GET `/api/cards/{card_id}/thumbnail`. Endpoint читает URL фото текущего основного варианта через существующие сервисы; клиент не может передать произвольный URL для серверной загрузки. Карточка/фото отсутствуют — 404; недоступный или некорректный источник — контролируемая ошибка изображения, без падения каталога. Не менять imageUrl, export/import и schema БД.

Миниатюры создаются по первому запросу, а не при сборе цен. Это сразу покрывает уже существующие карточки и не добавляет работу в worker/CLI. httpx выполняет асинхронную загрузку; Pillow работает вне event loop. PNG соответствует принятому демо (thumbnail 204 × 204 с Resampling.LANCZOS, без дополнительных преобразований качества; исходники меньше 204 не увеличиваются).

Дисковый кэш — `$XDG_CACHE_HOME/price-watch/thumbnails` или `~/.cache/price-watch/thumbnails`, отдельный временный путь в тестах. Ключ — SHA-256 URL и версии рецепта. Запись атомарная; повторы одного ключа ожидают одну операцию. Лимит две одновременные операции загрузки/обработки; кэш ограничен 256 МиБ с удалением давно не использованных собственных файлов. Через 24 часа выполняется повторная проверка источника с ETag/Last-Modified, если сервер их поддерживает; неизменное содержимое не перерабатывается. Ошибки кратковременно запоминаются, чтобы прокрутка не создавала бесконечных повторов. Не удалять файлы вне собственного кэша.

Загрузка ограничена HTTPS публичных CDN: отклонять localhost, приватные/служебные IP и небезопасные редиректы, проверять каждый переход и сетевой адрес. Согласованное исключение: DNS Fake-IP 198.18.0.0/15 только для ozone.ru, wbbasket.ru, aliexpress-media.com и их поддоменов; не доверять одному лишь URL из БД. Лимиты: 15 секунд на загрузку, 20 МиБ входных данных, 40 мегапикселей декодированного изображения. Ошибки формата/лимитов дают штатную ошибку миниатюры. Не передавать API token внешним серверам или в URL.

### Frontend

В API client добавить чтение бинарного PNG через fetch с действующим токеном. Кэшировать Blob через существующий query client; object URL создавать/освобождать в жизненном цикле компонента, не копить ссылки при виртуализации. Ключ запроса включает cardId и исходный imageUrl; смена baseUrl/token также сбрасывает связанные запросы. При смене варианта/фото использовать актуальное изображение, исключив закрепление ответа старого запроса за новой карточкой.

Ввести компактный компонент для фото строки, использующий подготовленный PNG и существующее отображение ProductImage. Подключить в CatalogProduct.row (включая вложенные строки); при загрузке/ошибке — штатная заглушка. Не оставлять параллельную legacy-ветку исходника в этом списке. Не менять крупные ProductImage и небольшие фото таблицы вариантов, которые не участвовали в сравнении. Существующий mock API поддерживает новый контракт через синтетическую тестовую фикстуру, без реального API и БД. Экспериментальный экран и фотографии товара в приложение не возвращаются.

Новая зависимость Pillow добавляется через установленный порядок обновления lock-файла. Durable docs: API-контракт в docs/guide/DATA_AND_API.md; границы и поток в существующих архитектурных документах; путь/восстановимость кэша в NATIVE_DESKTOP.md и тесты в TESTING_AND_TROUBLESHOOTING.md. Миграций, изменений сборщиков и массовых запросов к реальной БД не требуется.

### Исследование зерна при отображении (2026-11-09)

Запрос пользователя: изучить текущую реализацию и предложить варианты улучшения; production-код не менять до выбора решения. Подтверждённые факты:

- Работающий установленный API вернул для карточки 103 / externalId 1623388135 HTTP 200, PNG 153×204, 39599 байт. Ответ побайтно равен `render_thumbnail` от сохранённого исходника демо `/tmp/thumbnail-original`, SHA-256 исходника 510483aee0a686b44034a142f3f6ceefbf1ce97e642212de6657945512854997. Установленный thumbnails.py совпадает с репозиторием. Для этого фото ни кэш, ни повторное сжатие не объясняют различие.
- `CatalogThumbnail` получает Blob защищённого endpoint, создаёт object URL и передаёт обычному ProductImage. CSS global.css задаёт области списка 68×68 и img `width:auto; height:auto; max-width:100%; max-height:100%; margin:auto`. Фото 153×204 фактически уменьшается до 51×68 CSS px. В текущем каталоге нет transform scale, zoom или image-rendering pixelated; виртуализация использует spacer rows, а не transform для строк товаров.
- Первоначальное демо проверялось Playwright Chromium, приложение на Linux использует WebKitGTK. Сейчас установлен WebKitGTK 2.54.2. Изолированные пробы одного PNG на реальном системном WebKitGTK (PyGObject), включая Wayland, воспроизводят зерно при DPR=1. Chromium тот же PNG на том же размере сглаживает. Результат WebKit 204→68 в этой пробе побайтно совпал с Pillow NEAREST; это описание результата, а не доказательство выбранного внутри движка алгоритма: bilinear при трёхкратном уменьшении также может выбирать центральные пиксели без достаточного предварительного сглаживания.
- Проба с исходным JPEG 1800×2400 также даёт зерно в WebKit. CSS optimizeQuality и отдельный GPU layer translateZ(0) не устраняют эффект. Обычный Canvas2D drawImage с imageSmoothingQuality=high в пробе DPR=1 тоже не устраняет эффект. При DPR=2 картинка отличается, поэтому переносить вывод DPR=1 на все масштабы нельзя.
- Подготовленный Pillow конечный PNG 51×68, показанный в WebKit в 51×68 при DPR=1, выглядит сглаженным. Протестированы как уменьшение из мастера 204, так и из оригинала. Это подтверждает рабочий путь обхода проблемного последнего уменьшения; точное визуальное совпадение с Chromium-демо ещё не принято пользователем.

Варианты для согласования:

1. Рекомендуемый: готовить на backend конечную миниатюру под фактический размер в физических пикселях (CSS-размер × devicePixelRatio), сохраняя Lanczos/PNG/кэш и при необходимости мастер 204. Для области 68 CSS px это длинная сторона 68 при DPR=1, 136 при DPR=2, 204 при DPR=3. Потребуются параметр размера endpoint, ключ кэша по рецепту/размеру, определение масштаба на frontend и обновление после смены монитора/масштаба; строгие границы параметра. Преимущество — контролируемое сглаживание и отсутствие зависимости от алгоритма уменьшения WebView. Риски — округление пропорций/координат и дробные DPR; проверить 1/1.25/1.5/2/3 и тот же реальный товар в native runtime. Это не слепая замена 204 на 136: значение должно соответствовать реальной плотности экрана.
2. Оставить API 204 и выполнять независимый программный resampling на frontend в конечный canvas bitmap (не полагаться только на drawImage high). Нужен проверенный resampler, кэш и очистка, желательно worker при сотне фото. Больше frontend CPU/сложности; текущая проба нативного Canvas2D недостаточна для решения. Алгоритм ещё не реализован и не измерен.
3. Перенос desktop-оболочки на Chromium. Это более широкая смена архитектуры, упаковки и потребления ресурсов; ради этого дефекта не рекомендуется. Обновление WebKit/смена backend рендера — возможное отдельное исследование, исправление в другой версии не подтверждено.

Для любого выбранного варианта конечная приёмка должна проходить в native WebKitGTK с текущим фото, в списке и после прокрутки/смены масштаба, а не только на синтетическом PNG в Chromium. Изолированный системный WebView не доказывает все свойства окна Tauri: реальное окно приложения не инструментировалось, параметры его DPR/дробных координат не измерены. Рабочая БД не изменялась; в процессе исследования прочитан только защищённый thumbnail endpoint. Browser plugin недоступен, для Chromium использован имеющийся Playwright. Все диагностические HTML/Python/скриншоты находятся в /tmp, демо в репозитории не создавалось. Основные артефакты: /tmp/pw-webkit-original-qa.png (Wayland), /tmp/pw-webkit-final-size.png, /tmp/pw-chromium-resampling.png, /tmp/pw-webkit-resampling.png, /tmp/pw-webkit-resampling-dpr2.png. Следующее действие — представить варианты пользователю; код, контракт endpoint и рецепт до выбора не меняются.
