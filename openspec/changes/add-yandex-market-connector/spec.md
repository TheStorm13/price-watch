# Task: Коннектор Яндекс Маркета с ценой по карте и одним промокодом

## Goal and acceptance criteria

Подключить `yandex-market` к существующему сбору Price Watch. Использовать
авторизованный Chrome-профиль приложения, получать все SKU товара и сохранять цену
с картой Яндекса с применением максимум одного лучшего подходящего промокода.
Пользователь согласовал выбор цены и остальной план, потребовав получение всех SKU
вместо ограничения одним вариантом. Это уточнение включено в план ниже.

Критерии и проверки:

1. Desktop/API/worker, плановый сбор, retry и `main.py collect` собирают карточки
   Маркета через общий builder. Проверка: integration-тесты executor/repository
   на отдельной disposable БД, регрессии очереди и начального сбора.
2. Запрос использует профиль Price Watch и проверяет авторизацию. Пропавший вход,
   CAPTCHA и ошибка схемы не превращаются в успешный снимок с завышенной ценой
   либо отсутствием товара. Проверка: browser-тесты и live-проверка профиля.
3. Обнаруживаются все связанные размеры/цвета товара; каждый SKU имеет собственные
   наличие, цену и историю. Initial collection получает начальные цены всех SKU;
   последующий сбор обновляет главный и включённые варианты, как у Ozon.
   Проверка: рекурсивные discovery fixtures и integration initial/selective/retry.
   Считается цена одной единицы каждого SKU у выбранного витриной продавца.
   Из действующих применимых кодов выбирается один, дающий минимальную цену
   относительно цены с картой. Проверка: табличные тесты условий и расчёта.
4. Для зафиксированных данных `2959 RUB`, `CLOTH11`, 10%, максимум скидки 500 RUB
   расчёт даёт `2663.10 RUB`. Это согласованное правило расчёта, а не уже
   подтверждённая live цена оплаты. Проверка: unit-тест и отдельное сопоставление
   с отображаемым Маркетом итогом без изменения пользовательской корзины.
5. История получает итоговую цену и достаточное объяснение в snapshot; повтор
   одинаковой цены/наличия не создаёт дубликат. Проверка: persistence/serialization.
6. Существующий числовой `main.py <ozon_id>` остаётся режимом Ozon без DATABASE_URL;
   оба CLI-импорта доступны. Проверка: существующие numeric/raw и CLI-тесты.

Единица цены — точный SKU (размер/цвет); единица карточки — всё связанное семейство.
Ввод любого SKU запускает обнаружение остальных вариантов. Главным первоначально
остаётся введённый SKU. Список вариантов, выбор главного и tracking используют
существующий интерфейс приложения. Обход всех продавцов и новый standalone CLI
для Маркета не требуются; UI для промокодов остаётся вне текущей задачи.

## Current system and evidence

### Текущий код

- `marketplace_connector/ports/connector.py`: `collection_session()` и
  `get_product(external_id) -> MarketplaceCard` — общий порт.
- `marketplace_connector/connectors/builder.py`: один `ChromeSession` на запуск;
  адаптеры Ozon, AliExpress, WB. Новый адаптер подключается тем же способом.
- `marketplace_connector/connectors/ozon/async_client.py` и `json_transport.py`:

  площадок; `MARKETPLACE_ORDER` пока содержит три площадки. Политика HTTP pools

  connector. `cards_repository.py` и `runs_repository.py` исключают его из
  initial/full/scheduled/retry collection.
- `frontend/src/api/queries.ts`, `frontend/src/api/mockApi.ts`,

  неподдерживаемого сбора Маркета.

- `marketplace_connector/application/card_identity.py`: для Маркета пока только

  при неизменной итоговой цене; существующий принцип дедупликации сохраняется.

### Ограничения доказательств

Совместный итог карта+промокод и округление на стороне checkout пока не проверены.
Пользователь явно определил требуемую базу расчёта. Расхождение live-итога с этим
правилом потребует остановки и решения пользователя, а не скрытой смены алгоритма.
Числовой URL SKU без slug, ошибка отсутствующего SKU, разновидности promo conditions
и варианты без цены по карте требуют точечных проб перед написанием адаптера.

CodeGraph возвращает текущие исходники. Локальный `repowise update . --no-workspace
--index-only --no-agents` завершился `Already up to date`; Repowise MCP продолжает
показывать старый commit и не находит часть текущих файлов. Его оценка риска не
считается достоверной; перед реализацией использовать локальный CLI по актуальному
индексу. Новая индексация/настройка другого репозитория не требуется.

## Agreed solution

### Согласованные пользователем решения

- Все live-пробы и production-запросы идут через профиль Price Watch, сохраняя
  авторизацию; отсутствие промокодов в анонимном ответе не доказательство их отсутствия.
- База — цена с картой Яндекса. Промокод применяется к этой цене; максимум один.
- Выбирается лучший подходящий под товар код. Последнее уточнение пользователя
  заменяет раннее обсуждение 2746 RUB: при цене 2959 и скидке 10% результат
  выбранного алгоритма — 2663.10 RUB до возможного storefront округления.
- Пользователь: «Нужно получать все sku; выбор цены верен; Все остальное хорошо».
  Это согласование остального плана и прямое требование расширить discovery на все
  SKU. Прежняя граница одного SKU отменена; ниже описано её расширение по паттерну Ozon.
  Приёмка реализованного результата не проводилась.

### Предлагаемый адаптер и транспорт

Новый пакет `marketplace_connector/connectors/yandex_market/`: identity, transport,
client, parser/models, pricing, mapper, connector. Использовать существующие
ChromeSession, RequestPool, нормализацию денег и общие ошибки; новых зависимостей
и общей абстракции HTTP-транспортов не вводить.

Ключ площадки остаётся `yandex-market`; external_id — точный ASCII numeric SKU.
Короткая ссылка может быть исходным URL при добавлении с известным SKU: разрешать
её в Chrome, проверять конечный домен и SKU; сохранять каноническую card-ссылку.
Не выводить SKU из parent product ID, не переключаться на поисковые рекомендации.
Запрос по SKU должен работать без хранения рекламных query-параметров short URL.

Bootstrap открывает Маркет в общем профиле; дальнейшие HTML получают browser fetch
с cookies. Из HTML извлекаются JSON Apiary, без исполнения извлечённого JavaScript.
Связывать compose/buyOption/price/promos только для целевого SKU и текущего offer;
данные рекомендаций и других продавцов не должны влиять на результат.
Источник — публичная витрина, не seller API. DOM-селекторы и JSON-LD не использовать
как альтернативный источник цены: они теряют условия оплаты/промо.

Отдельный request pool по действующей политике (100), без starts/second и card
semaphore; Маркет — следующий последовательный этап после WB. Слот включает полное
тело/подтверждённый abort, не ожидание в очереди. Таймаут запроса 30 s, максимум
3 попытки, Retry-After с ограниченным ожиданием до 30 s; повтор не дублируется
бесконтрольно на нескольких уровнях. Bootstrap/recovery сериализованы.

`isAuth=false` → AuthenticationRequired с просьбой войти через Chrome приложения;
не записывать анонимную цену. CAPTCHA → существующий challenge flow с учётом
ограничений скрытого Chrome; после подтверждения повторно проверить страницу.
429 → RateLimited; сеть/5xx → MarketplaceUnavailable; несовпавший SKU, неизвестная
обязательная структура → MarketplaceSchemaChanged. Только доказанное отсутствие
товара → ProductNotFound/OUT_OF_STOCK, цена null. Ошибки доступа не меняют историю.

### Все SKU: обнаружение и владение

Обходить граф ссылок размер/цвет только из контролов выбранной карточки
(`filterValue` с `filterid`, `value`, `pagehref`), не из произвольных ссылок,
рекомендаций или таблицы размеров. HTML-контролы используются для membership,
а цены и промо по-прежнему читаются из JSON. Если в другом ответе доступны
эквивалентные структурированные данные контролов, использовать их с теми же
проверками, не угадывая новые SKU по соседним числам/названиям.

Алгоритм: очередь начинается с введённого SKU; для каждого ещё не посещённого
узла получить карточку, проверить SKU и принадлежность семейству, извлечь точные
ссылки вариантов и добавить неизвестные. Текущие значения `#` описывают этот SKU,
а не отсутствующий вариант. Дедупликация по SKU, подавление циклов и одинаковых
ссылок; завершение только после исчерпания очереди и всех распознанных продолжений.
Текстовые цвета/размеры не перемножаются: отсутствующие комбинации не выдумываются.
Наличие/цена недоступного варианта не берутся из соседнего SKU.

`productId` из трёх проб совпадает и служит проверкой членства; не считать это
доказательством для всех категорий. Явная ссылка storefront — необходимое
свидетельство membership; неожиданный parent ID, скрытый список/продолжение,
несовпадающий SKU или redirect не игнорировать. До реализации проверить
представительные continuation controls. Нераспознанная полнота возвращает явную
ошибку discovery; частичный список нельзя объявить полным или удалить по нему
ранее известные SKU. Сохранять подтверждённые точные цены при частичном discovery,
как у Ozon, с failed target и диагностикой; retry не расширяет frozen target set.
Не вводить молчаливый лимит числа вариантов. Сетевые ограничения, отмена и
невозможность завершить обход должны давать видимый неполный результат.

Общий discovery на семейство в collection_session, coalescing одновременных
запросов и кеш проверенных снимков SKU в пределах запуска исключают повторный
полный обход для каждого варианта. Кеш не переносится между запусками. Начальный
обход получает цены каждого SKU отдельно; разные SKU могут иметь разные цены,
промокоды и наличие. `MarketplaceCard.variants` содержит полный подтверждённый
список ProductVariant: ref, canonical URL, title, options, image, availability,
selected. Выбор цены выполняется для каждого точного SKU независимо.

Встроить семейства Маркета в текущие `card_variants`, discovery и initial collection:
при добавлении получить все SKU/начальные цены, главным оставить исходный, остальных
по умолчанию не включать в регулярный tracking. При обычном обновлении открывать
новые подтверждённые SKU по existing discovery policy; их начальные цены получать
в этом запуске. Retry повторяет только неуспешные frozen targets. Удалённые с
витрины варианты/историю автоматически не удалять.

Использовать existing Ozon membership/ownership pattern: один SKU Маркета принадлежит
одной локальной карточке, транзакционная блокировка и проверка конфликтов при
добавлении из другого размера. Не создавать повторные истории и не выполнять
автоматическое destructive merge карточек. Проверить текущее добавление/импорт и
перенос предпочтений; ранее сохранённые карточки Маркета не пересоздавать.
При необходимости добавить marketplace-specific unique index на SKU в
`card_variants` по образцу `ozon_sku_unique`; миграция проверяет существующие
конфликты и останавливается с диагностикой, не удаляя данные. Конкретный migration
diff и data effects проверить до применения; live пользовательскую БД не менять
в рамках тестов. Нужда в substantive реорганизации модели сверх Ozon pattern
потребует отдельного согласования.

### Выбор цены

1. Получить валидную цену с картой и обычную цену в RUB. Если специальной цены
   по карте для товара действительно нет, использовать явно доступную обычную;
   отсутствие распознанного ценового блока не считать отсутствием скидки.
2. Рассматривать только привязанные к выбранному предложению действующие коды.
   Условия проверять для одной единицы: период, сумма, количество, категория,
   ограничения аккаунта, максимум скидки. Покупка других товаров ради порога
   не предполагается. Неясные ограничения исключают код с диагностикой причины.
3. Рассчитать каждый код независимо от одной базы: процентная скидка
   `base * percent / 100` с ограничением maxDiscount, либо заявленная фиксированная
   сумма. Не брать `discount.percent` как процент для кодов типа absolute:
   в live-ответе это может быть эффективный процент уже вычисленной скидки.
   Не извлекать сумму из названия кода. Проверить clipped absolute/minimum price
   semantics отдельной fixture/probe; при неясном контракте код не считать валидным.
4. Деньги — Decimal; предлагаемый контракт хранения — 2 знака, ROUND_HALF_UP
   после вычисления итоговой цены, без промежуточного float. Storefront округление
   сопоставить на live-данных; несовпадение материально и требует согласования.
5. Выбрать минимум из base и цен с каждым подходящим кодом. При равенстве с base
   оставить вариант без кода; между равными кодами выбирать по тексту кода для
   воспроизводимости. Никогда не применять второй код.

`MarketplaceCard.price` — выбранная итоговая цена. В `extensions.yandex_market`
сохранять JSON-совместимое объяснение: SKU/product/offer/business IDs,
`regular_price`, `card_price`, `base_price`, `final_price`, `price_source`
(`card`, `regular`, `card_promo`, `regular_promo`), выбранный `promo_code`, тип и
размер скидки, maxDiscount, пороги, срок действия, причины исключения кандидатов,
`calculation_basis=card_plus_single_promo`, `verification=calculated`.
Деньги — decimal strings, время — ISO UTC. Не сохранять cookies, токены, имя,
email, uid и полный ответ страницы. Расчётная цена не означает проверенную покупку.

Использовать существующий JSONB snapshot без новых ценовых колонок.
Возможная миграция касается только ограничения владения SKU, описанного выше. Удалить
superseded pending-ветки для Маркета у всех consumers; не сохранять старый режим
«карточки можно добавить, но нельзя собрать». Старые данные не удалять, историю
не пересчитывать. Текущая цена/статистика/выгодность получают выбранную цену через
существующий контракт. Показ промокода в UI — отдельное будущее изменение.

### Альтернативы и документация

Анонимный HTTP проще, но проба потеряла персональные промокоды и получила CAPTCHA.
Seller API не подтверждён как источник потребительской цены аккаунта. Запросы из
профиля и JSON страницы уже проверены, соответствуют паттерну Ozon и рекомендуются.
Расширяются существующий порт и паттерн семейств Ozon. Новая архитектура
не предлагается; возможный unique index не меняет ценовую модель.

Добавить `docs/guide/YANDEX_MARKET.md`; обновить ссылки в guide README, справочник
сбора/проверок и `docs/guide/DATA_AND_API.md` для semantics итоговой цены/snapshot.
Обновлять архитектурные guides только в частях списка адаптеров/этапов.

## Execution state

Реализация и проверки выполнены; требуется явная приёмка результата. Явное разрешение
на реализацию получено 2026-11-10: «Приступай к реализации». Сохранены требования
всех SKU и card_plus_single_promo; новых продуктовых решений не потребовалось.

  browser transport/client и connector; builder и этап после WB подключены.

  прежние варианты. Frozen retry не расширяет persisted targets.
