# Task: Средняя по времени и ценовая база за два года

## Goal and acceptance criteria

Заменить середину диапазона в роли средней на `Σ(price × duration) / Σduration`.
Пользователь выбрал окно последних двух лет также для исторического минимума.
Переключатель 7/30/90 дней должен менять только график и таблицу измерений;
верхняя статистика не зависит от переключателя. Перенос либо добавление
статистики под переключателем — отдельная идея в `docs/BACKLOG.md`.

Критерии и соответствующие проверки:
- Каталог и выгода используют среднее по времени за два года: числовые примеры
  и тесты PostgreSQL/demo с фиксированным временем.
- Минимум и верхняя статистика относятся к двухлетнему окну: тест старого
  экстремума и состояния, начавшегося до окна.
- Переключение 7/30/90 меняет только график/таблицу: компонентный тест с разными
  ответами для периодов и стабильными верхними показателями.
- Отсутствие товара/цены не имеет веса; история не смешивается между вариантами:
  регрессионные тесты интервалов и основного варианта.
- Сохранённая история не удаляется и не переписывается; нет миграции данных.

## Current system and evidence

- `price_watch/infrastructure/postgres/queries.py:22`: каталог считает
  `(min(price) + max(price)) / 2` за всю сохранённую историю основного варианта.
  Учитываются только `in_stock` и `price IS NOT NULL`, включая текущую точку.
  `baseline_days` — дни с сохранёнными валидными точками, не длительность
  наблюдения и не число успешных проверок.
- `price_watch/infrastructure/postgres/history_repository.py:87`: статистика
  выбранного периода использует ту же формулу, ограничивая точки по времени.
- `price_watch/domain/catalog_rules.py:6` и
  `price_watch/application/catalog_service.py:33`: текущая цена ниже этой базы
  даёт положительную выгоду и, при включённом участии и наличии, статус выгодной
  покупки. Достаточно одного дня с валидными точками.
- `price_watch/infrastructure/postgres/runs_repository.py:73`: повторное
  состояние `(price, availability)` не добавляет точку. При импорте
  `price_watch/domain/history_merge.py:25` тоже сокращает повторы.
- `frontend/src/api/mockPriceMetrics.ts:4` повторяет формулу для demo API.
- Контракт закреплён в `openspec/specs/deal-selection/spec.md` и
  `docs/guide/DATA_AND_API.md:155`. Это предусмотренное поведение, не ошибка
  реализации арифметического среднего.
- Repowise соответствует HEAD `809644bc6b51`; запрос истории решения не нашёл
  релевантного обоснования. Источник действующего контракта — код и спецификация.

Следствия: один старый максимум может завысить базу на неопределённый срок;
длительность обычной цены не учитывается. Если 29 дней цена была 1000, один
день 3000, середина диапазона 2000, средняя по времени 1066.67, медиана по
времени 1000. Это синтетический пример, не результат измерений рабочей базы.
При двух точках 100 и 80 текущая база 90, выгода 10; относительно предыдущей
цены снижение составляет 20. Метрики отвечают на разные вопросы.

Дополнительный факт: `frontend/src/features/card-details/CardDetailsPage.tsx`
передаёт выбранные `days` в `mainHistoryQuery` (строка 49), из его statistics
берёт верхние минимум/максимум и вычисляет середину диапазона и разницу
(строки 57–63, 107–116). Само `averagePrice` верхний блок не отображает.
Поэтому сейчас переключатель влияет и на показатели над ним.

## Agreed solution

Пользователем подтверждены формула, двухлетнее окно средней и минимума,
независимость верхней статистики от переключателя, добавление идеи в backlog.
Полный технический план ещё не одобрен. Следующие детали предложены для
утверждения вместе с планом, не считаются молчаливо согласованными.

### Правила расчёта

- Один момент `as_of` в UTC на расчёт. Начало окна — та же дата/время два
  календарных года назад; 29 февраля переводится в 28 февраля при необходимости.
- Для каждого варианта построить последовательность состояний с сортировкой
  `(observed_at, id)`. Цена действует до следующего состояния, последнее — до
  `as_of`. При одинаковом времени последнее по ID состояние действует дальше;
  предыдущие имеют нулевую длительность. Будущие точки не участвуют.
- Взять состояния внутри окна и последнее состояние до начала окна; обрезать
  интервалы границами окна. До первой известной точки цену не придумывать.
- В вес и знаменатель входят только положительные длительности состояний
  `in_stock` с известной ценой. Отсутствие, unknown и null разрывают интервал
  валидной цены, а не удаляются перед построением интервалов.
- При нулевой суммарной валидной длительности средняя — null. Одна доступная
  цена с положительной длительностью даёт среднюю, равную ей. Новая текущая
  точка с нулевой длительностью ещё не сдвигает среднюю.
- Минимум/максимум учитывают валидные цены, действовавшие внутри окна, включая
  унаследованное состояние и текущую точку на правой границе. Точка до окна,
  переставшая действовать до его начала, не участвует. По одной текущей точке
  экстремумы известны, даже если средняя пока null.
- Расчёт денег — Decimal/NUMERIC, без float; API сохраняет decimal strings/null.
  Деление с бесконечным десятичным представлением требует конечной точности;
  выбрать и документировать единую точность backend/demo в реализации.
- `baselineDays`/`observedDays` остаются счётчиками дней с сохранёнными валидными
  точками, теперь в соответствующем окне; не выдавать их за подтверждённое
  покрытие времени. Положительная средняя подразумевает известную временную
  базу даже при отсутствии новых точек внутри окна; согласовать с этим guard
  `baseline_days >= 1` и отображение выгоды, чтобы не блокировать унаследованную
  цену. Не вводить новый минимальный срок наблюдения или порог скидки.

### Допущение о перерывах — требуется подтверждение

Сохраняется модель «последнее известное состояние действует до следующего
изменения/момента расчёта», без произвольного срока годности. Это работает
с текущей компактной историей без изменений сбора и миграций, но долгий перерыв
в проверках продолжает вес последней известной цены. Реальная длительность
состояния между проверками неизвестна. Ограничение свежести — отдельный дизайн,
не добавлять его скрыто вместе с формулой.

### Потребители и интерфейсы

- `queries.py`: среднее/минимум каталога и вся зависимая выгода/сортировка/группы
  переходят на двухлетнюю базу, только по основному варианту.
- `history_repository.py`: единый расчёт статистики интервалов. Для HTTP-ответа
  истории statistics становится независимой от выбранных days и двухлетней;
  история, totalCount и пагинация остаются за запрошенные 7/30/90 дней. Явно
  описать период statistics в ответе; не оставлять поле, ложно обещающее выбранный
  период. Проверить CLI-потребителя статистики и согласованно обновить его контракт.
- `CardDetailsPage.tsx`: верхние показатели не зависят от days; подсказка явно
  говорит про последние два года. Состав и расположение блока не менять:
  «Середина диапазона» остаётся `(min + max) / 2`, это отдельная метрика,
  она не подменяет новую среднюю для выгоды.
- `mockPriceMetrics.ts`/`mockApi.ts`: те же временные правила для demo и тестов.
- Постоянные документы: `docs/guide/DATA_AND_API.md`, затронутые контракты
  `openspec/specs/deal-selection/spec.md` и при необходимости групповых метрик;
  остальные документы менять только при фактическом изменении их предмета.
- Сбор, worker, raw/numeric JSON не меняются: работают как поставщики наблюдений.
  История старше двух лет сохраняется для экспорта/графика и переноса состояния.
