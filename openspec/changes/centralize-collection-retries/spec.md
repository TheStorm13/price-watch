# Task: Дополнительный повтор неуспешного обновления

## Goal and acceptance criteria

Устранить сценарий, в котором получение товара завершилось ошибкой, но следующий
вызов коннектора успешен. Внутренние ретраи коннекторов сохраняются. Поверх них
нужен один дополнительный вызов для неуспешной цели в том же запуске через
1 секунду, с соблюдением Retry-After. Успешные варианты не повторяются.
Окончательная ошибка и failure_count появляются только после исчерпания повтора.
Ошибки записи в БД не должны вызывать повторное получение товара.

Критерии будущей реализации: временный отказ → успех без промежуточного failed;
два отказа → одна окончательная ошибка; отсутствие дубликатов истории и счётчиков;
соблюдение cooldown; отмена/потеря lease останавливают попытки. Проверить queued
desktop/API/worker, direct collect и numeric JSON без DATABASE_URL отдельно.

## Current system and evidence

Исходное поведение до реализации проверено 2026-11-07 по исходникам и синтетическим ответам:

- `marketplace_connector/connectors/ozon/json_transport.py:157` и
  `marketplace_connector/connectors/aliexpress/json_transport.py:132`: по умолчанию
  до трёх попыток для сети, таймаутов и 5xx; задержки 0.5 и 1 секунды.
  429 использует общий cooldown с fallback 1 секунда. Ожидание свыше 30 секунд
  возвращает RateLimited. Ошибки схемы/JSON и HTTP вроде 404 не повторяются.
- Обе реализации делают не более одного согласованного восстановления сессии;
  повторный отказ доступа и провал recovery блокируют дальнейшие отправки.
  Неуспешный `_bootstrap` сохраняется до конца сеанса: повтор fetch получает
  прежнее исключение без повторной подготовки страницы.
- `aliexpress/json_transport.py:230`: 429, распознанный как challenge, исключён
  из применения Retry-After; Ozon применяет заголовок при любом 429.
- `wildberries/transport.py:93,174`: max_attempts=3 ограничивает запросы витрины
  на endpoint, а не три вызова fetch. Собственный цикл повторяет runtime один
  раз после восстановления доступа при 401/403/498. Повторы временных сетевых
  отказов внутри витрины зависят от её кода. Синтетическая витрина в
  `tests/test_wildberries_browser.py:43` реализует собственный цикл; это не
  доказательство политики live-витрины WB. Таймаут освобождает страницу.
- `price_watch/application/collection_service.py:27` получает цель напрямую из
  коннектора; окончательная ошибка получения/сохранения записывается сразу.
  `run_executor.py` общий для worker и direct collect; numeric CLI использует
  `ProductService`, raw-режим вызывает Ozon client напрямую.

Исполнено: 30 тестов из tests.test_ozon_json_transport,
tests.test_aliexpress_transport, tests.test_wildberries_transport — passed.
Дополнительные эксперименты с FakePage/AsyncMock (без live-сети и БД):
1. AliExpress: JSON `{}` → ошибка схемы за один HTTP-вызов; следующий fetch с
   корректным fixture → успех.
2. AliExpress: временный сбой prepare → два последовательных fetch вернули
   MarketplaceUnavailable, prepare вызван только один раз, HTTP-вызовов нет.
3. AliExpress: 429 + HTML challenge + Retry-After=60 → recovery и успешный
   повтор, cooldown отсутствует; заголовок действительно обходится.

Причина наблюдавшихся пользователем live-сбоев AliExpress не установлена.
Repowise MCP ранее вернул устаревший снимок 9f3876d; его risk-выводы не являются
доказательством состояния текущего HEAD. Локальный state.json указывает текущий
HEAD a4091f8 и отключённую генерацию страниц. Локальные status/update подтверждают
этот checkpoint. В wiki.db присутствуют два repository: старый article_json_parser
с 9f3876d и текущий price-watch с a4091f8. MCP/CLI target risk возвращает старый
снимок даже при явном пути/ID, поэтому его выводы не использованы для доказательства
актуального графа. Diff risk CLI выполнен по текущему working tree (включает также
не относящийся к задаче BACKLOG); текущие источники и CodeGraph проверены отдельно.

## Agreed solution

Пользователь явно уточнил: внутренние ретраи остаются, добавляется ещё один
повтор выше для всех площадок, задержка 1 секунда с учётом Retry-After.
Перенос/удаление внутренних ретраев исключён. Имя директории создано до этого
уточнения и не определяет архитектуру решения.

Исследование выявило различия, которые необходимо учесть в конкретном плане:
не удваивать уже прошедшее ожидание Retry-After; не обещать реальный повтор
запроса при заблокированном транспорте; сохранить предел восстановления сессии;
не считать max_attempts WB эквивалентом max_attempts Ozon/AliExpress.
План одобрен пользователем 2026-11-07: «Даю добно» в ответ на конкретное
предложение сохранить внутренние попытки, добавить одну внешнюю и исправить
Retry-After при CAPTCHA и временный сбой bootstrap. Приёмка результата отдельно.

Общий helper `marketplace_connector/application/retry.py` повторяет операцию
получения данных один раз после любого Exception, кроме ProductNotFound
(доказанное отсутствие, существующая семантика сохраняется). CancelledError
не перехватывается. LeaseLost и ошибки persistence не входят в операцию.
Пауза max(1 секунда, оставшийся retry_after у RateLimited), без нового цикла
внутренних повторов внутри helper. Первый сбой логируется с traceback;
при втором исключение сохраняет связь с первым. БД не хранит промежуточный failed.
ProductService использует helper; CollectionService обращается к ProductService,
а лимит параллелизма применяется на каждую попытку и освобождается на паузе.
Numeric/raw CLI использует тот же helper в одном явно открытом клиентском сеансе.
Внешний вызов после неуспешного bootstrap может создать новую общую задачу
подготовки; незавершённая/успешная подготовка остаётся общей для соседей.
Неуспешно открытая страница закрывается, session recovery limit не сбрасывается.
AliExpress учитывает cooldown при любом 429, включая challenge.

Документация будущей реализации: openspec/specs/collection-run-execution/spec.md,
docs/guide/ARCHITECTURE.md, затронутые marketplace guides и тестовый guide.
При изменении архитектурных границ подготовить новый ADR, не переписывать ADR 0006.
Реализация использует существующий application-слой без переноса ответственности
коннекторов или изменения архитектурных границ; отдельный ADR не требуется.
Миграция БД для дополнительного повтора не предполагается; пользовательские данные
не используются в тестах. docs/BACKLOG.md имеет посторонние изменения и сохраняется.
