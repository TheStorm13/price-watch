# Design

## Context

Согласованные решения и сравнение альтернатив: docs/adr/0011-product-cards-and-variant-history.md. Предыдущий edit-card-fields заменён этим change; незавершённая общая форма используется после исправления.

## Goals / Non-Goals

Goals: одна карточка товара; нормализованные варианты; независимые история, точные цены, цели и ошибки; главный вариант для прежних каталоговых метрик. Non-goals: эвристическое объединение соседних артикулов Ozon, переписывание исторических snapshot, смена артикула/площадки.

## Decisions

marketplace_cards становится товарным уровнем с артикулом и primary_variant_id. Новая card_variants хранит точную внешнюю идентичность, подпись и параметры. История и цели запуска получают variant_id; card_id сохраняет принадлежность товару. Миграция сохраняет прежние ID как ID вариантов и переназначает товарные связи. Прямые запросы и DTO полностью переводятся на эту модель.

Очередь получает известные варианты. Проверенные ответы обнаруживают новые варианты того же артикула; они атомарно добавляются в текущий обычный запуск с увеличением total_count, затем выполняются следующей порцией. Retry берёт только прежние неуспешные цели, не добавляя уже успешные SKU. Метаданные ProductVariant не считаются ценой; каждый точный SKU проходит существующий парсер цены. Сессия переиспользуется, конкурентность ограничена.

Список/статистика/выгодность читают только главный SKU. Детали отдельно запрашивают список вариантов, график всех SKU и фильтруемую таблицу. График хранит раздельные временные ряды и null-разрывы, устойчивые цвета и видимость; выбор линии не меняет главный. Черновик формы живёт до закрытия; артикул/площадка read-only.

Export/import v3 содержит варианты и главный SKU, истории сливаются отдельно по каждому варианту. Старый формат не поддерживается скрытым адаптером. Неполные исторические идентификаторы сохраняются; сбор обнаруживает точные SKU автоматически по артикулу.

## Risks / Trade-offs

- Рост запросов по SKU → существующие лимиты и общая браузерная сессия, без неограниченного параллелизма.
- Миграция общих настроек → preflight, атомарный отказ при конфликте, тесты сохранности.
- Конкурирующие discovery/results → уникальные ключи, блокировки и lease; успех и счётчики атомарны.
- Много линий → поиск вариантов, прокрутка, скрытие серий и подписи помимо цвета.

## Migration Plan

Остановить writers; применить forward-only 0018 на disposable БД для проверки. Сохранить ID вариантов, наблюдения и raw snapshot; переназначить родителей и FK. При конфликте названий/тегов/групп/выгодных прервать до записи с ID конфликтующих карточек. В production не применять до отдельного разрешения на операцию с пользовательскими данными. Обновить все потребители и тесты; перед приёмкой проверить CLI/worker/API/UI. После приёмки документация, sync/archive и коммит.

## Исправление первичного обнаружения — 2026-11-03

Согласовано пользователем после диагностики ошибок WB «Не указан размер WB» для карточек 15/16. UI/API/CLI принимают артикул без SKU, товарная ссылка может содержать необязательный SKU. Внутренние варианты по-прежнему имеют точные пары ID. Товарный запрос WB/Ali возвращает только проверенные метаданные вариантов, без приписывания цены первому или минимальному SKU.

Имеющаяся запись без SKU служит целью начального обнаружения. В одной lease-защищённой транзакции она завершается, все точные варианты добавляются в тот же запуск, счётчики корректируются. Для retry неудачного обнаружения также разрешено расширение целей, а retry конкретного SKU сохраняет прежний состав. После обнаружения обычные запуски выбирают только точные варианты; неизвестная историческая запись сохраняется со своими наблюдениями. Пустая запись обнаружения скрыта из списка вариантов при наличии точных SKU, историческая остаётся видимой. Начальный главный выбирается детерминированно из ответа, существующий точный главный не меняется. Нет объединения или переписывания старой истории, нет новой миграции и изменений пользовательской БД при разработке.
