# decimal-money-contract Specification

## Purpose

Определяет точность цен и денежных метрик при получении, сохранении,
передаче и показе данных, включая одинаковое поведение live и mock UI.

## Requirements

### Requirement: Цены декодируются и сохраняются без двоичной арифметики
Система SHALL декодировать десятичные цены из ответа площадки без промежуточного float и использовать Decimal в Python и NUMERIC в PostgreSQL. Цена SHALL быть конечной, неотрицательной и после округления до двух знаков ROUND_HALF_UP меньше 10^12. Недопустимые значения SHALL отклоняться без частичного сохранения результата.

#### Scenario: Дробная цена
- **WHEN** площадка вернула цену 199.995
- **THEN** общая модель и история содержат Decimal 200.00 по одному правилу округления

#### Scenario: Недопустимая цена
- **WHEN** цена отрицательная, bool, NaN, бесконечная или превышает допустимый диапазон
- **THEN** результат отклоняется и прежняя цена не заменяется частичным результатом

### Requirement: Денежные значения JSON передаются строками
Все цены, минимумы, максимумы, средние и суммы выгоды в нормализованном товаре, HTTP API и CLI SHALL передаваться десятичными строками либо null. Цена товара SHALL иметь два знака после точки; вычисленные метрики SHALL сохранять доступную точность без округления для показа. Нормализованный товар SHALL иметь schema_version 2.0, а его схема SHALL соответствовать фактическому выводу, включая image_url.

#### Scenario: Передача цены
- **WHEN** сохранённая цена равна Decimal 199.90
- **THEN** товар, каталог, детали и история передают строку "199.90", а отсутствие цены — null

#### Scenario: Средняя цена
- **WHEN** вычисленная средняя содержит больше двух знаков
- **THEN** ответ сохраняет точность вычисленного значения и не округляет его до проверки выгодности

### Requirement: Клиент сравнивает денежные значения точно
Frontend SHALL хранить денежные значения десятичными строками, сравнивать их численно без float и форматировать до двух знаков ROUND_HALF_UP. Null SHALL сохранять действующие правила сортировки. Преобразование в number SHALL допускаться только для геометрии графика; подписи и tooltip SHALL использовать исходное точное значение.

#### Scenario: Числовая сортировка строк
- **WHEN** карточки имеют цены "9.90", "10.00" и null
- **THEN** сортировка по возрастанию даёт 9.90, 10.00, null, а по убыванию — 10.00, 9.90, null

#### Scenario: Изображение графика
- **WHEN** координаты строятся из числовой проекции цены
- **THEN** tooltip, подпись и денежное сравнение используют исходную десятичную строку

### Requirement: Денежный переход сохраняет очередь уведомлений
При обновлении денежного формата система SHALL однократно преобразовать прежние конечные числовые цены в localStorage уведомлений в канонические строки, сохранив pending и watermark. Действующий обработчик SHALL затем использовать только новый формат. Ошибка преобразования цены SHALL NOT удалять ожидающие обработки запуски.

#### Scenario: Обновление при ожидающем уведомлении
- **WHEN** storage содержит ожидающий запуск и ранее сохранённую числовую цену
- **THEN** запуск остаётся в очереди, цена переносится в строку, а прежняя цена не становится ложным изменением только из-за формата

### Requirement: Экспорт истории сохраняет точность и данные
Экспорт и импорт документа версии 2 SHALL использовать десятичные строки цен с прежними ограничениями и точными значениями. Числовой JSON-ввод цены SHALL отклоняться с ошибкой валидации; наличие готовых старых экспортов со строковыми ценами SHALL NOT требовать их переписи. Предпросмотр и импорт SHALL сохранять действующие транзакционные правила объединения истории.

#### Scenario: Существующий экспорт
- **WHEN** пользователь импортирует действующий v2-документ со строковыми ценами
- **THEN** цены сохраняются точно, а повторный импорт не создаёт дубликаты

#### Scenario: Цена JSON-числом
- **WHEN** в документе импорта цена передана JSON-числом вместо строки
- **THEN** API возвращает ошибку валидации до изменения данных
